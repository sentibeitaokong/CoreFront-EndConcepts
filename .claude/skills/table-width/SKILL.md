# 表格列宽

**不要自己去读表格内容、猜哪列该宽。** 这是纯布局计算，答案由浏览器决定，你猜不出来。
跑这个命令，它测完直接写回 markdown，你只需要看最后一行。

## 大部分时候你不需要跑它

提交时 husky 会自动校验（`package.json` 的 `lint-staged`）：

- **这次要提交的文件里，每一张表都过一遍**：没填 `[width(...)]` 的补上，填了但不是
  最优的改成最优。是**全量**，不只你这次改过的那几张。
- 整个文件一张表都没有 → **~50ms 退出，连浏览器都不起**。
- 有表格时约 **4–8 秒**（复用你已在跑的 dev server 就快些）。
- 已经是最优的表报「未变」、不写文件。所以重复提交不产生改动（实测幂等）。
- **算不出来不会拦提交**，只会打一行告警。宽度没算好是「不够好」，不是「有问题」。

所以下面这些情况才需要手动跑：只处理某几张表（`--heading` / `--table`）、
在没走 git 的环境里试。

## 跑

dev server 不用你操心——已经在跑就复用，没有就自己拉一个，跑完关掉。

```bash
node .claude/skills/table-width/scripts/fix-widths.mjs apps/docs/js/basic/closure.md
# 可以一次传多个文件
node .claude/skills/table-width/scripts/fix-widths.mjs a.md b.md c.md
```

| 选项               | 用途                                                         |
| ------------------ | ------------------------------------------------------------ |
| `--dry`            | 只报告，不改文件（**先跑这个看它想改什么**）                 |
| `--insert`         | 给没有 `[width(...)]` 的表格补一条                           |
| `--heading <前缀>` | 只处理某个标题下的表格，如 `--heading '## 3.'`               |
| `--table <n>`      | 只处理第 n 张（1 起，按 DOM 顺序）                           |
| `--check`          | 需要改动时退出码 5，文件不动（给 CI 用）                     |
| `--quiet`          | 不打印未改动的表格                                           |
| `--json`           | 机器可读，**别在正常流程里用**——它的意义就是让你不必看见细节 |
| `--auto`           | 给 husky 用的，手动跑不需要                                  |

输出（改动/未变/跳过各一行，最后一行汇总）：

```
~ #2 3col 20,30,50 -> 21,37,42  -24px  L76
apps/docs/js/basic/foo.md: 1 改动, 2 未变, 0 跳过 -> 写入 1 处
```

`-24px` 是表格渲染高度省下的像素。**未变的表格说明当前值已经是最优**，不是失败。

## 看完输出做什么

- **有 `~`（改动）**：已经写进文件了。不用再手工核对数值——工具写完会重新读文件、
  重新解析、复测高度，任一项对不上就整体放弃并保留原文件（退出码 1）。
- **全是 `=`（未变）**：什么都不用做，本来就好。
- **有 `!`（跳过）**：看原因，常见三种：
  - `表格有合并单元格（colspan/rowspan）` —— 不支持，手工写一个合理的值。
  - `没有 [width(...)]（加 --insert 可以补一条）` —— 按需加 `--insert`。
  - `结果未通过自检` —— 是工具的 bug 或页面异常，把这个原因原样告诉用户，别硬改。
- **退出码 3**：连自己拉都没拉起来 dev server（多半是没 `pnpm install`）。看报错原文。
- **退出码 4**：页面上的表格数和文件里的对不上（URL 指错页）。别忽略，会写错地方。

## 两个要知道的点

- **它只保证「实测最优 + 写回成功」，不保证表格内容本身合适。** 如果内容该拆成两张表
  或该精简，那是内容问题，宽度帮不了。
- **回写时不会跑 prettier --write。** 现有文档并不全是 prettier-clean 的，跑了会顺带改掉
  无关的行。提交时 lint-staged 会格式化，不用在这操心。

改完之后 `git diff` 应该只有 `[width(...)]` 行变了。要是多了别的改动，说明有问题，回滚。
