# 首屏体验优化

**核心本质**：首屏优化（First Contentful Paint & LCP Optimization）是一场“**时间争夺战**”。它的目标并非无脑压缩一切，而是通过精准的关键渲染路径（Critical Rendering Path）编排，让用户以最快速度看到主体内容，并完成核心交互。

**战术纪律**：优先砍掉最长的网络瀑布流，优先打散主线程最长的阻塞任务。

> 相关：[从输入 URL 到页面渲染](/networkAndBrowsers/browser/renderingProcess) 详解关键渲染路径与回流重绘。

## 1. 首屏渲染的生命周期链路

一次典型的首屏加载，本质上是浏览器资源的获取与解析接力。理解链路是寻找瓶颈的前提：

- **网络建立**：DNS 解析 -> TCP 握手 -> TLS 协商 -> 获取并下载 HTML。
- **DOM 解析**：浏览器单线程从上到下解析 HTML，遇到 `<script>` 或 `<link>` 触发资源请求。
- **渲染树构建**：下载并解析 CSS（CSSOM 构建会阻塞渲染）。
- **执行与激活**：下载并执行首屏强依赖的 JS 脚本（CSR 应用此时才开始生成 DOM）。
- **绘制上屏**：Layout（布局计算） -> Paint（绘制像素） -> Composite（图层合并），首屏内容最终呈现。

**链路阶段与指标、瓶颈的对照**（排查时先定位阶段，再谈手段）：

[width(17,24,59)]

| 链路阶段   | 对应指标          | 常见瓶颈                             |
| ---------- | ----------------- | ------------------------------------ |
| 网络建立   | TTFB              | 无 CDN、DNS 慢、TLS 往返多、重定向链 |
| HTML 下载  | TTFB → 首字节到达 | 服务端渲染慢、接口串行等待           |
| DOM 解析   | DOMContentLoaded  | 同步 `<script>` 阻塞解析             |
| CSSOM 构建 | FCP（白屏结束）   | 关键 CSS 未内联、`@import` 造成串行  |
| JS 执行    | LCP / INP / TBT   | 首屏包过大、长任务霸占主线程         |
| 绘制上屏   | LCP               | 主线程被占住、图片发现时机太晚       |

## 2. 服务端与网络提速

首屏慢，很多时候是底座慢（TTFB 过高）。

- **边缘交付**：全量静态资源与不常变的 HTML 必须挂载 CDN。对半动态页面探索 Edge Rendering（边缘渲染）或流式传输。
- **架构升级**：内容型（如资讯、电商详情页）或重度依赖 SEO 的系统，必须采用 SSR（服务端渲染）或 SSG（静态生成），彻底消灭 CSR 的“**千禧白屏**”。
- **接口前置聚合**：如果首屏需要串行调取 3 个以上 API，强烈建议在服务端或 BFF（Backend For Frontend）层进行接口聚合，一次性吐出，或直接将首屏数据内联（Inline）在 HTML 的 `<script>` 标签中。

## 3. 关键资源调度与抢占

浏览器的默认并发下载能力是有限的，必须手动指挥它“**先加载什么，后加载什么**”。

- **首屏主图特权**：对首屏最具视觉冲击力的元素（Banner、Hero 视频图），给予最高优先级 `fetchpriority="high"`。
- **阻塞剔除 (Critical CSS)**：首屏渲染极其依赖 CSS。建议内联“**首屏关键样式**”，并将其余不重要的 CSS 设为异步加载，防止其阻塞渲染树的构建。
- **非关键资源延后**：非首屏图片（Lazyload）、底部评论区组件、第三方统计脚本（如 Google Analytics、Sentry），一律延后到 `requestIdleCallback` 或 `window.onload` 之后执行。

```html
<head>
  <!-- ① 关键字体：preload 抢下载。
       两个必写项 —— as="font" 声明类型（写错会导致重复下载），
       crossorigin 是字体规范的硬性要求（匿名跨域模式），漏了同样会被下载两次 -->
  <link
    rel="preload"
    href="/fonts/inter.woff2"
    as="font"
    type="font/woff2"
    crossorigin
  />

  <!-- ② 首屏主图：preload 负责“提前被发现”，fetchpriority="high" 负责“排到最前面”。
       两者是两件事，只写一个都收效有限：preload 解决发现时机，fetchpriority 解决排队顺位 -->
  <link rel="preload" as="image" href="/hero.avif" fetchpriority="high" />

  <!-- ③ 关键样式：CSSOM 是渲染树的前置条件，必须同步加载，不能省。
       更优的做法是把首屏关键 CSS 直接内联进 head，其余样式用 media/onload 异步化（见下方示例） -->
  <link rel="stylesheet" href="/assets/home.css" />

  <!-- ④ 第三方统计：与业务完全解耦、不影响首屏，用 defer —— 后台并行下载，
       但等 HTML 解析完才执行，绝不阻塞首屏；独立性更强的脚本可用 async -->
  <script defer src="https://analytics.com/script.js"></script>
</head>
```

**浏览器默认优先级速查**——先知道它会怎么排,才知道该干预谁（Network面板的`Priority`列可以实测验证）：

[width(33,15,52)]

| 资源                         | 默认优先级     | 干预手段                                      |
| ---------------------------- | -------------- | --------------------------------------------- |
| HTML 文档                    | 最高           | ——                                            |
| `<head>` 中同步加载的 CSS    | 最高           | 内联首屏关键 CSS，其余用 `media` / 异步加载   |
| 视口内的 `<img>`             | 高             | `fetchpriority="high"` 再往上顶，或 `preload` |
| `<script>`（无 async/defer） | 高（阻塞解析） | 能移就移走；关键脚本用 `preload` + 立即执行   |
| `async` / `defer` 脚本       | 低             | 首屏强依赖的脚本提升为 `preload`              |
| 视口外的图片                 | 低             | `loading="lazy"` 进一步降级                   |
| `<link rel="prefetch">`      | 最低           | 只用于**未来**页面的资源，绝不用于首屏        |

## 4. 客户端运行时剥离

现代前端最沉重的负担在于：**庞大的 JavaScript 包不仅需要下载，更需要极其耗时的单线程解析与执行**。

- **极致的路由拆分**：首屏 JS 强行锁定在仅包含当前路由页面的逻辑。
- **超重组件“放逐”**：首屏如果存在 Echarts、PDF.js、Three.js 或富文本编辑器，必须使用动态引入 `import()` 进行物理隔离。
- **砍掉初始化冗余**：检查全局的 `main.ts` 或 `App.vue`。如果启动时去扫描了全量的持久化数据（如几千条 IndexedDB 记录），或是全量执行了不必要的鉴权运算，请将其推迟。

```javascript
// Vue 3 异步组件隔离法
import { defineAsyncComponent } from 'vue'

// 只有当用户真的点开了图表弹窗，这个重型文件才会被拉取并解析
const HeavyChartPanel = defineAsyncComponent({
  loader: () => import('./components/HeavyChartPanel.vue'),
  delay: 200, // 防闪烁延迟
})
```

**高频场景：不同类型页面的首屏策略**

[width(15,18,67)]

| 页面类型        | 首屏瓶颈                | 优先动作                                                      |
| --------------- | ----------------------- | ------------------------------------------------------------- |
| 电商详情页      | LCP 大图 + 接口串行     | 主图 `preload` + `fetchpriority="high"`；价格/库存走 BFF 聚合 |
| 资讯 / 内容列表 | 首屏 HTML 与图片        | SSR / SSG，首屏前几条直接渲染进 HTML，图片走 CDN 按需出图     |
| 后台工作台      | 首屏 JS 体积 + 鉴权阻塞 | 路由级拆包、图表等重型库动态 `import()`、鉴权并行或后置       |
| 营销活动页      | 视觉资源密集            | 首屏资源强预载，非首屏一律懒加载，关键 CSS 内联               |
| 多语言站点      | 语言包与字体            | 只加载当前语言包，中文字体做子集化裁剪                        |

## 5. DOM 复杂度与视觉维稳

渲染引擎的压力同样不可忽视。

- **控制 DOM 深度**：首屏 DOM 节点总数建议控制在 1500 个以内，最大嵌套深度不超过 32 层。深不可测的 DOM 树会几何级增加 Layout 的计算时间。
- **严打强制同步布局 (Layout Thrashing)**：绝不要在 JS 的循环中交替进行 DOM 的“**读**”操作（如 `offsetHeight`）和“**写**”操作（如 `style.height`）。
- **防御 CLS (累积布局偏移)**：骨架屏不仅是为了好看，更是为了“**占坑**”。骨架屏的物理尺寸必须与真实数据加载后的尺寸 1:1 对齐，绝不能让真实内容上屏时把别的元素挤飞。

## 6. 核心度量指标

优化没有玄学，一切看真实数据的 P75 分位值表现：

[width(25,56,19)]

| 核心指标                 | 观测目标与含义                                     | 优化达标线 |
| ------------------------ | -------------------------------------------------- | ---------- |
| **TTFB** (首字节)        | 服务器响应是否拖了后腿。                           | < 800ms    |
| **FCP** (首次内容绘制)   | 用户何时打破了令人焦虑的纯白屏。                   | < 1.8s     |
| **LCP** (最大内容绘制)   | 首屏主体内容是否已完整呈现。                       | < 2.5s     |
| **INP** (交互到下次绘制) | 首屏期间，JS 是否把主线程卡死，导致点击无响应。    | < 200ms    |
| **CLS** (累积布局偏移)   | 首屏加载全程，画面是否出现了令人不悦的抖动和错位。 | < 0.1      |

## 7. 常见问题 (FAQ)

### 7.1 首屏优化应该先从哪一步动手？

- **先量 TTFB**：如果超过 800ms，后面所有优化都是杯水车薪——先解决 CDN、服务端渲染、接口串行这些底座问题；
- **再看 LCP 是哪个元素、卡在哪一段**（四段拆解见 [Core Web Vitals](/performanceOptimization/coreWebVitals)）：图的问题去压图，渲染延迟的问题去砍 CSS/JS；
- **最后收拾 JS 体积与长任务**，它们决定 FCP 之后的体感与 INP。

一句话：**先修水管（网络与服务端），再修路障（阻塞资源），最后才是轻装（拆包）**。

### 7.2 用了 SSR 就一定比 CSR 快吗？

不一定，SSR 只是把「生成 HTML」提前到了服务端，换来的是**更快的 FCP/LCP**，代价也随之而来：

- **TTFB 变长**：服务端要多做一次数据获取与模板渲染，服务端一旦慢，反而拖垮所有指标；
- **需要水合 (Hydration)**：HTML 到了、JS 还得跑一遍才能交互，水合期间点击无响应（INP 变差）；
- **架构成本**：缓存、降级、异常处理都要重新设计。

所以 SSR / SSG / 流式 SSR 是**换收益的方案**，不是免费的加速开关。内容型、SEO 强依赖的页面收益最大；后台系统这类不需要 SEO 的应用，CSR + 精细拆包往往更划算。

### 7.3 内联关键 CSS 会不会反而变慢？

可能，如果做法不对：

- **内联得太多**：把整站样式都塞进 HTML，等于**每个页面都重复下载一遍**，还失去了浏览器缓存；
- **只内联首屏、其余异步**才是正确姿势，且总量控制在十几 KB 量级；
- 记得配合构建工具**自动提取**（如 `critters`），别手工维护，否则改版后必然失同步。

### 7.4 `defer` 和 `async` 到底怎么选？

[width(32,30,38)]

| 脚本类型                       | 用什么                    | 原因                           |
| ------------------------------ | ------------------------- | ------------------------------ |
| 业务入口、有依赖关系的模块     | `defer` / `type="module"` | 保序执行，且在 DOM 解析完之后  |
| 完全独立的第三方（埋点、统计） | `async`                   | 谁先下载完谁先执行，不阻塞解析 |
| 首屏强依赖的关键脚本           | `preload` + 正常加载      | 抢下载优先级，同时保证执行时机 |

原则：**有依赖用 `defer`，无依赖用 `async`，首屏关键用 `preload` 抢带宽**。

### 7.5 首屏要串行调 3 个接口，怎么优化？

按收益从高到低：

- **BFF 层聚合**：服务端并行调完，只给前端一个接口，直接砍掉两轮往返；
- **首屏数据内联**：SSR 场景下把数据直接写进 HTML（`window.__INITIAL_STATE__`），前端拿到就能渲染，不用再等接口；
- **改成并行**：若必须前端自己调，用 `Promise.all` 并行，并注意不要互相阻塞；
- **拆优先级**：主内容先渲染，次要模块（推荐位、评论数）延后加载。

### 7.6 骨架屏是不是只是「好看的 Loading」？

不是，但**只有尺寸对得上才有价值**。骨架屏的两项真实收益：

- **心理收益**：让用户明确“**内容正在来**”，降低跳出；
- **性能收益**：**提前占位**，把 CLS 消灭在加载阶段——这也是它比转圈 Loading 更高级的地方。

反面案例：骨架屏比真实内容矮/高，数据一回来整页跳一下，反而把 CLS 做坏了。

### 7.7 首屏 JS 包太大，第一刀砍在哪里？

先看**构成**再下手，别凭感觉：

- **用打包分析工具**（`webpack-bundle-analyzer` / `rollup-plugin-visualizer`）找出体积 top 10；
- **先干这些**：重复依赖（同一库多版本）、全量引入的 UI 库 / 图标库、`moment` 这类可替换的重库（换 `dayjs`）、仅用于开发环境的代码没被 tree-shake；
- **再拆**：路由级懒加载、重型组件动态 `import()`、把首屏用不到的 polyfill 按需注入。

> 常见误区：盯着几百行的业务代码抠，却放任一个 300KB 的图表库常驻首屏。
