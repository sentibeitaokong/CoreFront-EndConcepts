# 资源加载优化

**核心本质**：资源加载优化的终极奥义，并非将所有静态资源一股脑地提前塞给浏览器，而是充当一名精密的“**交通指挥官**”。你需要指挥浏览器在极为有限的带宽、有限的并发连接数以及单线程的主线程时间里，优先服务那些真正决定首屏存亡和核心交互的资源。关键资源晚一秒，LCP（最大内容绘制）就晚一秒；而非关键资源如果抢跑，关键渲染路径（Critical Rendering Path）就会被无情挤占，导致页面“**假死**”。

**战术纪律**：当前页面立刻要用的资源，使用 `preload` 抢占；未来极大概率要用的资源，使用 `prefetch` 捡漏；第三方跨域的关键域名，使用 `preconnect` 铺路。精准克制，绝不滥用。

> 相关：[浏览器缓存机制](/networkAndBrowsers/caching/browserCache) 与 [前端缓存策略](/networkAndBrowsers/caching/frontendCacheStrategy) 从缓存视角补充资源加载的复用策略。

## 1. 浏览器资源调度链路

现代浏览器极其聪明，但它再聪明也需要时间去解析和推断。理解浏览器的内部调度链路，是你介入优先级控制的前提：

- **资源发现时机**：浏览器的 HTML 流式解析器、CSS 词法分析器以及 JavaScript 引擎的执行，都会在不同阶段暴露出新的资源请求。
- **网络建连损耗**：每一次全新的跨域请求，都不可避免地经历 DNS 查询、TCP 三次握手和极其耗时的 TLS 密文协商。
- **启发式排队与降级**：浏览器内部有一套默认的优先级评分机制（Highest, High, Medium, Low, Lowest）。通常，HTML 文档、关键 CSS 和视口内的图片会被赋予极高优先级；而异步脚本、视口外的图片则会被自动降级。
- **下载解码与执行**：资源下载完毕仅仅是开始。图片的解码、字体的光栅化、JavaScript 的 V8 编译，都会继续疯狂消耗 CPU 资源。
- **木桶效应**：CSS（构建 CSSOM）、定制字体（FOUT/FOIT）、LCP 英雄图片以及主入口 JS，这四者是决定首屏生死的核心要素。

**资源提示 (Resource Hints) 全家福**

[width(36,24,13,27)]

| 指令                                  | 做到哪一步                     | 成本             | 典型用途                                  |
| ------------------------------------- | ------------------------------ | ---------------- | ----------------------------------------- |
| `<link rel="dns-prefetch">`           | 只做 DNS 解析                  | 极低             | 所有**可能**会用到的第三方域名            |
| `<link rel="preconnect">`             | DNS + TCP + TLS                | 中（占用连接数） | 确定会用到的跨域核心域名（CDN、接口域名） |
| `<link rel="preload">`                | 下载当前页**立刻要用**的资源   | 高（抢带宽）     | 字体、LCP 图、首屏关键 CSS / JS           |
| `<link rel="modulepreload">`          | 下载**并预解析** ES 模块依赖图 | 中高             | ESM 入口及其静态依赖                      |
| `<link rel="prefetch">`               | 空闲时下载**未来页面**的资源   | 低               | 下一个路由的 chunk、多步表单的下一步      |
| `prerender` / Speculation Rules       | 后台**完整渲染**目标页         | 极高             | 转化路径上命中率极高的下一页              |
| `fetchpriority="high"｜"low"`（属性） | 调整**已存在资源**的优先级     | 无               | 首屏大图提优、非首屏图降级                |

> 一句话记住三者的区别：**preconnect 只铺路不搬货，preload 搬当前要用的货，prefetch 搬以后可能用的货。**

## 2. 抢占当前页面关键资源

`preload` 是开发者向浏览器下达的强制指令：“**不要等解析到对应的 DOM 才去下载，现在、立刻、马上把这个资源拉下来，我保证页面很快就会用到它。**”

```html
<link
  rel="preload"
  href="/fonts/main.woff2"
  as="font"
  type="font/woff2"
  crossorigin="anonymous"
/>

<img src="/img/hero.avif" fetchpriority="high" alt="Hero Banner" />
```

- **适用靶点**：首屏最大内容绘制（LCP）图片、防闪烁的关键字体、当前路由极其关键的 CSS 文件，以及那些深藏在 CSS 文件内部、浏览器极难提前发现的背景大图。
- **类型声明（as 属性）**：必须绝对准确。错误的类型声明会导致浏览器使用不同的请求上下文（Request Context），最终导致资源被重复下载两次，严重浪费带宽。
- **跨域属性（crossorigin）**：字体文件即使在同源策略下，规范也要求必须以匿名跨域模式请求。漏写 `crossorigin` 是导致字体被重复拉取的头号元凶。
- **克制与收敛**：如果把所有资源都打上 `preload`，就等于没有优先级。滥用会导致浏览器并发数爆满，反而把真正的关键资源堵在网络队列里。

## 3. 预取未来高概率资源

如果说 `preload` 是“**雪中送炭**”，那么 `prefetch` 就是“**锦上添花**”。它的优先级极低，专门利用浏览器渲染完毕后的网络空闲期，静默下载未来可能会用到的资源。

```html
<link rel="prefetch" href="/assets/dashboard-chunk.js" as="script" />

<script type="speculationrules">
  {
    "prerender": [{ "source": "list", "urls": ["/next-page"] }]
  }
</script>
```

- **黄金场景**：多步表单的下一步逻辑、登录成功后必然跳转的工作台页面、鼠标悬停（Hover）在导航菜单上时的目标路由包裹。
- **严格隔离首屏**：绝不允许用 `prefetch` 去拉取当前首屏的关键资源，这会导致首屏加载出现毁灭性的延迟。
- **弱网环境的克制**：在 3G 或极差的移动网络下，低命中率的预取会疯狂消耗用户的有限流量和手机电量。成熟的框架（如 Next.js/Nuxt）通常会结合 `navigator.connection` API，在 4G/WIFI 环境下才开启预取。
- **数据驱动预判**：不要靠产品经理的直觉去预取。应当基于真实用户的数据埋点（如马尔可夫链模型），精准算出点击转化率最高的下一个页面。

## 4. 缩短第三方建连耗时

第三方域名（如 CDN、统计、客服系统）的第一个请求，往往要承受完整的 DNS + TCP + TLS 的“**三连暴击**”，耗时动辄几百毫秒。提前打通网络管道，是优化第三方加载的最佳手段。

```html
<link rel="preconnect" href="https://cdn.example.com" crossorigin />

<link rel="dns-prefetch" href="//static.example.com" />
```

- **preconnect 策略**：极其适合那些承载了首屏核心图片、核心字体或是核心 API 接口的跨域服务器。它会在后台静默完成漫长的 TLS 握手。
- **dns-prefetch 策略**：由于不建立 TCP 链接，几乎没有成本。可以把页面内所有潜在的第三方域名全部列上。
- **严格控制数量**：浏览器同时维持的 TCP 闲置连接数是有上限的（通常单域名 6 个）。如果给十几个域名建立 `preconnect` 却迟迟不发送真实请求，连接会在 10 秒左右被浏览器主动切断，你的优化心血将付之东流。

## 5. Script 加载策略

JavaScript 的下载与执行时机，直接决定了 HTML 解析器是否会被强制挂起（Blocking）。

```html
<script src="/legacy-jquery.js"></script>

<script src="/analytics.js" async></script>

<script src="/main.js" defer></script>

<script type="module" src="/src/main.js"></script>
```

- **async（异步执行）**：谁先下载完谁就立刻抢占主线程执行。它完全破坏了脚本之间的依赖顺序，极其适合那些与业务逻辑完全解耦的独立脚本（如 Google Analytics、各种打点探针）。
- **defer（延迟执行）**：它向浏览器保证：“**我只在后台默默下载，绝对不打断 HTML 解析。等 DOM 树彻底构建完毕（`DOMContentLoaded` 触发前），我再严格按照 `<script>` 标签书写的先后顺序依次执行。**” 这是目前前端入口脚本的标准答案。

[width(31,11,27,11,20)]

| 写法                           | 是否阻塞解析 | 执行时机                          | 执行顺序   | 适用场景                 |
| ------------------------------ | ------------ | --------------------------------- | ---------- | ------------------------ |
| `<script src>`                 | **阻塞**     | 下载完立即执行                    | 保序       | 几乎没有（除非必须同步） |
| `<script async>`               | 不阻塞       | 谁先下载完谁执行                  | **不保序** | 完全独立的第三方脚本     |
| `<script defer>`               | 不阻塞       | DOM 解析完、`DOMContentLoaded` 前 | 保序       | 业务入口脚本             |
| `<script type="module">`       | 不阻塞       | **默认即 defer**                  | 保序       | 现代 ESM 入口            |
| `<script type="module" async>` | 不阻塞       | 下载完立即执行                    | 不保序     | 无依赖的独立模块         |

> `type="module"` 自带 defer 这一点常被忽略——所以现代项目里 `<script type="module" src="/src/main.js">` 已经是「不阻塞 + 保序」的组合；想抢下载优先级，再额外加一条 `preload` 或把入口挂上 `fetchpriority`。

## 6. 字体、第三方资源与主线程解放

第三方资源（客服、广告、埋点、地图）往往是首屏性能崩溃的罪魁祸首，它们常常肆无忌惮地抢占关键渲染路径。

- **字体加载体验（FOIT vs FOUT）**：使用 `font-display: swap`，告诉浏览器如果自定义字体还没下载完，先用系统默认字体兜底显示文字，绝不让用户盯着一块空白屏幕发呆。
- **第三方脚本的终极延后**：那些不影响用户核心体验的探针或客服代码，必须延后到页面完全空闲时加载。可以利用 `window.onload` 结合 `requestIdleCallback` 实现极致的错峰执行。

:::details

```js
window.addEventListener('load', () => {
  requestIdleCallback(() => {
    import('./analytics.js')
  })
})
```

:::

- **拥抱 Web Worker (Partytown)**：对于重度消耗主线程的第三方脚本，可以使用类似于 Partytown 这样的先进库，将它们全部放逐到 Web Worker 中运行，彻底解放浏览器的渲染主线程。
- **错误沙箱隔离**：第三方资源的超时、崩溃或是接口 500 报错，必须被异常捕获（Try/Catch 或全局 Error Boundary）拦截，绝不能牵连主业务线白屏。

**高频场景：常见第三方资源的处理姿势**

[width(29,30,41)]

| 第三方类型                | 主要风险                  | 处理方式                                                                |
| ------------------------- | ------------------------- | ----------------------------------------------------------------------- |
| 埋点 / 统计（GA、Sentry） | 阻塞解析、拖慢 INP        | `async` + 延后到 `load` 后加载；重度脚本可用 Partytown 丢进 Worker      |
| 客服 / 在线咨询 SDK       | 体积大、往页面里插 DOM    | **用户点击后再加载**，先用自绘按钮占位                                  |
| 广告 / 推荐位             | 完全不可控、CLS 重灾区    | 预留固定高度容器 + `iframe` 沙箱隔离，绝不改文档流                      |
| 地图 / 播放器 SDK         | 体积大，且只在个别页面用  | 动态 `import()` 按需加载，别进主包                                      |
| 字体                      | FOIT/FOUT、最容易重复下载 | `font-display: swap` + `preconnect` + `preload`（务必带 `crossorigin`） |

## 7. 核心度量指标与水位线

优化效果必须用冷酷的数据来验收。以下是资源调度优化的核心监控矩阵：

[width(22,52,26)]

| 核心度量指标             | 观测目标与深度解析                                                                              | 极客级优化达标线                           |
| ------------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **LCP Resource Delay**   | 最大内容绘制资源的发现是否太晚？如果 HTML 解析了很久才开始请求主图，说明缺乏 `preload`。        | **接近于 0ms** (HTML 收到后立即发起请求)   |
| **Request Waterfall**    | 关键网络请求瀑布流中，是否存在严重的串行排队、等待或是资源阻塞现象。                            | **消除阶梯状长链**，实现首屏核心资源高并发 |
| **TTFB (首字节时间)**    | 服务端响应、DNS 解析以及连接建立的耗时是否严重拖垮了后续所有资源的加载起点。                    | **< 800ms** (边缘节点交付更应 < 200ms)     |
| **Unused Preload**       | 你的“**预判**”是否失误？所有被 preload 但在页面加载后几秒内未被使用的资源，都是严重的性能事故。 | **绝对值为 0** (100% 精准命中)             |
| **Third-party Blocking** | 第三方不可控资源（广告/监控）占用主线程的时间总和，是否严重影响了 INP 交互延迟。                | **首屏关键路径内为 0ms**                   |

## 8. 常见问题 (FAQ)

### 8.1 `preload` 了但页面没用上，会怎样？

会有实打实的代价，不是「写了也没坏处」：

- **控制台警告**：Chrome 会提示 _The resource was preloaded but not used within a few seconds_；
- **带宽被白白占用**：它抢的是**最高优先级**的下载通道，挤掉的正是真正关键的资源；
- **可能被下载两次**：如果 `as` 写错（请求上下文不一致），浏览器会把同一个资源再拉一遍。

所以 `preload` 的铁律是**精准**：只给「当前页面首屏确定要用、且浏览器发现得晚」的资源用。上线后要盯 Network 面板，确认每一条 preload 都真的被用到了。

### 8.2 `preload` 字体为什么必须写 `crossorigin`？

因为**字体请求在规范上永远是跨域模式**，即便同源也一样。`preload` 里如果不写 `crossorigin`，浏览器会按「无 CORS」的上下文去下载，而真正用到字体时是「CORS 模式」请求——两次请求的凭据模式不同，缓存无法复用，于是**字体被下载两次**。

这也是「明明 preload 了字体，Network 里却出现两条字体请求」的经典原因。正确的写法是 `crossorigin` 或 `crossorigin="anonymous"`（**不能写 `use-credentials`**，除非服务端真的需要凭据）。

### 8.3 `prefetch` 和 `preload` 到底差在哪？

[width(15,31,54)]

| 维度       | `preload`                 | `prefetch`                    |
| ---------- | ------------------------- | ----------------------------- |
| 目标       | **当前**页面马上要用      | **未来**页面可能要用          |
| 优先级     | 高（抢占）                | 最低（捡漏）                  |
| 触发时机   | 立刻开始下载              | 浏览器判断空闲时才下载        |
| 跨页复用   | 只服务当前导航            | 可被后续导航复用（HTTP 缓存） |
| 用错了后果 | 挤占关键资源、Unused 警告 | 浪费用户流量与电量            |

一句话：**preload 用错会伤当前页，prefetch 用错会伤用户流量**。

### 8.4 `modulepreload` 是干什么的？

它是为 **ESM 模块**专门设计的 `preload`。普通的 `preload as="script"` 只下载单个文件，而 ESM 会有依赖图（入口 import A，A import B…），浏览器得逐层解析才能发现下一个依赖——`modulepreload` 会**下载并提前解析**这个模块及其静态依赖，把串行的瀑布流压平。

现代打包工具（Vite）会自动为入口预置它，一般不用手写；但如果你手工控制 ESM 入口，记得补上。

### 8.5 `defer` 与 `type="module"` 有什么区别？

`type="module"` 的脚本**默认就是 defer 行为**（并行下载、解析完 DOM 后保序执行），所以不需要也不应该再写 `defer`。它们的区别在别处：

- **作用域**：模块有自己的顶层作用域，不会污染全局；
- **严格模式**：模块代码自动是严格模式；
- **请求模式**：模块**始终以 CORS 模式**请求，跨域需要正确的 CORS 响应头；
- **执行一次**：同一模块被多次 import 只会执行一次。

### 8.6 `preconnect` 建太多会有什么问题？

- **占用连接资源**：浏览器对每个域名的并发连接数有限（通常 6 个），提前建连会占住名额；
- **白建易断**：建立后约 10 秒内没有真实请求，浏览器会主动断掉连接——等真正要用时，又得重来一遍。

所以 `preconnect` 只给**首屏必需的 2~4 个关键域名**用；其余域名一律降低为 `dns-prefetch`（几乎零成本，可以放心多写）。

### 8.7 怎么验证预加载 / 优先级真的生效了？

- **Priority 列**：右键表头打开它，确认高优资源确实是 `Highest` / `High`；
- **Initiator 列**：确认资源的发起者是 `preload`（而不是某个 CSS/JS 深处）；
- **Waterfall 时序**：确认关键资源是**尽早并发**发出的，而不是被排成阶梯状长链。

另外用 Performance 面板看 `LCP Resource Delay`：如果主图是「HTML 收到后立刻发起请求」，说明 preload 生效了；如果延迟很久，就说明发现时机仍然太晚。
