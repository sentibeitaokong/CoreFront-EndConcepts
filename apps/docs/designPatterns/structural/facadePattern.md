# 外观模式

## 1. 核心概念与价值

外观模式的定义是：**为子系统中的一组接口提供一个一致的界面，此模式定义了一个高层接口，这个接口使得这一子系统更加容易使用。**

[width(11,59,30)]

| 维度           | 描述                                                                                                                                                              | 形象比喻                                                                 |
| :------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------- |
| **核心意图**   | 隐藏系统的复杂性，提供一个简单的入口。                                                                                                                            | **全屋智能面板**。按一下“**离家模式**”，自动关灯、关空调、锁门、开监控。 |
| **关键角色**   | **外观 (Facade)**：对外暴露简化的高层接口；**子系统 (Subsystem)**：真正干活的多个类，彼此独立；**客户端 (Client)**：只依赖外观，不直接触碰子系统。                | **酒店前台**。你只找前台，前台替你联系厨师、保洁和司机。                 |
| **主要优点**   | 1. **简化调用**：客户端无需了解底层的复杂逻辑；<br>2. **降低耦合**：业务代码只依赖外观对象，不依赖底层子系统；<br>3. **灵活性**：底层系统变动时，只需修改外观类。 | **遥控器**。一个按钮背后可能是十几个元器件的协同工作。                   |
| **主要缺点**   | 如果设计不当，外观类可能变得过于庞大（演变成“**上帝对象**”）。                                                                                                    | **集权过度**。如果前台辞职了，所有服务都找不到了。                       |
| **适用场景**   | 1. 子系统复杂、调用步骤繁琐；<br>2. 需要为遗留代码提供更清爽的新入口；<br>3. 要按层次组织系统，让上层只通过固定门面通信。                                         | **旅行管家**。机票、酒店、签证打包成一条龙。                             |
| **不适用场景** | 1. 子系统本就简单，再加一层纯属多余；<br>2. 客户端需要频繁使用底层的高级能力，外观反而挡住路。                                                                    | **多此一举**。本来一步就能开灯，却非要绕去总控面板。                     |

## 2. 模式实现：从“琐碎”到“一键触发”

### 2.1 实战场景：跨浏览器兼容性封装

这是前端开发中最经典的“**外观**”。以前为了兼容 IE 和标准浏览器，我们必须写很多判断。

```js
// 这是一个“外观”函数
function addEvent(el, type, fn) {
  // 隐藏底层的判断逻辑
  if (el.addEventListener) {
    el.addEventListener(type, fn, false)
  } else if (el.attachEvent) {
    el.attachEvent('on' + type, fn)
  } else {
    el['on' + type] = fn
  }
}

// 业务代码：调用极其简单
addEvent(document.body, 'click', () => console.log('点击了'))
```

### 2.2 实战场景：子系统整合 (家庭影院示例)

假设开启影院模式需要操作多个独立系统。

```js
// 子系统 A：屏幕
class Screen {
  up() {
    console.log('屏幕升起')
  }
  down() {
    console.log('屏幕降下')
  }
}

// 子系统 B：音响
class Audio {
  on() {
    console.log('音响开启')
  }
  setVolume(v) {
    console.log(`音量设为: ${v}`)
  }
}

// 外观类 (Facade)
class HomeTheaterFacade {
  constructor() {
    this.screen = new Screen()
    this.audio = new Audio()
  }

  // 高层接口：一键观影
  watchMovie() {
    console.log('--- 准备观影 ---')
    this.screen.down()
    this.audio.on()
    this.audio.setVolume(10)
  }
}

// 客户端使用
const theater = new HomeTheaterFacade()
theater.watchMovie()
```

### 2.3 真实项目里的常见落地场景

[width(20,31,49)]

| 场景             | 外观提供的“**一键入口**”      | 被隐藏的子系统                                      |
| :--------------- | :---------------------------- | :-------------------------------------------------- |
| 跨浏览器事件绑定 | `addEvent(el, type, fn)`      | `addEventListener` / `attachEvent` / `onXxx`        |
| 前端发起请求     | `request(config)`（如 axios） | 适配器选择、拦截器链、JSON 解析、错误处理           |
| 组件库全局提示   | `Message.success('...')`      | DOM 创建、定时器、动画、销毁队列                    |
| Node 读取配置    | `config.get('db.host')`       | 默认值、环境变量、配置文件的合并与优先级            |
| 一键初始化 SDK   | `sdk.init(options)`           | 埋点、日志、上报、鉴权、路由挂钩                    |
| 浏览器存储封装   | `storage.set(k, v)`           | `localStorage` / `sessionStorage`、序列化、过期策略 |

## 3. 关键语言特性与易错点

外观模式在 JavaScript 里几乎“**不需要语法支持**”——**任何能把多次调用聚合成一次的东西，都能当外观用**，因此它更考验你的抽象能力。

[width(19,81)]

| 语言特性 / 写法  | 在这里的作用                                                             |
| :--------------- | :----------------------------------------------------------------------- |
| **普通函数**     | 最轻量的外观，一个函数把多步操作收进去（如 `initApp()`）。               |
| **闭包 (IIFE)**  | 隐藏内部子系统的引用，只暴露少数方法（jQuery 的 `$` 就是典型）。         |
| **ES Module**    | 一个模块的 `export` 列表天然就是该模块的“**外观**”，外部只认这几张面孔。 |
| **`class` 组合** | 在构造函数里 `new` 出各子系统，再由高层方法统一编排。                    |
| **单例导出**     | `export default new Api()`，全应用共用一个门面。                         |

**容易踩的坑**：

- **门面膨胀**：什么都往里塞，外观终会退化成“**上帝对象**”，反而更难维护。让它只做**编排**，别写业务细节。
- **把外观当适配器**：外观是**新增**一个统一入口（接口是新的），适配器是**转换**已有接口（让两个不兼容的接口能对接），两者目的不同。
- **忘了外观是“**可绕过**”的**：需要精细控制时依然可以直接调用子系统，别硬把它做成唯一通道。

## 4. 模式对比：相似模式的辨析

外观模式经常被拿来与适配器、中介者、命令模式对比：

[width(15,38,13,34)]

| 模式       | 核心区别                                                       | 侧重点         | 形象比喻                                   |
| ---------- | -------------------------------------------------------------- | -------------- | ------------------------------------------ |
| 外观模式   | 封装并简化。接口是新的，逻辑是现有的。                         | 易用性         | 全屋智能的“**离家模式**”按钮。             |
| 适配器模式 | 转换接口。目的是让原本不兼容的接口能一起工作。                 | 兼容性         | 电源转接头（三孔转两孔）。                 |
| 中介者模式 | 管理交互。解耦多个同事对象之间的多对多关系。                   | 多边通信       | 机场塔台，负责调度所有飞机。               |
| 命令模式   | 封装请求。将一个请求封装为一个对象（包含执行者、方法、参数）。 | 解耦与操作控制 | 餐馆的点菜单。记录了谁点、吃什么、谁来做。 |

## 5. 常见问题 (FAQ)

### 5.1 什么时候该用外观模式？

- 当你要为一个复杂的子系统提供一个简单入口时。
- 当客户端代码与多个子系统紧密耦合，导致难以维护时。
- 当你想要构建一个层次结构，让每一层都通过“**外观**”与外界通信时。

### 5.2 外观模式会限制我直接调用底层接口吗？

**不会。** 外观模式只是提供了一个“**快捷方式**”。如果某些高级用户需要更精细的控制，他们依然可以直接绕过外观类去调用底层的子系统。

### 5.3 外观模式和单例模式经常配合使用吗？

**是的。** 通常整个系统只需要一个外观实例（例如一个全局的 API 管理器），因此外观类往往被设计成单例。

### 5.4 它是“开闭原则”的拥护者吗？

**不完全是。** 增加新功能时，通常需要修改外观类。但在 JavaScript 中，外观模式更强调的是**封装带来的代码整洁度**和**心智负担的降低**。
