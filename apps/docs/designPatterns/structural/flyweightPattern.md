# 享元模式

## 1. 核心概念与价值

享元模式的定义是：**运用共享技术有效地支持大量细粒度的对象。**

它的核心思想是：**区分内部状态和外部状态**，将可以共享的内部状态提取出来，实现对象的复用。

它靠三个角色搭伙：**享元对象 (Flyweight)** 保存可共享的内部状态；**享元工厂 (Flyweight Factory)** 负责创建并缓存享元，保证同一类享元全局只留一份；**外部状态管理器** 持有随场景变化的参数，在调用时把它们注入享元。打个比方，只要几个“**空心模特**”轮流换衣服，就拍完了上万套服装。

[width(15,85)]

| 维度           | 描述                                                                                                                                                          |
| :------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **核心意图**   | 通过共享技术减少内存中对象的数量。                                                                                                                            |
| **关键角色**   | **享元对象**：只存内部状态、可被共享；**享元工厂**：用缓存（常见 `Map` 或对象）保证同键只创建一次；**外部状态管理器**：持有随场景变化的参数，调用时注入享元。 |
| **内部状态**   | 存储在享元对象内部、可以被共享的信息。它**独立于场景**，不会随环境改变（如：衣服的性别）。                                                                    |
| **外部状态**   | 取决于具体场景、无法共享的信息。它会随环境改变，通常由外部注入（如：穿衣服的人）。                                                                            |
| **主要优点**   | 极大减少内存占用，提升程序性能。                                                                                                                              |
| **主要缺点**   | 增加了系统的复杂度，需要花费时间去拆分内部和外部状态。                                                                                                        |
| **适用场景**   | 1. 程序里有成千上万个对象，内存吃紧；<br>2. 对象的大部分状态可以外置；<br>3. 这些状态能按少数几种类型归并（如性别、颜色、形状）。                             |
| **不适用场景** | 1. 对象本就很少，强行拆分只会让代码更复杂；<br>2. 内部状态寥寥、外部状态几乎一致，没有共享价值；<br>3. 对性能不敏感，代码可读性更重要。                       |

## 2. 模式演进：从“内存溢出”到“按需共享”

### 2.1 传统写法（反面教材：创建 10000 个对象）

如果要给 5000 男款和 5000 女款衣服拍照，按普通思路要请 10000 个模特，内存直接爆掉。

```js
class Model {
  constructor(sex, underwear) {
    this.sex = sex
    this.underwear = underwear
  }
  takePhoto() {
    console.log(`性: ${this.sex}, 穿: ${this.underwear} 拍照`)
  }
}

// 循环 10000 次，内存占用极大
for (let i = 1; i <= 5000; i++) {
  const maleModel = new Model('male', `男款第${i}套`)
  maleModel.takePhoto()
}
```

### 2.2 享元模式写法（解耦版：仅需 2 个对象）

我们只需要一个男模特和一个女模特，让他们轮流穿不同的衣服拍照即可。

```js
// 1. 享元对象：只保留内部状态（性别）
class Model {
  constructor(sex) {
    this.sex = sex
  }
  takePhoto(underwear) {
    // 外部状态通过参数传入
    console.log(`性别: ${this.sex}, 穿: ${underwear} 拍照`)
  }
}

// 2. 享元工厂：负责创建和管理对象，确保唯一性
const modelFactory = (function () {
  const cache = {} // 存储已创建的单例
  return {
    create: function (sex) {
      if (cache[sex]) return cache[sex]
      return (cache[sex] = new Model(sex))
    },
  }
})()

// 3. 外部状态管理器：控制 10000 次逻辑，但只用 2 个实例
for (let i = 1; i <= 5000; i++) {
  const maleModel = modelFactory.create('male')
  maleModel.takePhoto(`男款第${i}套`)
}
for (let i = 1; i <= 5000; i++) {
  const femaleModel = modelFactory.create('female')
  femaleModel.takePhoto(`女款第${i}套`)
}
```

## 3. 实战场景

[width(20,80)]

| 场景               | 享元模式的应用                                                                                                                                          |
| :----------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **DOM 性能优化**   | 如果列表有 10 万行，不直接生成 10 万个节点，而是只生成可见区域的几十个节点，滚动时复用节点并更新数据（**虚拟滚动**的基础）。                            |
| **游戏开发**       | 森林中有 10 万棵树。每棵树的形状（内部状态）可能只有 5 种，但位置和颜色（外部状态）不同。                                                               |
| **对象池**         | 在线程、数据库连接、甚至游戏中子弹的创建中，预先创建一组对象重复使用，而不是频繁创建和销毁。                                                            |
| **富文本编辑器**   | 文档里每个字符都是一个对象。把字号、颜色、加粗等样式抽成少量样式实例共享，正文只存“**字符 + 样式引用**”（Draft.js 的 `CharacterMetadata` 就是此思路）。 |
| **图标 / 字体**    | 用 `<svg><symbol>` 定义一次图形，页面各处用 `<use>` 引用，相同的路径数据不重复内联。                                                                    |
| **框架的节点复用** | React / Vue 靠 `key` 复用组件与 DOM 节点，数据（外部状态）变了只更新内容，条目结构保持不变。                                                            |
| **Node 连接池**    | 数据库连接、`Buffer.allocUnsafe` 都预先复用一组小对象，避免频繁创建与回收带来的开销。                                                                   |

## 4. 关键语言特性与易错点

享元模式在 JS 里没有专门的语法，它的“**共享**”通常由**闭包缓存**和 **`Map`** 来实现。

[width(23,77)]

| 语言特性 / API        | 在这里的作用                                                         |
| :-------------------- | :------------------------------------------------------------------- |
| **闭包 + IIFE**       | 把缓存藏在函数作用域里，外部只能通过工厂方法取对象，天然实现唯一性。 |
| **`Map` / `Set`**     | 以内部状态组合为 key 缓存享元对象，查找是 $O(1)$。                   |
| **`WeakMap`**         | key 是对象时用它缓存，对象被回收后缓存项自动释放，避免内存泄漏。     |
| **工厂函数**          | `create(state)` 先查缓存、没有才 `new`，是享元的入口。               |
| **对象池**            | 用 `Array.pop()` 取、`Array.push()` 还，复用对象而非反复创建销毁。   |
| **`Object.freeze()`** | 冻结共享的享元对象，防止内部状态被意外修改。                         |

**容易踩的坑**：

- **污染共享对象**：享元是全局共享的，一旦把外部状态写进它的属性，别的调用方就会“**串味**”。内部状态务必不可变。
- **省了内存、丢了性能**：拆分与注入外部状态有额外计算成本，对象数量不够大时得不偿失。
- **缓存 key 设计不当**：键太细（每次都是新键）等于没缓存，键太粗（不同类型撞一起）会取错对象。
- **`WeakMap` 的 key 必须是对象**：拿字符串当 key 会直接报错，字符串键请改用 `Map`。

## 5. 常见问题 (FAQ)

### 5.1 享元模式和单例模式有什么区别？

- **单例模式**：整个应用只有**一个**唯一的实例（如全局 Store）。
- **享元模式**：可以有**一组**不同的共享对象（如 Model 工厂里有一个‘**男**’和一个‘**女**’）。享元模式的目标是减少数量。

### 5.2 什么时候应该考虑使用享元模式？

- 一个程序使用了大量的对象（上千甚至更多）。
- 对象的大部分状态都可以变为外部状态。
- 如果不使用享元模式，内存开销将难以承受。

### 5.3 如何存储外部状态？

由于外部状态不再存储在对象内部，通常需要一个外部的管理器（Manager）或者一个哈希表来存储每个对象对应的外部信息。在 JavaScript 中，经常利用**闭包**或者 **Map/Set** 来实现。

### 5.4 享元模式会增加 CPU 负担吗？

**是的。** 享元模式是一种典型的“**空间换时间**”（或“**时间换空间**”）策略。你需要花费额外的计算时间来拆分、提取和注入外部状态。但相比于内存溢出（OOM）导致的页面卡死，这点 CPU 开销通常是值得的。
