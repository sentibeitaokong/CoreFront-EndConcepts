# 装饰器模式

## 1. 核心概念与价值

装饰器模式就像是给手机“**贴膜**”或“**加手机壳**”：手机的核心功能（打电话、上网）没变，但增加了额外的属性（防摔、好看）。

[width(13,87)]

| 维度         | 描述                                                                                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心定义** | 动态地给一个对象添加一些额外的职责。就增加功能来说，装饰器模式比生成子类更为灵活。                                                                                    |
| **主要优点** | 1. 灵活性高：可以在运行时选择如何包装对象；<br>2. 职责分离：核心业务逻辑和辅助逻辑（如日志、校验）彻底解耦；<br>3. 组合性强：可以通过多个装饰器嵌套，实现功能的累加。 |
| **主要缺点** | 1. 产生大量的小类/小函数，增加系统复杂度；<br>2. 多层嵌套后，如果调试不当，排查问题的路径会变长。                                                                     |

**谁在扮演什么角色、什么时候该用**

[width(15,85)]

| 维度           | 描述                                                                                                                                                                                           |
| :------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **关键角色**   | **抽象组件 (Component)**：约定被装饰对象的接口；**具体组件 (ConcreteComponent)**：原始对象（一杯咖啡）；**装饰器 (Decorator)**：持有组件引用且接口一致；**具体装饰器**：加奶、加糖等具体增强。 |
| **适合使用**   | 1. 想在不修改原类的前提下，动态添加或撤销职责；<br>2. 多个可选功能需要自由组合（咖啡加奶又加糖）；<br>3. 用继承会导致子类爆炸（加奶咖啡、加糖加奶咖啡……）。                                    |
| **不适合使用** | 1. 增强逻辑固定、只有一两种且不会变，直接写死更简单；<br>2. 依赖对象身份唯一（`===`），或靠 `instanceof` 判断类型——装饰后是新的包装对象，这两种判断都会失效。                                  |

## 2. JavaScript 实现方案

在 JS 中，装饰器有两种常见的实现方式：**传统的包装函数（高阶函数）** 和 **现代的 `@` 语法（Stage 3 提案）**。

### 2.1 传统实现：包装函数 (推荐用于普通逻辑)

这种方式本质上是利用了闭包和高阶函数。

```js
// 1. 原始对象：普通咖啡
class Coffee {
  cost() {
    return 10
  }
}

// 2. 装饰器：加奶
function withMilk(coffee) {
  const originalCost = coffee.cost()
  coffee.cost = function () {
    return originalCost + 5 // 增加 5 元
  }
  return coffee
}

// 3. 装饰器：加糖
function withSugar(coffee) {
  const originalCost = coffee.cost()
  coffee.cost = function () {
    return originalCost + 2 // 增加 2 元
  }
  return coffee
}

// 使用：自由组合功能
let myCoffee = new Coffee()
myCoffee = withMilk(myCoffee)
myCoffee = withSugar(myCoffee)
console.log(myCoffee.cost()) // 输出: 17
```

### 2.2 现代实现：`@Decorator` 语法 (推荐用于类和方法)

_注：目前该语法处于 Stage 3 提案阶段，在生产环境中通常需要 Babel 或 TypeScript 支持。_

```js
// 定义一个装饰器：记录日志
function log(target, name, descriptor) {
  const original = descriptor.value
  descriptor.value = function (...args) {
    console.log(`正在执行方法: ${name}，参数: ${args}`)
    return original.apply(this, args)
  }
  return descriptor
}

class Calculator {
  @log
  add(a, b) {
    return a + b
  }
}

const calc = new Calculator()
calc.add(2, 3) // 输出: 正在执行方法: add，参数: 2, 3
```

## 3. 实战场景

装饰器模式在前端工程化中几乎随处可见：

[width(20,80)]

| 场景               | 说明                                                         |
| ------------------ | ------------------------------------------------------------ |
| **权限控制**       | 在进入页面组件前，用装饰器检查当前用户是否有权访问。         |
| **埋点与统计**     | 在点击按钮或进入页面时，自动发送统计数据，而不侵入业务代码。 |
| **数据校验**       | 为表单提交方法添加装饰器，先校验数据，校验不通过则拦截执行。 |
| **高阶组件 (HOC)** | React 中的 HOC 本质上就是组件层面的装饰器模式。              |

**高频场景：遇到这类需求，直接对号入座**

[width(23,35,42)]

| 场景                | 应该用哪个                                        | 关键手段                         |
| :------------------ | :------------------------------------------------ | :------------------------------- |
| 日志 / 耗时统计     | 方法装饰器 `@log`                                 | 包裹原方法，前后打印入参与耗时   |
| 结果缓存            | `@memoize`                                        | 闭包里的 `Map` 按参数做缓存 key  |
| 防抖 / 节流         | `@debounce` / `@throttle`                         | 装饰器返回被包装的函数           |
| 权限 / 登录校验     | 路由或方法装饰器                                  | 校验不通过直接抛错或重定向       |
| 参数校验与转换      | NestJS `@Body` / class-validator                  | 进入方法前校验并转换成 DTO       |
| 依赖注入 / 路由注册 | NestJS `@Controller` `@Get`、Angular `@Component` | 元数据装饰器，运行时读取反射信息 |
| 状态响应式          | MobX `@observable` / `@computed` / `@action`      | 字段变成可观察，方法变成动作     |
| React 组件增强      | HOC / `connect` / `withRouter`                    | 返回新组件并透传 `props`         |
| 失败重试            | `@retry`                                          | 捕获异常后按策略重试             |

## 4. 关键语言特性与易错点

装饰器的两种写法都依赖下面这些 JS 特性：

[width(30,70)]

| 特性 / API                       | 在装饰器里的作用                                                                                     |
| :------------------------------- | :--------------------------------------------------------------------------------------------------- |
| **`Object.defineProperty`**      | 传统描述符装饰器读写 `descriptor.value`、`writable`、`enumerable`、`configurable`。                  |
| **`descriptor.value` + `apply`** | 先 `const original = descriptor.value` 存原方法，再 `original.apply(this, args)` 调用，保住 `this`。 |
| **闭包**                         | 包装函数靠闭包记住原方法与缓存，是高阶函数式装饰器的基础。                                           |
| **高阶函数 / 高阶组件**          | `withMilk(coffee)`、`connect(mapState)(Comp)` 都是“**接收一个东西、返回增强版**”。                   |
| **元数据反射**                   | NestJS、Angular 依赖 `reflect-metadata` 读取装饰器写入的信息。                                       |

几个高频易错点：

- **执行顺序**：多个装饰器“**自上而下进入、自下而上返回**”，顺序写反会得到意料之外的结果（见 FAQ）。
- **`this` 丢失**：包装时若用了箭头函数或直接赋值，可能拿不到实例 `this`，务必 `original.apply(this, args)`。
- **污染传入对象**：`coffee.cost = …` 改的是传进来的那个对象；若它被多处共享，副作用会外溢，必要时先克隆。
- **描述符漏配**：用 `defineProperty` 时忘了 `enumerable` / `configurable`，方法可能变得不可枚举，影响遍历与序列化。
- **编译依赖**：`@` 语法必须经 Babel 或 TS 编译，TS 还需开启 `experimentalDecorators`。

## 5. 模式对比

装饰器模式常与代理模式混淆，下表为您清晰辨析：

[width(15,54,31)]

| 模式           | 核心区别                                             | 形象比喻                          |
| -------------- | ---------------------------------------------------- | --------------------------------- |
| **装饰器模式** | **增强功能**。侧重于给原对象增加额外的职责。         | 手机加了个挂绳。                  |
| **代理模式**   | **控制访问**。侧重于在中间层做过滤、拦截或延迟执行。 | 手机的前台秘书代接。              |
| **适配器模式** | **接口转换**。解决接口不兼容问题。                   | 手机的转接头（Type-C 转 3.5mm）。 |

## 6. 常见问题 (FAQ)

### 6.1 `@decorator` 语法现在能在浏览器里直接跑吗？

**不能直接跑**。虽然处于 Stage 3 提案，但主流浏览器尚未完全原生支持。你需要使用 **Babel**（插件 `@babel/plugin-proposal-decorators`）或 **TypeScript** 将其编译为普通的 JS 语法。

### 6.2 装饰器模式和类继承相比，什么时候该选谁？

如果你的功能是**横向扩展**的（比如多个不相关的类都需要“**日志**”功能），选装饰器模式。如果你的功能是**纵向演化**的（比如“**鸟**” -> “**麻雀**”），且有严格的父子关系，选继承。**“多用组合，少用继承”**是现代设计的核心理念。

### 6.3 一个方法可以被多个装饰器装饰吗？

**可以**。执行顺序通常是“**自上而下**”进入，“**自下而上**”执行完返回。就像剥洋葱一样，最上面的装饰器是最外层。

### 6.4 装饰器可以改变方法的参数吗？

**可以**。通过修改 `descriptor.value` 里的 `apply(this, modifiedArgs)`，你可以拦截并修改传入原方法的参数，这在参数预处理或标准化场景中非常有用。
