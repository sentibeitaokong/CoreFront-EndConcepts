# 适配器模式

## 1. 核心概念与价值

适配器模式在不改变原有代码的基础上，通过增加一个“**中间层**”来抹平接口之间的差异。

### 1.1 **角色**

[width(23,28,49)]

| 角色                   | 职责                     | 在本模式里对应谁           |
| :--------------------- | :----------------------- | :------------------------- |
| **目标接口 (Target)**  | 客户端期望调用的接口     | 示例里的 `render(mapData)` |
| **被适配者 (Adaptee)** | 已有但接口不兼容的对象   | 高德地图 `GaodeMap.show()` |
| **适配器 (Adapter)**   | 把 Adaptee 包装成 Target | `GaodeMapAdapter`          |
| **客户端 (Client)**    | 只依赖 Target 编程       | `renderMap(map)` 的调用方  |

### 1.2 **核心意图与优缺点**

[width(13,87)]

| 维度         | 描述                                                                                                                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心意图** | 转换接口。解决“**这个东西很好，但我没法直接用**”的问题。                                                                                                                                      |
| **主要优点** | 1. **复用性强**：让旧的组件或第三方库能在新系统中继续发光发热；<br>2. **解耦**：客户端代码只关注目标接口，不关心底层实现的变化；<br>3. **灵活性**：可以在适配器中加入逻辑，对数据进行预处理。 |
| **主要缺点** | 如果系统中充斥着大量的适配器，会增加代码的阅读成本，有时直接重构原始代码反而更清晰。                                                                                                          |

### 1.3 **适用与不适用**

[width(15,85)]

| 维度           | 说明                                                                                                                                                            |
| :------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **适合使用**   | 1. 要复用第三方库、SDK 或遗留代码，却无权修改其源码；<br>2. 新旧接口需要并存、平滑过渡；<br>3. 同一功能有多套实现（多地图、多支付渠道），想给上层一个统一入口。 |
| **不适合使用** | 1. 项目还在早期，直接统一接口比套一层更干净；<br>2. 适配器会长期存在且越堆越多，说明底层接口设计本身有问题，应优先治理源头，而不是层层包装掩盖问题。            |

## 2. 经典实战场景️

### 2.1 第三方 SDK 切换（地图组件示例）

假设你的项目原本使用百度地图，现在要切换到高德地图，但它们的渲染方法名完全不同。

[width(24,76)]

| 角色                  | 接口 / 方法名                |
| --------------------- | ---------------------------- |
| **旧接口 (BaiduMap)** | `render(mapData)`            |
| **新接口 (GaodeMap)** | `show(data)`                 |
| **目标需求**          | 统一使用 `render` 方法调用。 |

```js
// 1. 旧的组件实现
class BaiduMap {
  render(mapData) {
    console.log('开始渲染百度地图...', mapData)
  }
}

// 2. 新的第三方组件（接口不兼容）
class GaodeMap {
  show(data) {
    console.log('开始渲染高德地图...', data)
  }
}

// 3. 编写适配器
class GaodeMapAdapter {
  constructor() {
    this.gaodeMap = new GaodeMap()
  }
  // 抹平差异：让 show 变成 render
  render(mapData) {
    this.gaodeMap.show(mapData)
  }
}

// 4. 统一调用
const renderMap = map => map.render({ city: 'Beijing' })

renderMap(new BaiduMap())
renderMap(new GaodeMapAdapter()) // 成功适配！
```

### 2.2 后端数据格式适配

前端 UI 组件通常需要特定的数据格式，而后端返回的数据结构可能千奇百怪。

```js
// 后端返回的原始数据
const oldData = [
  { day: 'Monday', val: 100 },
  { day: 'Tuesday', val: 200 },
]

// UI组件需要的格式: { "Mon": 100, "Tue": 200 }
function dataAdapter(data) {
  const map = { Monday: 'Mon', Tuesday: 'Tue' }
  return data.reduce((acc, item) => {
    acc[map[item.day]] = item.val
    return acc
  }, {})
}

const uiData = dataAdapter(oldData)
console.log(uiData) // { Mon: 100, Tue: 200 }
```

**高频场景：遇到这类需求，直接对号入座**

[width(30,15,55)]

| 场景                         | 应该用哪个  | 关键手段                                                    |
| :--------------------------- | :---------- | :---------------------------------------------------------- |
| 统一各端请求                 | 请求适配器  | 小程序 / H5 / Node 各实现同一个 `request(options)` 接口     |
| 旧回调式 API 转 Promise      | `promisify` | `new Promise` 包一层，把 `callback(err, data)` 转成 Promise |
| 多地图 / 多支付 / 多登录渠道 | 渠道适配器  | 抹平 `render` / `pay` / `login` 等方法名差异                |
| 后端字段与 UI 字段不一致     | 数据适配器  | `reduce` 把 `{ day, val }` 重组成 `{ Mon: 100 }`            |
| 老旧浏览器缺失原生 API       | polyfill    | 用已有 API 组合出 `Element.closest` 之类的替代实现          |
| 事件对象归一                 | 事件适配器  | 抹平 `e.target` / `e.srcElement`、`e.keyCode` / `e.which`   |
| WebSocket / SSE 消息统一     | 协议适配器  | 不同协议的消息归一成同一个事件回调                          |

其中“**回调转 Promise**”在 JS 里极其常见，一行工厂函数就能搞定：

```js
// 把“回调式”旧接口适配成 Promise 接口
function promisify(fn) {
  return (...args) =>
    new Promise((resolve, reject) => {
      fn(...args, (err, data) => (err ? reject(err) : resolve(data)))
    })
}
```

## 3. 关键语言特性与易错点

适配器本身不需要新语法，但下面这些特性会被反复用到：

[width(39,61)]

| 特性 / API                             | 在适配器里的作用                                                      |
| :------------------------------------- | :-------------------------------------------------------------------- |
| **`Proxy`**                            | 最通用的“**动态适配器**”，拦截 `get` 即可按需转发，不必手写每个方法。 |
| **展开运算符 `...` / `Object.assign`** | 合并默认配置与用户配置，做参数归一。                                  |
| **解构 + 默认参数**                    | 在适配器入口统一参数形状，避免下游拿到 `undefined`。                  |
| **`Promise` / `new Promise`**          | 把回调式、事件式旧接口适配成 `async/await` 友好的接口。               |
| **`util.promisify`（Node）**           | 内置的适配器工厂，一键把 `(…args, cb)` 回调 API 变 Promise。          |

几个高频易错点：

- **忘记转发返回值**：适配器方法里调用了被适配对象，却忘了 `return`，调用方只会拿到 `undefined`。
- **只包了一半接口**：适配器要覆盖客户端会用到的全部方法，否则“**半残**”，直到真正调用时才报错。
- **副作用污染原数据**：数据适配时直接改原对象（浅拷贝陷阱），会波及其他使用者。
- **`this` 丢失**：`const { show } = gaodeMap; show()` 会丢 `this`，应先保留对象引用再调用。

## 4. 模式对比

适配器模式经常被拿来与代理、装饰器对比。

[width(15,58,27)]

| 模式           | 核心区别                                                   | 形象比喻           |
| -------------- | ---------------------------------------------------------- | ------------------ |
| **适配器模式** | **转换接口**。重点在于解决接口不兼容，让东西能动起来。     | **电源转接头**。   |
| **代理模式**   | **控制访问**。接口不变，重点在于控制谁能用、怎么用。       | **明星经纪人**。   |
| **装饰器模式** | **增强功能**。接口不变，重点在于给原有对象加“** Buff **”。 | **手机贴膜加壳**。 |

## 5. 常见问题 (FAQ)

### 5.1 什么时候该用适配器，什么时候该直接重构代码？

[width(15,85)]

| 选择           | 适用场景                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| **使用适配器** | 1. 原始代码极其复杂，改动风险极大；<br>2. 原始代码是第三方库或 SDK，你没有修改权限；<br>3. 只是临时过渡方案。 |
| **直接重构**   | 1. 项目处于早期阶段，修改成本低；<br>2. 接口设计极其不合理，适配器也救不了。                                  |

### 5.2 适配器模式会影响性能吗？

在大多数 JS 应用场景中，多一层函数调用或对象封装带来的性能损耗是**微秒级**的，完全可以忽略不计。相比之下，它带来的代码可维护性提升要重要得多。

### 5.3 “包装模式” (Wrapper) 是指适配器吗？

是的。在许多文献中，适配器模式也被称为 **Wrapper 模式**，因为它本质上就是给旧接口包了一层新外壳。

### 5.4 适配器可以适配多个对象吗？

可以。这被称为**组合适配器**。你可以创建一个适配器，在内部调用多个不同的类，将它们聚合成一个统一的、更好用的接口暴露给外界。
