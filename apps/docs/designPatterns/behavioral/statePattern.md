# 状态模式

## 1. 核心概念与价值

状态模式的定义是：**允许一个对象在其内部状态改变时改变它的行为。对象看起来似乎修改了它的类。**

它的核心思想是：**将每一种状态封装成一个独立的类/对象**，并将请求委托给当前状态对象。

[width(13,87)]

| 维度         | 描述                                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心目的** | 消除庞大的条件分支语句，将状态逻辑分布到各个状态类中。                                                                                                        |
| **主要优点** | 1. 结构清晰，避免了状态判断的逻辑堆积；<br>2. 封装性好，将“**状态切换**”和“**状态行为**”结合在一起；<br>3. 扩展性强，新增状态只需增加一个新类，符合开闭原则。 |
| **主要缺点** | 1. 增加系统类/对象的数量；<br>2. 逻辑分散，如果状态极多且跳转复杂，可能导致“**迷路**”。                                                                       |

**三个核心角色**

[width(29,71)]

| 角色                         | 职责                                                        |
| :--------------------------- | :---------------------------------------------------------- |
| **环境类 (Context)**         | 持有当前状态对象的引用，把请求委托给它，并提供 `setState`。 |
| **抽象状态 (State)**         | 约定状态行为的统一接口（如 `handle`）。                     |
| **具体状态 (ConcreteState)** | 实现当前状态下的行为，并决定是否以及如何切换到下一个状态。  |

**适用与不适用**

[width(44,56)]

| 适用                                     | 不适用                                 |
| :--------------------------------------- | :------------------------------------- |
| 对象的行为随内部状态改变而剧烈变化       | 状态只有 2 个（开 / 关，用布尔值即可） |
| 状态多（≥3）且每个状态下逻辑复杂         | 状态之间没有任何流转，只是静态枚举     |
| 需要消除庞大的 `if-else` / `switch` 分支 | 状态切换全靠外部驱动、内部无自主逻辑   |

## 2. 模式演进：从“面条代码”到“状态机”

让我们以一个简单的 **“交通灯”** 系统为例。

### 2.1 传统写法（难以维护）

这种写法在增加新状态（如“**黄灯闪烁**”）时，需要改动整个函数逻辑。

```js
class TrafficLight {
  constructor() {
    this.state = 'red'
  }

  change() {
    if (this.state === 'red') {
      console.log('红灯停 -> 变绿灯')
      this.state = 'green'
    } else if (this.state === 'green') {
      console.log('绿灯行 -> 变黄灯')
      this.state = 'yellow'
    } else if (this.state === 'yellow') {
      console.log('黄灯等 -> 变红灯')
      this.state = 'red'
    }
  }
}
```

### 2.2 状态模式写法（解耦版）

我们将行为委托给具体的状态对象。

```js
// 1. 定义状态对象集合
const States = {
  red: {
    handle(context) {
      console.log('🔴 红灯停 -> 下一站：绿灯')
      context.setState(States.green) // 状态自动流转
    },
  },
  green: {
    handle(context) {
      console.log('🟢 绿灯行 -> 下一站：黄灯')
      context.setState(States.yellow)
    },
  },
  yellow: {
    handle(context) {
      console.log('🟡 黄灯等 -> 下一站：红灯')
      context.setState(States.red)
    },
  },
}

// 2. 环境类 (Context)
class TrafficLight {
  constructor() {
    this.currentState = States.red // 初始状态
  }
  setState(newState) {
    this.currentState = newState
  }
  request() {
    this.currentState.handle(this)
  }
}

// 使用
const light = new TrafficLight()
light.request() // 🔴 红灯停...
light.request() // 🟢 绿灯行...
```

## 3. 实战场景：工作流与复杂 UI

状态模式在以下场景中几乎是“**标准答案**”：

1.  **文件审批流**：`草稿 -> 待审批 -> 已发布 -> 已下线`。
2.  **网络游戏状态**：`加载中 -> 菜单页 -> 战斗中 -> 结算中`。
3.  **复杂组件 UI**：例如一个上传组件，有 `等待上传`、`上传中`、`暂停`、`成功`、`失败` 状态，不同状态下按钮的文字和功能完全不同。

**高频场景：遇到这类需求，直接对号入座**

[width(15,47,38)]

| 场景       | 落地示例                                   | 关键点                       |
| :--------- | :----------------------------------------- | :--------------------------- |
| 单据审批流 | 草稿 → 待审批 → 已发布 → 已下线            | 每个状态决定能执行哪些操作   |
| 播放器     | 播放中 / 暂停 / 缓冲 / 结束                | 同一按钮在不同状态下含义不同 |
| 上传组件   | 等待 / 上传中 / 暂停 / 成功 / 失败         | 状态映射到按钮文案与可点击性 |
| 订单支付   | 待付款 → 已付款 → 已发货 → 已完成 / 已取消 | 状态机约束合法迁移           |
| 游戏角色   | 待机 / 移动 / 攻击 / 受伤 / 死亡           | 状态间有明确优先级与打断规则 |
| 有限状态机 | 复杂流转交给 XState                        | 用状态图代替手写嵌套判断     |

## 4. 关键语言特性与易错点

- **用对象字面量或 `Map` 组织状态**：JS 里状态通常是普通对象，键为状态名；键名建议集中成常量或 `Symbol`，避免字符串魔法值写错却难以发现。
- **`Context` 要把自己传给状态**：状态方法需要回调 `context.setState(...)`，所以习惯写成 `state.handle(this)`，注意 `this` 的指向——把方法从对象里取出单独调用会丢失上下文。
- **共享状态对象要冻结**：若所有实例共用同一份状态对象，可用 `Object.freeze` 防止被意外篡改；若每个状态需要私有数据，则应在实例化时为每个状态创建独立实例。
- **给非法迁移加保护**：状态模式本身不校验迁移合法性，配合守卫判断或状态机（FSM），才能拒绝“**从待付款直接跳到已完成**”这类操作。
- **面试常问**：状态模式与策略模式结构几乎一样，区别在“**意图**”与“**是否自主流转**”，见 5.1。

## 5. 常见问题 (FAQ)

### 5.1 状态模式和策略模式（Strategy Pattern）有什么区别？

这是最经典的问题。它们结构非常相似，但**意图**完全不同：

- **策略模式**：不同的算法之间是**平等、独立**的。由**外部调用者**决定用哪一个。它们通常不互相知道对方的存在。
- **状态模式**：状态之间是**有联系、有流转**的。状态的切换通常是由**状态内部逻辑**自动触发的。目的是表现对象在不同生命周期的不同行为。

### 5.2 状态模式会增加很多对象，值得吗？

如果你的状态只有 2 个（如 开/关），用布尔值即可。但如果状态超过 3 个，且每个状态下的操作逻辑很重，那么增加对象的成本远低于维护“**面条代码**”的成本。

### 5.3 如何处理状态转换非常复杂的情况？

如果状态转换变成了一个巨大的迷宫，手动写状态模式可能会出错。此时推荐使用 **有限状态机 (FSM)** 库。

- 在 JavaScript 社区，**[XState](https://xstate.js.org/)** 是目前的行业标准，它基于状态图理论，能处理极复杂的逻辑。

### 5.4 状态对象需要存储在 Context 内部还是外部？

- 如果状态是**无状态的**（即所有实例共用逻辑），可以像我上文示例中那样放在外部常量中。
- 如果每个状态需要存储不同的私有数据，则应该在 `Context` 实例化时为每个状态创建独立实例。
