# 模块模式

## 1. 核心概念

模块模式的核心意图是：**将逻辑相关的代码封装在一个独立单元中，隐藏内部状态和实现细节，仅向外部暴露必要的接口。**

[width(15,85)]

| 维度           | 描述                                                                                                                                          |
| :------------- | :-------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心机制**   | 利用**闭包**来创建私有作用域。                                                                                                                |
| **关键角色**   | 私有作用域（IIFE / 模块顶层，藏住内部状态）、公共接口（`return` 的对象或 `export` 的成员）。                                                  |
| **主要优点**   | 1. **封装性**：保护内部数据不被外部随意修改；<br>2. **命名空间管理**：减少全局变量的使用；<br>3. **可维护性**：模块间解耦，方便独立开发测试。 |
| **主要缺点**   | 1. 无法为私有成员编写单元测试；<br>2. 扩展私有成员比较困难；<br>3. 可能会造成内存占用（因为闭包）。                                           |
| **适用场景**   | 1. 需要隐藏实现细节、只暴露稳定接口；<br>2. 避免污染全局命名空间；<br>3. 封装带状态的单例服务（配置、请求实例、埋点）。                       |
| **不适用场景** | 1. 只是一次性、无状态的纯函数（直接 `export` 即可）；<br>2. 过度拆分会带来“**模块碎片化**”，反而增加维护成本。                                |

## 2. 模式实现：从传统到现代

### 2.1 经典模块模式 (基于 IIFE 和闭包)

这是最经典的形式，即使在今天的一些老旧代码库或插件开发中依然可见。

```js
const CounterModule = (function () {
  // 1. 私有变量
  let count = 0

  // 2. 私有方法
  function log(msg) {
    console.log(`[Counter]: ${msg}`)
  }

  // 3. 返回公共接口 (暴露给外界)
  return {
    increment: function () {
      count++
      log(`增加后值为 ${count}`)
    },
    getCount: function () {
      return count
    },
  }
})()

CounterModule.increment() // [Counter]: 增加后值为 1
console.log(CounterModule.count) // undefined (无法访问私有变量)
```

### 2.2 现代模块化 (ES Modules)

在 ES6 之后，JavaScript 终于有了官方原生的模块系统。这已经成为了目前工程化开发的**行业标准**。

```js
// math.js
let privateValue = 10 // 默认就是模块私有的

export function add(a, b) {
  return a + b
}

export const version = '1.0.0'

// main.js
import { add, version } from './math.js'
```

### 2.3 模块化背后的关键语言点

- **闭包**：模块私有状态能存活，靠的是内部函数持续引用外层作用域的变量；这也是经典模块模式与内存占用的根源。
- **IIFE**：`(function(){ ... })()` 立即执行，制造出函数作用域，是最早期的“**模块容器**”。
- **块级作用域**：`let` / `const` 只在所在块内可见，是 ESM 内部默认私有、只暴露 `export` 成员的基础。
- **静态分析**：ESM 的 `import` / `export` 在编译期就能确定依赖图，因此支持 **Tree-shaking**；CommonJS 的 `require` 是运行时的，难以摇树。
- **动态导入**：`import('./x.js')` 返回 Promise，可做按需加载 / 路由懒加载，是代码分割（code splitting）的入口。
- **易错点**：`<script>` 上漏写 `type="module"` 会让 `import` 语句直接报错；循环依赖在 ESM 下会得到“**暂时未初始化**”的绑定，可能拿到 `undefined`。

## 3. 模块模式的变体

### 3.1 揭示模块模式 (Revealing Module Pattern)

这种变体让公共接口的定义更加清晰，它在内部先定义好所有函数，最后在 return 对象中只写引用。

```js
const myModule = (function () {
  let name = 'Alice'
  function getName() {
    return name
  }
  function setName(val) {
    name = val
  }

  // 这里的映射关系一目了然
  return {
    readName: getName,
    updateName: setName,
  }
})()
```

## 4. 典型应用场景

[width(20,80)]

| 场景                    | 说明                                                                                    |
| :---------------------- | :-------------------------------------------------------------------------------------- |
| **第三方库 / 插件封装** | jQuery 插件、各类 SDK 多用 IIFE 藏住内部状态，只暴露一个全局对象（如 `window.mySDK`）。 |
| **单例服务**            | axios 实例、埋点实例、配置读取器：整个应用共享一份实例和内部状态。                      |
| **工具库**              | Lodash 等把大量工具函数按模块组织，供按需 `import`，避免把未用到的代码打进产物。        |
| **配置与常量管理**      | 集中管理环境变量、常量表，对外只暴露读取接口，防止被随意改写。                          |
| **旧项目命名空间**      | 老代码用 `MyApp.utils`、`MyApp.api` 挂到统一命名空间下，减少全局变量冲突。              |

落地时的关键点与易错点：

- **挂载方式**：经典模块模式常显式挂到全局（`window.X`）；ESM 则由构建工具打包，无需手动挂载。
- **接口越窄越好**：一个模块别一股脑导出几十个成员，接口越窄耦合越低，Tree-shaking 也越有效。
- **易错点**：模块顶层直接执行副作用（发请求、改全局）会让导入方“**被动触发**”，难以测试，应把副作用封装进函数。

## 5. 常见问题 (FAQ)

### 5.1 模块模式和单例模式有什么区别？

模块模式通常**就是**以单例的形式存在的（尤其是通过 IIFE 实现的）。它们的目标是一致的：创建一个唯一的、封装好的全局访问点。但在现代 ES 模块中，你可以导出一个类，从而允许创建多个实例。

### 5.2 模块模式会导致内存泄漏吗？

**有可能。** 由于模块内部的私有变量是通过闭包被持有的，只要该模块对象没有被销毁，这些变量就会一直占用内存。

### 5.3 如何解决“循环依赖”问题？

循环依赖（A 依赖 B，B 依赖 A）是模块化开发中的噩梦。

- 重构代码，将共有逻辑提取到第三个模块 C 中；
- 使用异步加载（动态 import）；
- 在函数内部进行 `require`（仅限 CommonJS）。

### 5.4 ES Modules (ESM) 和 CommonJS (CJS) 有什么区别？

- **CommonJS**：Node.js 默认标准。**运行时加载**，同步导出，导出的是值的**拷贝**。
- **ES Modules**：浏览器和现代前端标准。**编译时加载**（静态分析），导出的是值的**引用**（符号绑定）。

### 5.5 为什么现代开发不再手动写 IIFE 模块了？

因为有了 **Webpack、Vite** 等构建工具。你可以直接写最直观的 ES 模块语法，工具会自动帮你完成封装、混淆、压缩和跨浏览器兼容处理。
