# 设计模式核心原则

## 1. SOLID 五大原则

### 1.1 单一职责原则 (Single Responsibility Principle)

- **核心思想**：一个类或一个函数应该**只做一件事**。如果一个对象承担的职责过多，就等于把这些职责耦合在了一起。
- **JS 实战**：不要写一个既负责获取数据、又负责格式化数据、还负责渲染 DOM 的大函数。应该将其拆分为三个独立的小函数。
- **解决什么问题**：当一个类 / 函数同时承担多个“**变化原因**”时，改A需求会意外弄坏B逻辑，牵一发而动全身。
- **反例**：`fetchAndRender()` 同时负责请求、格式化、操作 DOM，任何一环要改都得动同一个函数，改动风险成倍放大。

### 1.2 开闭原则 (Open-Closed Principle)

- **核心思想**：**对扩展开放，对修改关闭**。
- **解释**：当需求变化时，你应该通过增加新代码来扩展功能，而不是去修改已经写好的、经过测试的旧代码。
- **JS 实战**：这是**策略模式**和**装饰器模式**的灵魂。利用配置文件或插件机制来增加功能，而不是在大函数的 `if-else` 里硬写。
- **解决什么问题**：频繁修改已经过测试、已经稳定的旧代码，容易引入回归 Bug，破坏原有功能。
- **反例**：每加一种支付方式就往 `pay(type)` 里再塞一个 `if-else`，函数越改越长、越改越不敢动。

### 1.3 里氏替换原则 (Liskov Substitution Principle)

- **核心思想**：子类必须能够完全替换掉它们的父类，而不会导致程序出错。
- **解释**：子类不应该覆盖父类中已经实现的非抽象方法，否则会破坏继承的意义。
- **JS 实战**：如果你写了一个 `Bird` 类有 `fly` 方法，那么 `Ostrich`（鸵鸟）类就不应该继承 `Bird`，或者你应该把 `fly` 拆分出来。
- **解决什么问题**：当子类的行为与父类不兼容时，所有按“**父类**”写的代码一旦替换成子类就会出错。
- **反例**：`Square extends Rectangle`，设置宽高会互相影响，把正方形当矩形用时面积计算结果直接错掉。

### 1.4 接口隔离原则 (Interface Segregation Principle)

- **核心思想**：不应该强迫客户依赖于它们不使用的接口。
- **解释**：一个接口（在 JS 中通常指对象的方法集合）不应该过于臃肿。
- **JS 实战**：如果一个组件只需要“**读取**”权限，就不要传给它一个包含“**读取、写入、删除**”所有方法的巨大权限对象。
- **解决什么问题**：臃肿的“**全能接口**”会强迫实现者去实现一堆根本用不到的方法，任何改动牵连面都很广。
- **反例**：一个权限对象同时塞进读、写、删方法，只读的展示组件也被迫依赖这一整坨能力。

### 1.5 依赖倒置原则 (Dependency Inversion Principle)

- **核心思想**：面向接口编程，而不是面向实现编程。
- **解释**：高层模块不应该依赖于低层模块，两者都应该依赖于抽象。
- **JS 实战**：你的业务组件不应该直接依赖具体的 `Axios` 实例，而应该依赖一个通用的 `request` 接口。这样当你把底层从 `Axios` 换成 `Fetch` 时，业务逻辑不需要改动。
- **解决什么问题**：高层业务直接依赖底层实现，一旦底层更换，高层代码就要被大范围改写。
- **反例**：组件里到处 `import axios` 直接发起请求，等要换成 `fetch` 时，只能全项目逐个替换。

## 2. 补充重要原则

### 2.1 DRY 原则 (Don't Repeat Yourself)

- **核心思想**：**不要写重复的代码**。
- **做法**：通过抽象和封装，将共有的逻辑提取出来。如果同一段代码你写了三次，就该考虑重构它了。
- **解决什么问题**：同一逻辑散落在多处，改一处漏改另一处，就会产生前后不一致的 Bug。
- **反例**：三个页面各自复制了一份相同的日期格式化代码，调整格式时只改了两处，剩下那处就成了隐形炸弹。

### 2.2 KISS 原则 (Keep It Simple, Stupid)

- **核心思想**：**保持简单，不要炫技**。
- **做法**：能用简单的代码解决问题，就不要强行套用复杂的设计模式。简单意味着好维护、易调试。
- **解决什么问题**：过度设计会让简单需求变得难懂、难维护，还会放大出错的面积。
- **反例**：为了在页面上显示一句 “**Hello**”，硬套抽象工厂加策略模式，几十行能搞定的事写成几百行。

### 2.3 最少知识原则 (Law of Demeter / Least Knowledge)

- **核心思想**：一个对象应该对其他对象有尽可能少的了解。
- **JS 实战**：这是**中介者模式**的核心。对象 A 想改对象 C，不应该通过 `A -> B -> C` 这种长链条，而应该通过一个中介者来管理。
- **解决什么问题**：对象之间互相了解太深、层层穿透调用，会织成一张网状依赖，任何一处变动都会向外扩散。
- **反例**：`a.b.c.d.do()` 这种一路点下去才能干活的写法，中间任何一层结构一变，整条调用链立刻断掉。

**原则与模式的关系总结**

[width(17,83)]

| 设计原则         | 对应的典型设计模式               |
| :--------------- | :------------------------------- |
| **单一职责 (S)** | 代理模式、单例模式、装饰器模式   |
| **开闭原则 (O)** | 策略模式、观察者模式、适配器模式 |
| **依赖倒置 (D)** | 工厂模式、模板方法模式           |
| **最少知识**     | 中介者模式、外观模式             |

## 3. 典型应用场景

**高频场景：遇到这类需求，直接对号入座**

[width(33,18,49)]

| 痛点 / 场景                   | 该用哪条原则 | 关键手段                                        |
| :---------------------------- | :----------- | :---------------------------------------------- |
| 一段逻辑被复制到好几处        | DRY          | 抽成函数 / 常量 / 配置，一处修改处处生效        |
| `if-else` / `switch` 越写越长 | 开闭原则     | 用策略表、插件机制代替硬编码分支                |
| 组件直接依赖具体的请求库      | 依赖倒置     | 依赖一个 `request` 抽象接口，底层实现可随时替换 |
| 子类一继承就出错              | 里氏替换     | 检查是否真的“**is-a**”，必要时改用组合代替继承  |
| 对象层层穿透调用              | 最少知识     | 引入中介者 / 外观，收敛出唯一调用入口           |
| 一个函数几百行、啥都干        | 单一职责     | 按职责拆成小函数，各自可独立测试                |
| 为简单需求写了一大堆抽象      | KISS         | 退回最直白的实现，先跑通再考虑抽象              |

## 4. 关键语言特性与易错点

[width(13,39,48)]

| 原则     | 在 JS 里怎么体现                         | 易错点                                                 |
| :------- | :--------------------------------------- | :----------------------------------------------------- |
| 单一职责 | 拆函数、拆模块，一个文件只做一件事       | 把“**行数少**”当唯一标准，拆得过碎反而增加跳转成本     |
| 开闭原则 | 策略对象、`Map` 映射、插件 / 中间件      | 一开始就为“**可能的变化**”预留抽象，属于过度设计       |
| 里氏替换 | ES6 `class` 继承、`extends`、方法重写    | 用重写改掉父类已实现的方法，破坏“**可替换**”的前提     |
| 接口隔离 | TypeScript `interface`、按需传入的小对象 | JS 没有编译期接口，只能靠约定与文档约束                |
| 依赖倒置 | 参数注入、`import` 抽象模块              | 直接 `import` 具体实现，换底层时要全局改动             |
| DRY      | 工具函数、常量、配置抽离                 | 把“**看起来像**”但语义不同的代码强行合并，耦合无关逻辑 |
| 最少知识 | 组合、中介者、外观模式                   | 为了“**少知道**”而堆砌过多封装层，反而更难追踪         |

## 5. 常见问题 (FAQ)

### 5.1 SOLID 五个原则必须全部满足吗？

不必。它们是**权衡的方向**，不是硬性打分项。小型脚本或一次性页面上强行套 SOLID，只会让代码更绕；当模块开始变大、需要多人协作与长期维护时，再把它们当作重构的指南针。

### 5.2 这些原则之间会冲突吗？

**会，而且很常见。** 例如为了满足开闭原则引入插件机制，往往会增加抽象层而违背 KISS。此时要按“**当前最痛的点**”取舍，而不是要求每条原则都拿满分。

### 5.3 在 Vue / React 项目里怎么落地这些原则？

单一职责对应“**一个组件只做一件事**”；依赖倒置对应“**组件依赖 `props` / `useContext` 这类抽象，而不是直接 `import` 具体实现**”；开闭原则对应“**用插槽、自定义 Hook 去扩展，而不是改老组件**”。

### 5.4 怎么判断自己是不是“过度设计”？

如果一段代码没有测试、没有第二处复用、未来几乎不会变，就不该为它引入模式或多余抽象。黄金法则是“**等痛了再重构**”，而不是一开始就把所有变化都预留出来。
