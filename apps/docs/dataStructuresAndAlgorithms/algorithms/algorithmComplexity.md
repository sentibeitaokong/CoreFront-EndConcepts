# 算法复杂度分析 (Algorithm Complexity Analysis)

## 1. 核心概念概览

在计算机科学中，我们无法通过“**运行这段代码花了多少秒**”来准确评估一个算法的好坏，因为这受到硬件性能、当前系统负载等太多外界因素的影响。

因此，我们引入了**渐进复杂度分析（Asymptotic Complexity Analysis）**，也就是我们常说的大 O 表示法（Big O Notation）。它主要关注当输入数据规模（`n`）趋于无穷大时，算法运行时间或内存占用的**增长趋势**。

### 1.1 大 O 表示法 (Big O Notation) 的核心法则

大 O 表示法用于描述算法在**最坏情况**下的时间或空间表现（有时也会分析平均情况）。在计算大 O 时，我们必须遵循以下三个核心法则：

- **只保留最高阶项：** 随着 `n` 变大，低阶项的影响微乎其微。例如，运行次数为 $2n^2 + 5n + 10$，我们只看 $2n^2$。
- **去掉常数系数：** 常数系数在 `n` 趋于无穷大时意义不大。上面的 $2n^2$ 最终会被记为 **$O(n^2)$**。
- **大 O 表示的是量级，而非精确次数。**

### 1.2 大 O、大 Ω 与大 Θ：三种渐进记号

日常口语里我们常把三者统称为“**大 O**”，但在严格定义下，它们描述的是不同的边界：

[width(23,18,43,16)]

| 记号               | 名称          | 含义                                                                                 | 生活化理解 |
| :----------------- | :------------ | :----------------------------------------------------------------------------------- | :--------- |
| **$O(f(n))$**      | 大 O (上界)   | 存在常数 $c$，当 $n$ 足够大时 $T(n) \le c \cdot f(n)$。即“**不会比它更差**”。        | 最悲观估计 |
| **$\Omega(f(n))$** | 大 Ω (下界)   | 当 $n$ 足够大时 $T(n) \ge c \cdot f(n)$。即“**不会比它更好**”。                      | 最乐观估计 |
| **$\Theta(f(n))$** | 大 Θ (紧确界) | 同时是上界和下界，$c_1 \cdot f(n) \le T(n) \le c_2 \cdot f(n)$。即“**就是这么多**”。 | 精确量级   |

> [!TIP]
> 面试与工程中说“**这段代码的复杂度是 O(n)**”，绝大多数时候指的其实是 Θ，只是习惯上借用了大 O 的写法。真正要严格区分时，判断标准是：**既给出了上界又给出了下界，才叫 Θ**；只给一头，才用 O 或 Ω。

### 1.3 最好、最坏、平均与均摊复杂度

同一个算法在不同输入下的表现可能天差地别。业界默认的口径是**最坏情况**，但另外三种也必须能说清楚：

[width(25,38,37)]

| 口径                        | 定义                                                               | 典型例子                                                         |
| :-------------------------- | :----------------------------------------------------------------- | :--------------------------------------------------------------- |
| **最好情况 (Best Case)**    | 输入恰好最“**配合**”算法时的复杂度。                               | 插入排序对已有序数组是 $O(n)$。                                  |
| **最坏情况 (Worst Case)**   | 输入最“**刁难**”算法时的复杂度，是算法性能的保底承诺。             | 快速排序每次选到极值作为基准，退化为 $O(n^2)$。                  |
| **平均情况 (Average Case)** | 在所有等概率输入上的期望复杂度，最难分析，却最贴近真实使用。       | 快速排序的平均复杂度是 $O(n \log n)$。                           |
| **均摊复杂度 (Amortized)**  | 把偶尔一次的高开销**分摊**到一连串操作上，得到单次操作的平均代价。 | 动态数组 `push` 触发扩容那一次是 $O(n)$，均摊到每次仍是 $O(1)$。 |

**均摊复杂度 ≠ 平均复杂度。** 平均复杂度是对**随机输入**求期望；均摊复杂度则是对**同一段代码的最坏操作序列**求平均，它给出的是确定性保证，与输入是否随机无关。

```js
// 以动态数组的扩容为例，理解均摊 O(1)
// 容量按 1、2、4、8... 成倍增长，元素搬移总数约为 1 + 2 + 4 + ... + n/2 < n，
// 所以连续 push n 次的代价是 O(n)，均摊到每一次 push 就是 O(1)。
function totalCopies(n) {
  let copies = 0
  // 第 k 次扩容会搬移 2^k 个元素，累加所有扩容的搬移量
  for (let size = 1; size < n; size *= 2) {
    copies += size
  }
  return copies // 结果小于 2n，相对元素总量 n 只是常数倍
}
```

## 2. 时间复杂度 (Time Complexity)

时间复杂度是指算法执行所需操作次数随数据规模 `n` 增长的趋势。

### 2.1 常见时间复杂度量级 (从优到劣)

[width(18,22,24,36)]

| 符号              | 读法 / 名称          | 增长趋势               | 典型算法/操作代表                                                         |
| :---------------- | :------------------- | :--------------------- | :------------------------------------------------------------------------ |
| **$O(1)$**        | 常数阶 (Constant)    | 无论数据多少，时间不变 | 哈希表查找、数组索引访问 (`arr[5]`)、简单数学计算。                       |
| **$O(\log n)$**   | 对数阶 (Logarithmic) | 极其平缓，近乎完美     | 二分查找、二叉搜索树查找。通常出现于“**每次砍掉一半**”的场景。            |
| **$O(n)$**        | 线性阶 (Linear)      | 数据翻倍，时间翻倍     | 数组遍历、顺序查找。                                                      |
| **$O(n \log n)$** | 线性对数阶           | 稍微陡于线性           | 快速排序、归并排序、堆排序的平均情况。通常出现于“**分治 + 遍历**”的场景。 |
| **$O(n^2)$**      | 平方阶 (Quadratic)   | 数据增加，时间暴增     | 冒泡排序、选择排序、两层嵌套的 `for` 循环。                               |
| **$O(2^n)$**      | 指数阶 (Exponential) | 数据稍大，直接死机     | 斐波那契数列的纯递归解法、部分回溯算法。                                  |
| **$O(n!)$**       | 阶乘阶 (Factorial)   | 最差，毫无实用价值     | 全排列问题。                                                              |

### 2.2 时间复杂度分析

#### 2.2.1 $O(1)$ - 常数阶

没有循环，没有与 `n` 相关的递归，即使代码有成百上千行，只要执行次数是固定的，就是 $O(1)$。

```js
function getFirstElement(arr) {
  const a = 1 + 1 // 1次操作
  return arr[0] // 1次操作
} // 总计 2 次，大O表示为 O(1)
```

#### 2.2.2 $O(n)$ - 线性阶

一层循环，循环次数直接受到输入规模 `n` 的影响。

```js
function findMax(arr) {
  let max = arr[0]
  for (let i = 1; i < arr.length; i++) {
    // 循环 n-1 次
    if (arr[i] > max) max = arr[i]
  }
  return max
} // O(n)
```

#### 2.2.3 $O(n^2)$ - 平方阶

双层嵌套循环，外层循环 `n` 次，内层也循环 `n` 次（或者 `n` 的某个比例，如 $n/2$）。

```js
function printPairs(arr) {
  for (let i = 0; i < arr.length; i++) {
    // 执行 n 次
    for (let j = i; j < arr.length; j++) {
      // 平均执行 n/2 次
      console.log(arr[i], arr[j])
    }
  }
} // 总次数约为 n^2 / 2，忽略系数和低阶项，记为 O(n^2)
```

#### 2.2.4 $O(\log n)$ - 对数阶

循环条件每次都成倍地缩小范围。这是面试中最常要求优化的目标。

```js
function binarySearch(arr, target) {
  let left = 0
  let right = arr.length - 1
  while (left <= right) {
    let mid = Math.floor((left + right) / 2)
    if (arr[mid] === target) return mid
    // 关键：每次排除一半的数据
    if (arr[mid] < target) left = mid + 1
    else right = mid - 1
  }
  return -1
} // O(log n)
```

### 2.3 常见数据结构操作复杂度速查表

[width(13,11,11,11,11,9,34)]

| 数据结构                  | 访问        | 查找        | 插入                | 删除                | 空间   | 说明                                                             |
| :------------------------ | :---------- | :---------- | :------------------ | :------------------ | :----- | :--------------------------------------------------------------- |
| **数组 (Array)**          | $O(1)$      | $O(n)$      | $O(n)$，末尾 $O(1)$ | $O(n)$，末尾 $O(1)$ | $O(n)$ | 索引访问是常数时间；头部、中部增删要整体搬移后续元素。           |
| **链表 (Linked List)**    | $O(n)$      | $O(n)$      | $O(1)$              | $O(1)$              | $O(n)$ | 给定节点时增删是 $O(1)$，但定位到该节点本身要花 $O(n)$。         |
| **栈 (Stack)**            | 栈顶 $O(1)$ | $O(n)$      | 栈顶 $O(1)$         | 栈顶 $O(1)$         | $O(n)$ | 只在栈顶操作，`push` / `pop` 均为 $O(1)$。                       |
| **队列 (Queue)**          | 队首 $O(1)$ | $O(n)$      | 队尾 $O(1)$         | 队首 $O(1)$         | $O(n)$ | 用数组 `shift` 出队是 $O(n)$，高频出队应改用双端队列或循环队列。 |
| **哈希表 (Hash / Map)**   | —           | 平均 $O(1)$ | 平均 $O(1)$         | 平均 $O(1)$         | $O(n)$ | 最坏 $O(n)$：哈希冲突严重时退化为链表甚至红黑树。                |
| **二叉搜索树 (BST)**      | $O(\log n)$ | $O(\log n)$ | $O(\log n)$         | $O(\log n)$         | $O(n)$ | 仅当树**相对平衡**时成立；退化成链表时全部操作变为 $O(n)$。      |
| **堆 (Heap)**             | 堆顶 $O(1)$ | $O(n)$      | $O(\log n)$         | 堆顶 $O(\log n)$    | $O(n)$ | 适合反复取最值（优先队列）；查找任意元素是 $O(n)$。              |
| **平衡树 (AVL / 红黑树)** | $O(\log n)$ | $O(\log n)$ | $O(\log n)$         | $O(\log n)$         | $O(n)$ | 有序且动态，是有序 `Map` 之类场景与数据库索引的常用底层。        |

> [!NOTE]
> 哈希表与 BST 的复杂度都分“**平均 / 平衡**”和“**最坏 / 退化**”两种情况，工程中真正的性能事故往往就发生在最坏情况下，选型时要一并考虑。

### 2.4 递归算法的复杂度分析：递归树与主定理

递归代码的复杂度不能只看循环，要先写出**递推式**再求解。最通用的两种方法如下。

#### 2.4.1 **递归树（画出每一层的工作量）**

以二分查找为例，递推式是 $T(n) = T(n/2) + O(1)$：每一层只做一次比较，一共 $\log n$ 层，所以 $T(n) = O(\log n)$。

#### 2.4.2 **主定理 (Master Theorem)**

对于形如 $T(n) = a \cdot T(n/b) + f(n)$ 的递推式（其中 $a \ge 1$、$b > 1$），比较 $f(n)$ 与 $n^{\log_b a}$ 的量级即可得出结果：

[width(11,58,31)]

| 情形   | 条件                                                     | 结论                                 |
| :----- | :------------------------------------------------------- | :----------------------------------- |
| 情形 1 | $f(n) = O(n^{\log_b a - \epsilon})$                      | $T(n) = \Theta(n^{\log_b a})$        |
| 情形 2 | $f(n) = \Theta(n^{\log_b a})$                            | $T(n) = \Theta(n^{\log_b a} \log n)$ |
| 情形 3 | $f(n) = \Omega(n^{\log_b a + \epsilon})$，且满足正则条件 | $T(n) = \Theta(f(n))$                |

> [!WARNING]
> 主定理只适用于“**子问题规模相等**”的均匀划分。像快速排序那样基准随机、两侧规模可能极不平衡的场景，主定理并不直接适用，需要用期望分析，或直接看它退化为 $O(n^2)$ 的最坏情况。

### 2.5 工程实践：如何根据复杂度选算法

复杂度不是纸面游戏，选型时要同时权衡数据规模、数据特征、最坏情况、常数与内存：

[width(15,44,41)]

| 决策维度           | 要点                                                                           | 实践建议                                                            |
| :----------------- | :----------------------------------------------------------------------------- | :------------------------------------------------------------------ |
| **先看数据规模**   | $n$ 很小时，$O(n^2)$ 与 $O(n \log n)$ 的差距可能只有几毫秒，代码可读性更重要。 | $n < 100$ 时别过早优化；$n > 10^5$ 时必须想办法把 $O(n^2)$ 降下来。 |
| **再看数据特征**   | 数据是否已有序、是否分布均匀、是否支持随机访问，直接决定能否使用特化算法。     | 有序数据用二分查找；分布均匀的数值可考虑插值查找。                  |
| **关注最坏情况**   | 平均快不代表安全，攻击者可能专门构造输入触发最坏路径（哈希碰撞、快排退化）。   | 面对不可信输入，选有最坏情况保证的算法，或加随机化打散。            |
| **考虑常数与缓存** | 同一量级下，循环紧凑、内存连续的代码往往更快。                                 | 同样是 $O(n \log n)$，小数组上插入排序常快于递归的归并排序。        |
| **别忽略空间**     | 递归、辅助数组都会占用额外内存，内存敏感的场景尤其要算清楚。                   | 内存吃紧时优先选原地算法（堆排序），而不是归并排序。                |

**一句话总结：** 先确认规模，再匹配数据特征，最后用最坏情况和常数因子兜底——而不是无脑追求“**理论上最优**”的复杂度。

## 3. 空间复杂度 (Space Complexity)

空间复杂度是指算法在运行过程中**临时占用存储空间**大小的量度，同样使用大 O 表示法。

**注意：** 我们评估空间复杂度时，**通常不包括输入数据本身所占的空间**，只计算算法为了解决问题而**额外开辟**的内存空间（如临时数组、哈希表、递归调用栈等）。

### 3.1 常见空间复杂度分析

[width(16,84)]

| 空间复杂度      | 典型场景                                                                           |
| :-------------- | :--------------------------------------------------------------------------------- |
| **$O(1)$**      | 只使用了几个固定的辅助变量，不随输入规模 `n` 变化。（如冒泡排序、双指针遍历）。    |
| **$O(n)$**      | 创建了一个与输入规模长度相同的临时数组或哈希表;或者**单分支的递归深度**达到了`n`。 |
| **$O(n^2)$**    | 创建了一个 `n * n` 的二维数组或矩阵（如某些图的邻接矩阵表示）。                    |
| **$O(\log n)$** | 快速排序或归并排序的递归调用栈深度。                                               |

### 3.2 递归的空间复杂度陷阱

很多初学者认为只要没有显式地 `new Array()`，空间复杂度就是 $O(1)$。这是大错特错的！

**在递归算法中，系统必须为每一次函数调用分配“执行栈（Call Stack）”。递归的深度有多深，空间复杂度就有多大。**

```js
// 示例：求 1 到 n 的和（纯递归）
function sumRecursion(n) {
  if (n === 1) return 1
  return n + sumRecursion(n - 1)
}
// 分析：为了计算 sumRecursion(n)，必须等 sumRecursion(n-1) 返回... 一路压栈。
// 栈的深度达到了 n 层。因此，虽然没有创建数组，但其 空间复杂度是 O(n)。
// （这也是为什么递归层数太多会引发 Stack Overflow 的原因）。
```

## 4. 常见问题深度剖析 (FAQ)

### 4.1 `O(2n)` 和 `O(n)` 有区别吗？

在大 O 表示法中**没有区别**，统一记为 $O(n)$；但常数因子在实际工程中当然有影响，同为 $O(n)$ 的 $20n$ 与 $n$ 次操作，后者会明显更快。面试时可以说：“**复杂度是 $O(n)$，但常数系数更小，实际性能更好。**”

### 4.2 最好情况、最坏情况、平均情况，以哪个为准？

业界默认讨论**最坏情况复杂度 (Worst-case Complexity)**，因为它为性能提供了“**保底承诺**”。对于最坏情况极难出现的算法（如加入随机化后的快速排序，其最坏 $O(n^2)$ 几乎不会发生），则会重点讨论**平均情况复杂度**，快排的平均是 $O(n \log n)$。

### 4.3 时间和空间可以兼得吗？

很难，二者通常需要权衡，“**空间换时间**”正是最常用的优化套路。例如无序数组的查找每次遍历是 $O(n)$ 时间、$O(1)$ 空间，改用哈希表后查找降为 $O(1)$，代价是空间升到 $O(n)$。优秀的工程师要在业务场景中找到两者的**最佳平衡点**。

### 4.4 怎么判断我的算法够不够快？（估算技巧）

在 LeetCode 这类评测系统中，服务器每秒约能执行 $10^7$ 到 $10^8$ 次基础运算。

- 数据量 $n \approx 10^5$ 时，算法必须是 $O(n \log n)$ 或 $O(n)$ 才能通过，写 $O(n^2)$ 必然超时。
- 数据量 $n \le 100$ 时，可以放心地写 $O(n^3)$ 甚至回溯。

### 4.5 均摊复杂度里的“**均摊**”到底是怎么摊的？

把低频的高开销操作摊到高频的廉价操作上。以动态数组 `push` 为例：第 $n$ 次插入触发扩容时要复制 $O(n)$ 个元素，但扩容间隔按 1、2、4、8…… 指数级拉长，连续 `push` $n$ 次的总复制量只有 $O(n)$，均摊后每次仍是 $O(1)$。它是对**最坏操作序列**求出的确定性上界，与“**平均复杂度**”对随机输入求期望是两回事。

### 4.6 为什么二分查找是 $O(\log n)$ 而不是 $O(n/2)$？

每次比较都把候选范围砍掉一半，$n$ 经 $\log_2 n$ 次折半后降到 1，所以是 $O(\log n)$。大 O 会忽略底数，$O(\log_2 n)$ 与 $O(\log_{10} n)$ 只差一个常数倍，写作 $O(\log n)$ 即可。

### 4.7 递归一定比迭代慢吗？

不一定。递归的额外成本主要是函数调用与栈帧，时间和空间都是 $O(\text{递归深度})$；但归并、快排这类分治算法天生适合递归，硬改成迭代反而更复杂、更易错。只有递归深度过大可能栈溢出时，才值得改成显式栈的迭代写法。

### 4.8 同样的复杂度，为什么实测快慢能差好几倍？

大 O 丢掉了常数因子和低阶项，也忽略了**缓存局部性**——内存连续、分支可预测的代码，常比“**同复杂度但到处跳转**”的代码快数倍（哈希表 vs 数组遍历就是典型）。所以复杂度是用来**筛选方案**的，最终仍要用真实数据做基准测试。
