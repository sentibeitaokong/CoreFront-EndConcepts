# HTTP 协议

**HTTP** (HyperText Transfer Protocol，超文本传输协议) 是当今互联网上应用最为广泛的一种网络通信协议。它是基于 TCP/IP 协议之上的**应用层协议**，规定了客户端（如浏览器）与服务器之间**报文的格式**和**交互的规则**——HTTP 自己不负责把数据从 A 送到 B（那是 TCP 的事），它只负责定义双方“**说什么、怎么说**”。

**一句话理解**：HTTP 是一套“**一问一答、说完就忘**”的通信约定——客户端把“**我要什么**”写成一段有格式的文本发出去，服务器把“**给你什么**”写成同样有格式的文本发回来；每一次对话互相独立，谁都不记得上一次说过什么。浏览器地址栏里的每一个 `https://` 地址、页面上每一次点击触发的数据加载，背后都是一次或多次这样的问答。

> [!TIP] 相关阅读
> HTTP 跑在 [TCP 协议](/networkAndBrowsers/transport/tcp) 之上（HTTP/3 则跑在 UDP 之上的 QUIC 里，见 [UDP 协议](/networkAndBrowsers/transport/udp)），它所在的层次见 [OSI 七层模型](/networkAndBrowsers/fundamentals/osi)；它的加密版本见 [HTTPS 协议](/networkAndBrowsers/http/https)，头部字段清单见 [HTTP 请求头与响应头](/networkAndBrowsers/http/headers)，域名如何变成 IP 见 [DNS 解析](/networkAndBrowsers/fundamentals/dns)；它的状态保持依赖 [Cookie 与浏览器存储](/networkAndBrowsers/browser/cookieAndStorage)，缓存策略见 [浏览器缓存](/networkAndBrowsers/caching/browserCache)，前端发起请求的 API 见 [fetch](/networkAndBrowsers/api/fetch)。

## 1. 什么是 HTTP 协议？

### 1.1 它在协议栈中的位置

HTTP 处在**应用层**：它不碰网线、不认 IP、不管丢包，只负责把“**请求**”和“**响应**”这两种报文定义好，然后交给下层的 [TCP](/networkAndBrowsers/transport/tcp) 去送。

```markdown
┌─────────────────────────────────────────────┐
│ 应用层 HTTP / HTTPS / DNS / WebSocket │ ← HTTP 在这一层：定义报文格式
├─────────────────────────────────────────────┤
│ 传输层 TCP / UDP │ ← 负责把字节可靠（或不保证）地送到
├─────────────────────────────────────────────┤
│ 网络层 IP │ ← 负责把包路由到哪台机器
├─────────────────────────────────────────────┤
│ 链路层 以太网 / Wi-Fi │ ← 负责一段一段地传
└─────────────────────────────────────────────┘
```

分层的价值就在这里：**HTTP 完全不用关心底层是网线、Wi-Fi 还是 5G**。你换一个网络，报文格式一个字都不用改。也正因为 HTTP 只是一个“**格式约定**”，它才能被塞进任何能传字节的通道里——HTTP/2、HTTP/3 换了底层传输方式，但方法、状态码、头部字段的语义**完全没有变**。

### 1.2 五个核心特点

- **无连接**：HTTP 本身不维护“**连接**”这个概念，它的一次交互就是“**请求 → 响应**”这么一对报文，用完即走。历史上（HTTP/1.0）每请求都要重新建一次 TCP 连接，开销极大；HTTP/1.1 引入了 `Keep-Alive` **持久连接**后，TCP 连接可以复用，如今已经是默认行为。所以更准确的说法是：**HTTP 在语义上是无连接的，只是在传输层面借用了 TCP 的长连接来省去反复握手的开销**。
- **无状态**：协议对事务处理没有记忆能力。服务器不记得“**上一秒是谁在问我**”“**这个用户登录了没**”。好处是服务器更简单、更容易横向扩容（任何一台机器都能处理任何一个请求）；代价是**如果后续处理需要前面的信息，就必须重传**——这正是 Cookie 和 Session 被发明出来的原因。
- **灵活、可扩展**：HTTP 允许传输任意类型的数据，数据类型由 `Content-Type` 标记。图片、JSON、视频、字体走的都是同一套报文格式。开发者还可以通过**自定义头部**扩展协议（见 [HTTP 请求头与响应头](/networkAndBrowsers/http/headers)）。
- **C/S 架构**：经典的 Client-Server（客户端-服务端）请求-响应模型。通信**一定由客户端发起**，服务器不会主动推送（服务器主动推数据要靠 SSE、WebSocket 等手段，见 [实时通信](/networkAndBrowsers/realtime/realtimeCommunication)）。
- **报文可读（HTTP/1.x）**：HTTP/1.x 的报文是纯文本的，用开发者工具或 `curl -v` 能直接看懂。这一点让它极其容易调试——代价是冗余（每个请求都要重复带一整套头部），HTTP/2 正是为了解决这个代价才改成了二进制格式。

### 1.3 把 HTTP 放回全局：一次页面加载发生了什么

理解 HTTP 的最好方式，是看它在整条链路上处于哪一环。当你在地址栏敲下 `https://example.com/index.html`：

1. **[DNS 解析](/networkAndBrowsers/fundamentals/dns)**：把 `example.com` 翻译成 IP 地址。
2. **建立连接**：[TCP 三次握手](/networkAndBrowsers/transport/tcp)，若是 HTTPS 还要再做一次 [TLS 握手](/networkAndBrowsers/http/https)。
3. **发送请求**：浏览器按 HTTP 格式发出请求报文（方法 + 路径 + 头部 + 可能的正文）。
4. **服务器处理**：服务器（或前面的 [CDN](/networkAndBrowsers/fundamentals/cdn)、Nginx）解析报文，查缓存、查数据库，产出响应报文。
5. **返回响应**：状态码 + 响应头 + 响应正文（HTML）。
6. **浏览器渲染**：解析 HTML，为了页面里的 CSS、JS、图片，再重复第 3～5 步（这些请求可以复用第 2 步建立的连接）。
7. **连接复用或关闭**：HTTP/1.1 默认保持连接，等一段时间没有新请求再关闭。

一次页面加载往往意味着**几十到几百次 HTTP 请求**。前端的性能优化，大半都是在减少这个次数、或者让每次请求更快。

## 2. URL：HTTP 的资源定位

HTTP 的报文里写的“**要什么**”，靠的就是 URL。理解 URL 的组成，是理解请求路径、查询参数、锚点行为的前提。

### 2.1 URL 的组成

```markdown
https:// user:pass @ www.example.com : 443 /a/b/index.html ? id=1&tab=2 # 章节
└─┬──┘ └───┬───┘ └──────┬──────┘ └┬┘ └──────┬──────┘ └────┬────┘ └─┬─┘
协议 身份信息 主机(Host) 端口 路径(Path) 查询字符串 片段
scheme authority
```

[width(19,49,32)]

| 部分              | 作用                                                                    | 是否发给服务器             |
| :---------------- | :---------------------------------------------------------------------- | :------------------------- |
| **协议 (scheme)** | `http` / `https`，决定用什么协议、什么端口。                            | 否（体现在报文格式上）     |
| **主机 + 端口**   | 定位到哪台服务器上的哪个服务。端口省略时 http 补 `80`、https 补 `443`。 | 是，作为 `Host` 头部       |
| **路径 (path)**   | 定位服务器上的哪个资源。                                                | 是，出现在请求行里         |
| **查询字符串**    | `?key=value&key2=value2`，给资源的附加参数（分页、筛选、搜索词）。      | 是，包含在请求行里         |
| **片段 (hash)**   | `#section`，**只在浏览器内部使用**（页面内跳转、前端路由）。            | **否，永远不会发给服务器** |

### 2.2 URL、URI、URN 是什么关系

- **URI (Uniform Resource Identifier)**：统一资源**标识符**，是个大概念——只要能唯一标识一个资源，就算 URI。
- **URL (Uniform Resource Locator)**：统一资源**定位符**，是 URI 的一个子集，通过“**在哪里能找到它**”来标识资源（有协议、有主机名）。日常说的网址都是 URL。
- **URN (Uniform Resource Name)**：统一资源**名称**，通过“**它叫什么**”来标识资源（如 `urn:isbn:0451450523`），与位置无关。

一句话：**URI 是总称，URL 和 URN 是它的两种实现**。日常开发和文档里说的“**URI**”基本等同于“**URL**”，HTTP 报文里的 `Request-URI` 指的也是请求行里那一段路径 + 查询字符串。

### 2.3 百分号编码：为什么中文要变成 `%E4%B8%AD`

URL 能安全传输的只有一小撮 ASCII 字符。中文、空格、`&`、`#`、`/` 这些字符如果原样出现，会造成歧义（比如参数里的 `&` 会被当成参数分隔符），所以必须**先转义再拼接**：

- 空格的编码是 `%20`（在查询字符串里也可以写成 `+`）。
- 中文按 **UTF-8** 转成字节，每个字节写成 `%XX`。`中` → `E4 B8 AD` → `%E4%B8%AD`。

```js
// 前端拼查询参数时，永远用 URLSearchParams 或 encodeURIComponent，不要手写字符串拼接
const params = new URLSearchParams({ q: '前端 面试', page: 1 })
console.log(params.toString()) // q=%E5%89%8D%E7%AB%AF+%E9%9D%A2%E8%AF%95&page=1
```

注意 `encodeURI` 和 `encodeURIComponent` 的区别：前者**不转义** `& = ? / #` 等 URL 结构字符，适合对一整条 URL 做编码；后者会转义它们，适合对**参数值**做编码。**在拼接参数值时用 `encodeURIComponent`，用错会导致参数被截断或注入**。

### 2.4 路径参数 vs 查询参数

RESTful 风格里两者分工明确：

- **路径参数**表示“**是哪个资源**”，是资源身份的一部分：`/users/123/orders`。
- **查询参数**表示“**怎么筛选/排序/分页**”，不影响资源身份：`/users?role=admin&page=2`。

## 3. HTTP 报文结构

HTTP 报文是客户端和服务器之间交换数据的方式，分为两种：**请求报文 (Request Message)** 和 **响应报文 (Response Message)**。两者结构完全对称，都分成「**起始行 / 头部 / 空行 / 正文**」四段。

### 3.1 请求报文

由客户端发送给服务器。

```http
POST /api/users HTTP/1.1          ← 请求行：方法 + 路径 + 版本
Host: api.example.com             ┐
Content-Type: application/json    │ 请求头：一行一个字段
Content-Length: 27                ┘
                                  ← 空行：CRLF，头部到此结束
{"name":"张三","age":18}          ← 请求正文（可选）
```

- **请求行 (Request Line)**：`<Method> <Request-URI> <HTTP-Version>`。
  - **Method**：请求方法，如 `GET`、`POST`，表明要对资源做什么。
  - **Request-URI**：请求的资源标识符。注意这里**通常是相对路径**（`/api/users`）而不是完整 URL——主机名已经在 `Host` 头部里了。
  - **HTTP-Version**：协议版本，如 `HTTP/1.1`。
  - _示例_：`GET /index.html HTTP/1.1`
- **请求头 (Headers)**：一组 `字段名: 字段值` 的键值对，向服务器传递客户端信息与请求的附加信息。
  - _示例_：`Host: www.example.com`、`User-Agent: Chrome/120.0...`
- **空行 (CRLF)**：一个回车换行符（`\r\n`），是**头部结束、正文开始的分界标记**。这个空行是必须的，解析器靠它才知道“头部读完了”。
- **请求正文 (Body)**：可选。`POST`、`PUT`、`PATCH` 等方法把要提交的数据放在这里。

### 3.2 响应报文

由服务器返回给客户端。

```http
HTTP/1.1 200 OK                   ← 状态行：版本 + 状态码 + 原因短语
Content-Type: application/json    ┐
Content-Length: 24                │ 响应头
Cache-Control: max-age=60         ┘
                                  ← 空行
{"id":1,"name":"张三"}            ← 响应正文
```

- **状态行 (Status Line)**：`<HTTP-Version> <Status-Code> <Reason-Phrase>`。
  - **Status-Code**：状态码，如 `200`、`404`。
  - **Reason-Phrase**：对状态码的简短文本描述，如 `OK`、`Not Found`。它**只是给人看的**，程序判断结果必须用状态码——原因短语可以被服务器随意改写。
  - _示例_：`HTTP/1.1 200 OK`
- **响应头 (Headers)**：传递服务器自身信息、对响应的附加说明（类型、长度、缓存、跨域权限等）。
  - _示例_：`Content-Type: text/html`、`Content-Length: 1234`
- **空行 (CRLF)**：分隔响应头和响应正文。
- **响应正文 (Body)**：服务器返回的实际数据，如 HTML 页面、JSON 数据、图片二进制等。

## 4. 请求方法 (Methods)

HTTP 定义了一组请求方法，以表明要对给定资源执行的操作。

### 4.1 方法总览

[width(15,28,9,9,39)]

| 方法          | 语义                                                         | 安全 | 幂等 | 说明                                                              |
| :------------ | :----------------------------------------------------------- | :--- | :--- | :---------------------------------------------------------------- |
| **`GET`**     | 获取资源。                                                   | ✅   | ✅   | 最常用，参数在 URL 上，可被缓存。                                 |
| **`HEAD`**    | 与 `GET` 相同，但**只返回头部**，不返回正文。                | ✅   | ✅   | 用于探测资源是否存在、大小、最后修改时间，或预检链接有效性。      |
| **`POST`**    | 提交数据，通常导致服务器状态改变或产生副作用（如创建资源）。 | ❌   | ❌   | 参数在正文里，无长度限制（受服务端配置限制）。                    |
| **`PUT`**     | **全量替换**目标资源。若资源不存在，可以创建它。             | ❌   | ✅   | 客户端提供完整表示，重复提交结果一致。                            |
| **`PATCH`**   | 对资源做**部分修改**。                                       | ❌   | ❌   | 只提交要改的字段。是否幂等取决于补丁语义（如“数值 +1”就不幂等）。 |
| **`DELETE`**  | 删除指定资源。                                               | ❌   | ✅   | 删两次和删一次的结果都是“**资源不存在**”。                        |
| **`OPTIONS`** | 查询服务器针对该资源支持的通信选项。                         | ✅   | ✅   | 跨域时的**预检请求**用的就是它；也可用于获取 `Allow` 头。         |
| **`CONNECT`** | 让服务器用一条连接充当到目标主机的**隧道**。                 | ❌   | ❌   | 用于 HTTPS 代理；普通业务开发不会用到。                           |
| **`TRACE`**   | 回显服务器收到的请求，用于调试。                             | ✅   | ✅   | **存在 XST 攻击风险，生产环境应在服务器上禁用**。                 |

> [!NOTE] 判断结果永远看状态码，别看原因短语
> 表中“**安全 / 幂等**”是**协议对语义的约定**，而不是服务器会自动帮你做到的保证。真正让幂等生效的，是服务端的实现（见 [幂等性对前端有什么用](#_12-5-幂等性对前端有什么用)）。

### 4.2 安全性、幂等性、可缓存性到底在管什么

[width(13,18,27,42)]

| 性质                     | 管什么                                           | 哪些方法                                                           | 对前端意味着什么                                                                                                                                                                        |
| :----------------------- | :----------------------------------------------- | :----------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **安全性 (Safe)**        | 请求**不会改变服务器状态**（只读）。             | `GET`、`HEAD`、`OPTIONS`、`TRACE`                                  | 浏览器、爬虫、CDN 会毫无顾忌地**预取、缓存、重复发送**——所以**绝不能用 `GET` 做删除、扣款**：一次预加载或一次爬虫抓取就能把数据改掉。                                                   |
| **幂等性 (Idempotent)**  | 执行一次和执行多次，**对服务器状态的影响相同**。 | `GET`、`HEAD`、`PUT`、`DELETE`、`OPTIONS`                          | 只有幂等的方法才能被**安全地自动重试**。网络抖动时重试 `PUT` 没事，重试 `POST` 下单却可能生成两笔订单——幂等键就是这么来的（见 [请求治理](/networkAndBrowsers/api/requestGovernance)）。 |
| **可缓存性 (Cacheable)** | 响应**默认是否可以被缓存**。                     | `GET`、`HEAD` **可缓存**；`POST`、`PUT`、`DELETE` **默认不可缓存** | 这是[浏览器缓存](/networkAndBrowsers/caching/browserCache)能自动生效的前提：强缓存与协商缓存，全都建立在这条约定上。                                                                    |

> [!NOTE] 幂等看的是服务器状态，不是响应报文
> `DELETE /users/1` 第一次返回 `204`，第二次返回 `404`——状态码不同，但服务器状态都是“**用户 1 不存在**”，所以仍然幂等。判断幂等时别拿两次响应去比对。

一句话串起来：**安全决定“能不能随便重发”，幂等决定“能不能自动重试”，可缓存决定“能不能省掉这次请求”**。

### 4.3 几组最容易混淆的方法

`GET` vs `POST`、`PUT` vs `PATCH`、`PUT` vs `POST` 这三组之所以容易混，是因为它们各自比的是**不同的维度**。把维度摊开看，就没有一组需要背：

[width(9,26,25,22,18)]

| 维度             | `GET`                                                    | `POST`                                                   | `PUT`                                                              | `PATCH`                                          |
| :--------------- | :------------------------------------------------------- | :------------------------------------------------------- | :----------------------------------------------------------------- | :----------------------------------------------- |
| **语义**         | 只读（安全 + 幂等）。                                    | 会改状态（不安全 + 不幂等）。                            | **全量替换**目标资源，不存在时可以创建（不安全 + 幂等）。          | **部分修改**（不安全；是否幂等取决于补丁语义）。 |
| **参数放哪**     | 拼在 URL 上——会进浏览器历史、服务器访问日志、`Referer`。 | 放在正文里——不落上面这些地方。                           | 放在正文里。                                                       | 放在正文里。                                     |
| **资源 ID 谁定** | 不涉及，用 URL 定位已有资源。                            | **服务器分配**：`POST /users` 重复提交会建出多个。       | **客户端指定**：`PUT /users/1` 重复提交结果相同。                  | 客户端指定：`PATCH /users/1`。                   |
| **典型用法**     | 查询、读取。                                             | 创建资源；触发带副作用的动作（如 `/users/1/activate`）。 | 整体更新——要提交**完整表示**，只改一个字段也得把其它字段一并带上。 | 局部更新——只提交变化的字段。                     |

## 5. 状态码 (Status Codes)

### 5.1 五大分类

状态码由三位数字构成，**第一个数字决定了响应的类别**，后两位没有分类含义。

[width(9,28,63)]

| 分类    | 类别                      | 描述                               |
| :------ | :------------------------ | :--------------------------------- |
| **1xx** | 信息性 (Informational)    | 表示请求已接收，继续处理。         |
| **2xx** | 成功 (Success)            | 表示请求已被成功接收、理解、接受。 |
| **3xx** | 重定向 (Redirection)      | 要完成请求，需要采取进一步操作。   |
| **4xx** | 客户端错误 (Client Error) | 请求有语法错误或请求无法实现。     |
| **5xx** | 服务器错误 (Server Error) | 服务器未能实现合法的请求。         |

### 5.2 常见状态码速查

[width(30,30,40)]

| 状态码                       | 含义                                           | 典型场景                                                                        |
| :--------------------------- | :--------------------------------------------- | :------------------------------------------------------------------------------ |
| `100 Continue`               | 服务器已收到请求头部，客户端可以继续发送正文。 | 大文件上传前的试探（`Expect: 100-continue`）。                                  |
| `101 Switching Protocols`    | 同意切换协议。                                 | WebSocket 握手成功。                                                            |
| `200 OK`                     | 请求成功。                                     | 常规成功响应。                                                                  |
| `201 Created`                | 请求成功并且服务器创建了新的资源。             | `POST /users` 创建成功，配合 `Location` 头。                                    |
| `204 No Content`             | 成功，但**没有正文**。                         | `DELETE` 成功；`PUT` 成功但无需返回内容。                                       |
| `206 Partial Content`        | 返回资源的一部分。                             | 视频拖动进度、大文件**断点续传**。                                              |
| `301 Moved Permanently`      | **永久**重定向，资源已永久搬到新位置。         | 域名更换、http → https。会被浏览器长期缓存。                                    |
| `302 Found`                  | **临时**重定向。                               | 登录后跳回原页面、活动页临时跳转。                                              |
| `304 Not Modified`           | 资源未修改，直接用本地缓存。                   | **协商缓存命中**（见 [浏览器缓存](/networkAndBrowsers/caching/browserCache)）。 |
| `307 Temporary Redirect`     | 临时重定向，且**保持原方法和正文**。           | 需要转发 `POST` 时的临时跳转。                                                  |
| `308 Permanent Redirect`     | 永久重定向，且**保持原方法和正文**。           | 需要转发 `POST` 时的永久跳转。                                                  |
| `400 Bad Request`            | 客户端请求有语法错误，服务器无法理解。         | 参数缺失、JSON 格式错误。                                                       |
| `401 Unauthorized`           | **未认证**，需要用户提供身份凭证。             | Token 过期或未携带。                                                            |
| `403 Forbidden`              | 已识别身份但**拒绝授权**。                     | 普通用户访问管理后台。                                                          |
| `404 Not Found`              | 请求的资源不存在。                             | 路由错误、资源被删除。                                                          |
| `405 Method Not Allowed`     | 资源存在，但不支持这个请求方法。               | 对只读接口发了 `POST`。                                                         |
| `408 Request Timeout`        | 服务器等待请求超时。                           | 客户端建立了连接却没发数据。                                                    |
| `413 Payload Too Large`      | 请求正文过大。                                 | 上传超过 `client_max_body_size`。                                               |
| `415 Unsupported Media Type` | 请求正文的类型服务器不支持。                   | 传了 `text/plain` 但接口只要 `application/json`。                               |
| `429 Too Many Requests`      | 请求过于频繁，被限流。                         | 应配合 `Retry-After` 头做退避重试。                                             |
| `500 Internal Server Error`  | 服务器内部发生了不可预期的错误。               | 后端未捕获的异常。                                                              |
| `501 Not Implemented`        | 服务器不支持此请求方法。                       | 极少见。                                                                        |
| `502 Bad Gateway`            | 作为网关或代理的服务器，从上游收到无效响应。   | 反向代理后的服务挂了 / 重启中。                                                 |
| `503 Service Unavailable`    | 服务器当前不能处理请求。                       | 过载、停机维护，应配合 `Retry-After`。                                          |
| `504 Gateway Timeout`        | 网关等待上游响应超时。                         | 后端接口太慢，超过 Nginx 的 `proxy_read_timeout`。                              |

## 6. 连接管理：从短连接到长连接

HTTP 在语义上无连接，但每一次请求总得真实地占用一条 TCP 连接。连接怎么建、怎么复用、怎么并发，直接决定了页面加载的快慢。

### 6.1 短连接与长连接

- **短连接（HTTP/1.0 默认）**：一个请求 → 一次 TCP 三次握手 → 一次响应 → 四次挥手断开。一个页面 50 个资源就是 50 次握手 + 50 次挥手，而三次握手本身就要 1 个 RTT（见 [TCP 协议](/networkAndBrowsers/transport/tcp)）。更糟的是 TCP 的**慢启动**：每条新连接都要从很小的拥塞窗口开始爬，还没爬到理想速度，请求就结束了。
- **长连接（HTTP/1.1 默认）**：请求头/响应头里的 `Connection: keep-alive`（HTTP/1.1 默认开启，不必显式写）表示“**这条连接先别关**”，后续请求可以复用。省掉了反复握手和慢启动，是 HTTP/1.1 对性能最大的贡献。
- **什么时候会关闭**：双方任意一方发送 `Connection: close`，或空闲超时（Nginx `keepalive_timeout` 默认 65 秒），或达到 `keepalive_requests` 上限。

> [!NOTE] TCP 的 Keep-Alive 和 HTTP 的 Keep-Alive 不是一回事
> 前者是 TCP 层的**保活探测**（定期发空包确认对端还活着），后者是 HTTP 层的**连接复用协商**。名字一样，作用完全不同，别混着说。

### 6.2 浏览器是怎么用连接的

浏览器不能把所有请求都压到一条连接上——HTTP/1.1 一条连接同一时刻只处理一个请求（见下）。所以浏览器对**同一个域名**会并行开若干条连接，主流浏览器的上限通常是 **6 条**。

- **请求排队**：一个页面有 10 个同域资源，最多 6 个同时在跑，剩下的排队等。这也是“**为什么资源多了首屏就慢**”的直接原因。
- **域名分片（domain sharding）**：HTTP/1.1 时代的经典优化——把静态资源分散到 `static1.example.com`、`static2.example.com`…… 让浏览器能开更多连接并行下载。**在 HTTP/2 下这个优化是负的**：多域名意味着多一次 DNS、多一次 TCP + TLS 握手，而 HTTP/2 单条连接就能并行，所以现代优化反过来提倡**减少域名数量**（域名收敛）。同理，雪碧图、CSS/JS 合并这些“**减少请求数**”的老优化，在 HTTP/2 下收益也大幅缩水。

### 6.3 队头阻塞的三种形态

“**队头阻塞 (Head-of-Line Blocking)**”这个词在不同层次含义不同：

[width(18,44,38)]

| 层次             | 现象                                                                         | 解决方式                                   |
| :--------------- | :--------------------------------------------------------------------------- | :----------------------------------------- |
| **应用层**       | HTTP/1.1 一条连接上的请求必须**串行**，前一个没响应，后面的只能等。          | HTTP/2 多路复用（一条连接并行多个流）。    |
| **传输层**       | TCP 保证有序，**一个包丢了，后面所有包都得等着重传**，哪怕它们是别的请求。   | HTTP/3（QUIC over UDP，流之间独立）。      |
| **浏览器调度层** | 同域并发数固定为 6，**超出部分在队列里等空闲连接**——严格说这是排队不是阻塞。 | 域名分片（HTTP/1.1）/ 多路复用（HTTP/2）。 |

## 7. 内容协商与数据编码

### 7.1 内容协商：同一份资源，不同客户端拿不同的东西

服务器可以针对同一个 URL 返回不同形式的内容，靠的是**请求头里的偏好声明**，这套机制叫**内容协商 (Content Negotiation)**：

- `Accept`：我要什么**类型**（`application/json`、`image/webp`）。
- `Accept-Encoding`：我能解压什么**压缩格式**（`gzip`、`br`）。
- `Accept-Language`：我要什么**语言**（`zh-CN`、`en`）。
- `Accept-Charset`：我要什么**字符集**（现在基本都是 UTF-8，已很少使用）。

服务器从中挑一个自己支持的，通过响应头 `Content-Type` / `Content-Encoding` / `Content-Language` **告诉客户端“**我给的是哪个**”**。这套应答式的协商叫**主动协商**，它有一个必须注意的副作用：**同一 URL 的响应会因人而异，缓存就被污染了**——所以响应必须带 `Vary` 头声明“**我是按哪些请求头变化的**”，例如 `Vary: Accept-Encoding`。这是缓存里一个非常隐蔽的坑（见 [前端缓存策略](/networkAndBrowsers/caching/frontendCacheStrategy)）。

### 7.2 数据编码：`Content-Length` 数的是压缩后的长度

协商定下“**给哪个版本**”之后，正文才真正上网络。这里最容易踩的坑在长度上：`Content-Encoding` 声明正文**被压过**（`gzip` / `br`），而 `Content-Length` 数的是**实际放在网络上的字节数**——压缩时它就是**压缩后**的大小，与解压出来的字符串长度无关。这个误解会以三种方式找上门：

- **进度条**：`fetch` 的 `response.body` 流里出来的是**解压后**的数据，而 `Content-Length` 是压缩后的字节数——两者口径不同，拿它当分母，进度条会在真正读完之前就冲过 100%。
- **流式响应**：正文边生成边发时事先不知道长度，此时用 `Transfer-Encoding: chunked` 取代 `Content-Length`——两者**互斥**，同时出现是协议错误。
- **缓存**：上一节说的 `Vary: Accept-Encoding` 正是为它服务的，否则压缩版与未压缩版会互相污染，这是缓存里最隐蔽的一类错。

## 8. 无状态与状态保持

HTTP 无状态，指的是**协议层面服务器不记账**。但业务上必须记账（你是谁、购物车里有什么），于是有了两条主流路线：

- **Cookie + Session（服务端有状态）**：服务器创建 Session 并把 `Session ID` 通过 `Set-Cookie` 下发，之后浏览器每次请求都自动带上 `Cookie: sessionId=...`。服务器靠 ID 查回自己的存储，就知道你是谁了。
- **Token（服务端无状态）**：服务器签发一个自包含的令牌（如 JWT），里面带着身份和过期时间，用签名防篡改。之后每个请求用 `Authorization: Bearer <token>` 带上它，服务器**验签即可，不用查存储**。代价是无法主动失效（只能等过期或用黑名单）。

两者的头部交互细节见 [HTTP 请求头与响应头](/networkAndBrowsers/http/headers)，存储位置、`SameSite`、容量限制与安全性对比见 [Cookie 与浏览器存储](/networkAndBrowsers/browser/cookieAndStorage) 和 [前端认证信息存放的取舍](/webSecurity/authStorageTradeoff)。

## 9. HTTP 缓存

HTTP 自带一套缓存机制，让第二次访问同一资源时**不必再走一遍网络**。核心只有两种模式：

- **强缓存**：`Cache-Control: max-age=3600`，一小时内直接用本地副本，**连请求都不发**。
- **协商缓存**：`Cache-Control: no-cache` + `ETag` / `Last-Modified`，每次发一个条件请求（`If-None-Match` / `If-Modified-Since`），服务器判断没变就回一个**没有正文的 `304`**，省的是带宽不是往返。

这块的完整机制、`no-cache` 与 `no-store` 的区别、以及“**发版后怎么让用户立刻看到新版本**”的实战方案，见 [浏览器缓存](/networkAndBrowsers/caching/browserCache) 与 [前端缓存策略](/networkAndBrowsers/caching/frontendCacheStrategy)。

## 10. HTTP 版本的演进

HTTP 协议的演进史，本质上是一场**与网络延迟（Latency）和底层传输瓶颈作斗争**的历史。

### 10.1 HTTP/0.9 与 HTTP/1.0：把 Web 跑起来

- **HTTP/0.9（1991）**：只有 `GET` 一个方法，没有头部，响应只能是 HTML。严格说它算不上一个正式协议，只是“**把文件里的内容发过去**”。
- **HTTP/1.0（1996）**：定义了现在这套报文结构（请求行 / 头部 / 空行 / 正文），引入了方法、状态码、`Content-Type`。最大问题是**一条 TCP 连接只能发一个请求，响应完立即断开**，每个资源都要付一次握手 + 慢启动的代价。

### 10.2 HTTP/1.1：长连接与它留下的问题

1997 年发布的 HTTP/1.1 是目前互联网上最经典的协议版本，奠定了现代 Web 的基础。（如今规范已由 2022 年的 RFC 9110～9112 重新整理，语义未变。）

- **持久连接 (Keep-Alive)**：默认开启。在一个 TCP 连接上可以发送和接收多个请求/响应，避免了 HTTP/1.0 时代每次请求都要经历 TCP 三次握手和四次挥手的巨大网络开销。
- **管道化 (Pipelining)**：规范允许客户端“**一次把 3 个请求全发出去，再按序读 3 个响应**”。但它仍然要求响应**按请求顺序返回**，所以**一个慢请求依然会卡住后面所有响应**，而且中间层代理支持得一团糟。因此**浏览器默认全部关闭了管道化**。
- **痛点：应用层队头阻塞**：即使不用管道化，一条连接同一时刻也只能处理一个请求。前一个请求因为服务器处理太慢或网络卡顿没回来，后面的请求就必须排队等待。
- **痛点：头部冗余**：每次请求都必须携带完整的头部（包括冗长的 `Cookie`、`User-Agent`），文本格式的头部无法压缩，在请求量大时占用了大量带宽。
- **痛点：一个域名 6 条连接**：为了绕开队头阻塞，浏览器只能靠多开连接，于是又回到了“**握手 × N + 慢启动 × N**”的老问题。

### 10.3 HTTP/2：多路复用与二进制分帧

为了解决 HTTP/1.1 的效率瓶颈，2015 年 HTTP/2 横空出世（RFC 7540，2022 年由 RFC 9113 取代）。它在**不改变 HTTP 语义**（Method、Status Code、Header 机制保持不变）的前提下，彻底重写了传输机制。

- **二进制分帧**：将 HTTP/1.x 的纯文本格式替换为更高效的二进制格式。报文被底层拆分为 `HEADERS 帧` 和 `DATA 帧`。
- **多路复用 (Multiplexing)**：这是 HTTP/2 的杀手锏。在一个 TCP 连接里可以划分出多个双向流通的“**流 (Stream)**”，每条流有自己的 ID。不同请求的帧可以**交错发送**，接收端再根据 Stream ID 重新组装。**这彻底解决了 HTTP 应用层面的队头阻塞问题**，也让域名分片、资源合并这些老优化失去了意义。
- **头部压缩 (HPACK)**：通讯双方各自在内存中维护一个“**头部字典**”（动态表 + 静态表）。对于重复的头部（`User-Agent`、`Cookie` 等），只需要发送对应的索引号即可；常用的字段名甚至被压进 2 个字节以内。
- **服务端推送 (Server Push)**：允许服务器在客户端没请求时就主动推送资源（如 CSS）。理想很美好，但缓存与优先级难以协调，实际收益有限，Chrome 已在 2022 年移除支持，**现在可以认为它已被淘汰**。
- **痛点：TCP 队头阻塞的残留**：HTTP/2 完美解决了应用层的排队问题，但它的底层仍然是 TCP。TCP 的机制是保证数据的**有序和可靠传输**，一旦发生丢包，TCP 层就会挂起所有后续的数据包等待重传。这意味着，在弱网环境下，HTTP/2 因为所有请求都压在同一个 TCP 连接里，其表现甚至可能不如建立了多个并发 TCP 连接的 HTTP/1.1。

### 10.4 HTTP/3 与 QUIC：彻底颠覆底层传输

为了解决 TCP 根深蒂固的队头阻塞问题，Google 牵头研发了 QUIC 协议，并在 2022 年以 RFC 9114 正式成为 HTTP/3 的标准。HTTP/3 做出了一个极其大胆的决定：**抛弃 TCP，拥抱 UDP**。

- **基于 UDP 的 QUIC 协议**：QUIC (Quick UDP Internet Connections) 建立在无连接、轻量级的 UDP 之上，并在**用户态代码**中重新实现了 TCP 的可靠性（重传机制、拥塞控制、流量控制）。放在用户态的另一个好处是：**升级协议不用换操作系统**——TCP 的改动要等内核和全网设备支持，QUIC 只在浏览器和服务器上更新即可。
- **彻底消除传输层队头阻塞**：在 QUIC 中，不同的流（Stream）之间是物理上真正独立的。如果流 A 发生丢包，系统只会要求重传流 A 的数据包，流 B 和流 C 依然可以畅通无阻地解析。
- **1-RTT 与 0-RTT 建连**：传统的 HTTPS (TCP + TLS) 需要 TCP 三次握手再加 TLS 握手，往往要 2～3 个 RTT 才能发出第一个业务请求。QUIC 把传输层握手和 TLS 1.3 加密握手**合并成一次**，首次连接只需 1-RTT；对于之前建立过连接的服务器，甚至可以 **0-RTT**——在第一个数据包里直接携带业务数据。
- **连接迁移 (Connection Migration)**：在 TCP 环境下，连接是基于【源 IP、源端口、目的 IP、目的端口】四元组绑定的。当你从 Wi-Fi 切换到 5G 移动网络时，IP 发生变化，TCP 连接必定断开重连。QUIC 引入了一个唯一的 **Connection ID (连接标识符)**，只要 ID 不变，即使 IP 或网络环境突然切换，连接依然可以保持活跃，实现了移动端的无缝平滑过渡。

> [!NOTE] 0-RTT 是有代价的
> 0-RTT 的数据包可以被攻击者**截获并原样重放**（重放攻击）。所以 0-RTT 只能安全地承载**幂等请求**——把首屏 HTML、静态资源放进去没问题，把“**下单**”“**支付**”这类非幂等请求放进去就是安全事故。

### 10.5 版本对比一览

[width(13,21,24,18,24)]

| 维度         | HTTP/1.0        | HTTP/1.1                    | HTTP/2                  | HTTP/3                      |
| :----------- | :-------------- | :-------------------------- | :---------------------- | :-------------------------- |
| **发布年份** | 1996            | 1997 → 2022 (RFC 9110 系列) | 2015 → 2022 (RFC 9113)  | 2022 (RFC 9114)             |
| **传输层**   | TCP             | TCP                         | TCP                     | **QUIC over UDP**           |
| **报文格式** | 文本            | 文本                        | **二进制分帧**          | 二进制分帧                  |
| **连接复用** | ❌ 每请求一连接 | ✅ 持久连接（串行）         | ✅✅ 多路复用（并行流） | ✅✅ 多路复用（流之间独立） |
| **队头阻塞** | 应用层 + 传输层 | 应用层 + 传输层             | **传输层残留**          | **基本消除**                |
| **头部压缩** | ❌              | ❌（纯文本）                | ✅ HPACK                | ✅ QPACK                    |

## 11. HTTP 头部字段速览

头部字段是 HTTP 里最庞杂也最常被问到的一块，这里只列最核心的几个，完整清单和细节见 [HTTP 请求头与响应头](/networkAndBrowsers/http/headers)：

- **`Host`：** 指定请求的服务器域名和端口号。HTTP/1.1 里唯一必填的头部，一台物理机靠它区分多个虚拟主机。
- **`User-Agent`：** 客户端的信息（操作系统、浏览器版本等）。
- **`Accept`：** 告诉服务器，客户端能够接收的数据格式（如 `text/html`、`application/json`）。
- **`Content-Type`：** 告诉接收方，正文里装的是什么类型的数据。
- **`Cookie` / `Set-Cookie`：** 用于客户端和服务器之间维持状态。
- **`Cache-Control`：** 指定请求和响应遵循的缓存机制。
- **`Authorization`：** 用于传递身份认证信息（如 Bearer Token）。
- **`Origin`：** 跨域请求时由浏览器自动携带，标记请求来源，是 CORS 判定的依据（见 [跨域](/webSecurity/cors)）。

## 12. 常见问题 (FAQ) 与面试题

### 12.1 HTTP 和 HTTPS 有什么区别？

主要区别在于**安全性**。

- **HTTP**: 超文本传输协议，数据以**明文**方式发送，不安全。默认端口 `80`。
- **HTTPS**: 安全套接字层超文本传输协议（HTTP over SSL/TLS），可以理解为“**HTTP 的安全版**”。它在 HTTP 之下增加了 SSL/TLS 协议层，对所有数据进行**加密**传输，确保了数据的机密性、完整性和身份验证。默认端口 `443`。

### 12.2 HTTP 是无状态的，那网站如何“记住”我？(Cookies 和 Sessions)

通过 Cookies 和 Sessions 技术。

- **服务器创建 Session**: 当你第一次访问网站（如登录），服务器会为你创建一个唯一的 **Session ID**，并把你的登录状态等信息存储在服务器上与这个 ID 关联。
- **服务器下发 Cookie**: 服务器通过响应头中的 `Set-Cookie`，将这个 Session ID 发送给你的浏览器。
- **浏览器存储 Cookie**: 浏览器会自动存储这个 Cookie（包含 Session ID）。
- **后续请求携带 Cookie**: 之后你对该网站的每一次请求，浏览器都会自动通过 `Cookie` 请求头，把这个 Session ID 带上。
- **服务器验证状态**: 服务器收到请求后，从 Cookie 中读取 Session ID，找到对应的 Session 数据，就知道你是谁、你的登录状态如何了。

> [!NOTE] 同源策略与 Cookie 的自动携带是一体两面
> “**自动携带**”既是便利也是风险：别的网站诱导浏览器发出的请求**也会带上你的 Cookie**，这就是 CSRF 攻击的原理。防御手段（`SameSite`、CSRF Token）见 [点击劫持与 SameSite](/webSecurity/clickJackingSameSite)。

### 12.3 什么是 RESTful API？它和 HTTP 是什么关系？

- **REST (Representational State Transfer)** 是一种**软件架构风格**，不是一种协议。它提倡用一种清晰、统一的方式来设计网络应用。RESTful API 就是遵循 REST 风格设计的 API。
- **关系**：REST **利用** HTTP 协议来工作。它充分利用了 HTTP 的方法（`GET`, `POST`, `PUT`, `DELETE`）来表达对资源的**增删改查 (CRUD)** 操作，使得 API 具有清晰的语义。

```markdown
GET /users 获取用户列表
POST /users 创建一个新用户
GET /users/123 获取 ID 为 123 的用户
PUT /users/123 替换 ID 为 123 的用户信息（全量）
PATCH /users/123 局部修改 ID 为 123 的用户
DELETE /users/123 删除 ID 为 123 的用户
```

REST、GraphQL、RPC 三种风格的具体对比与选型见 [API 风格](/networkAndBrowsers/api/apiStyles)。

> [!TIP] 为什么“用 POST 也能实现一切，还要守着 REST”
> 因为 REST 把**语义放进了协议本身**：正因为它声明了 `GET` 是安全的、`PUT` 是幂等的，浏览器才能放心缓存、网关才能安全重试、CDN 才能自动命中。用 `POST /deleteUser?id=1` 换来的灵活，代价是所有这些**基础设施级的自动能力全部失效**。

### 12.4 HTTP/1.0, HTTP/1.1, HTTP/2, HTTP/3 的主要区别是什么？

- **HTTP/1.0 (1996)**: 最基础的版本，每个 TCP 连接只能发送一个请求，完成后立即关闭。
- **HTTP/1.1 (1997)**: 引入了**持久连接 (Keep-Alive)**，一个 TCP 连接可以复用发送多个请求，避免了频繁建连的开销。但存在**队头阻塞 (Head-of-line blocking)** 问题，即一个请求阻塞了，后续请求必须等待。
- **HTTP/2 (2015)**: 这是一个重大升级。
  - **二进制协议**: 不再是纯文本，解析效率更高。
  - **多路复用 (Multiplexing)**: 在一个 TCP 连接上，可以同时发送和接收多个请求/响应，彻底解决了**应用层**队头阻塞问题。
  - **头部压缩 (HPACK)**: 压缩请求和响应的头部，减少传输体积。
  - **遗留问题**: 底层还是 TCP，一旦丢包，**所有流**都得等重传。
- **HTTP/3 (2022)**: 更进一步的革命。
  - **基于 QUIC 协议**: QUIC 建在 **UDP** 之上，而不是 TCP。
  - **解决了传输层队头阻塞**: 一个流的丢包不会影响其他流。
  - **更快的建连**: 1-RTT / 0-RTT，且支持连接迁移。
  - **为什么是 UDP 而不是改 TCP**: TCP 的实现**焊死在操作系统内核里**，动它就得同时更新全世界的内核和沿途所有中间设备；QUIC 把可靠性、拥塞控制搬到**用户态的应用代码**里，协议就能跟着浏览器/服务端一起升级——UDP 在这里只是“**一个不带历史包袱的信使**”。

### 12.5 幂等性对前端有什么用？

幂等性不是一个学术概念，它直接决定了两件事：

- **能不能自动重试**。网络超时并不代表服务端没处理——可能是响应在回来的路上丢了。此时重试一个幂等的 `GET`/`PUT`/`DELETE` 是安全的，重试一个 `POST` 下单则可能**创建两笔订单**。这就是下单、支付这类接口要额外传**幂等键 (Idempotency-Key)** 的原因（见 [请求治理](/networkAndBrowsers/api/requestGovernance)）。
- **能不能防重复提交**。用户狂点“**提交**”按钮、或者弱网下请求被浏览器自动重发，只有幂等的方法才扛得住。所以**后端接口该幂等就幂等，前端该禁用按钮就禁用按钮**，两者不是替代关系。

### 12.6 URL 长度和 HTTP 报文有大小限制吗？

- **协议层面**：都没有硬性上限。HTTP 规范没有规定 URL 或头部的最大长度。
- **实现层面**：处处是限制。URL 上，IE 的经典限制是 2083 字符，而**服务器（Nginx `large_client_header_buffers`、Tomcat `maxHttpHeaderSize`）通常只留 8KB，超了直接 `414`**；头部同理；正文则受 `client_max_body_size` 之类的配置限制，超了返回 `413`。
- **实践结论**：**URL 用来传标识和少量参数，大数据放正文**。`GET` 携带超长参数（比如把几百个 ID 拼进查询串）是一个典型的线上事故来源。

### 12.7 为什么 HTTP/2 之后“优化”的方向反过来了？

因为 HTTP/1.1 时代的优化大都是**为了绕开「一个域名 6 条连接 + 请求串行」**，而 HTTP/2 把这些前提都取消了：

[width(23,26,51)]

| 老优化（HTTP/1.1）    | 为什么当时有效          | 在 HTTP/2 下的变化                                   |
| :-------------------- | :---------------------- | :--------------------------------------------------- |
| **域名分片**          | 突破单域名 6 连接的限制 | **负优化**：多条连接就多几次 DNS + TCP + TLS 握手。  |
| **雪碧图 / 资源合并** | 减少请求数，减少排队    | 收益大幅下降，且影响缓存粒度（改一个图标全量失效）。 |
| **内联小资源**        | 省掉一次请求            | 收益下降，且不利于缓存与 CSP。                       |
| **管道化**            | 试图并行发请求          | 从来没被浏览器默认启用过，已被多路复用取代。         |

所以现代前端的优化重点，从“**减少请求数**”转向了“**减小单次传输体积 + 减少请求的往返次数**”：HTTP/2 与 HTTP/3、缓存策略、CDN、以及“**关键资源优先**”（`preload` / `fetchpriority`）。

### 12.8 从前端视角看，一次请求要经过哪些环节？

排查线上问题时，把每个环节都想一遍，通常能定位到问题所在：

1. **URL → IP**：[DNS 解析](/networkAndBrowsers/fundamentals/dns)（可能是 CDN 返回的就近节点）。
2. **建连**：[TCP 三次握手](/networkAndBrowsers/transport/tcp)；HTTPS 还要 [TLS 握手](/networkAndBrowsers/http/https)；有连接复用则跳过。
3. **发请求**：浏览器加上 `Cookie`、`Origin`、`Referer` 等头部；跨域且非简单请求时会先发一次 `OPTIONS` 预检（见 [跨域](/webSecurity/cors)）。
4. **到服务器**：可能被 [CDN](/networkAndBrowsers/fundamentals/cdn) 或 Nginx 截住，命中缓存就直接返回；否则转发给后端服务。
5. **服务端处理**：查缓存、查库、算业务。
6. **回响应**：状态码 + 头部 + 正文；大响应可能被 `gzip`/`br` 压缩。
7. **浏览器落盘**：按 `Cache-Control` / `ETag` 决定要不要存缓存。
8. **交给 JS**：`fetch` 的 Promise 兑现，JS 开始处理数据。
