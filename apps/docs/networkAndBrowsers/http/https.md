# HTTPS 协议

**HTTPS**（HyperText Transfer Protocol Secure，超文本传输安全协议）并不是一个全新的协议，而是 **HTTP + SSL/TLS** 的组合。

简单来说，HTTP 协议的数据是明文传输的，而 HTTPS 在 HTTP 的应用层和 TCP 的传输层之间，加入了一个安全套接字层（SSL/TLS），负责对传输的数据进行加密、身份验证和完整性保护。

- **默认端口：** HTTPS 的默认端口是 `443`（HTTP 是 `80`）。
- **网址前缀：** URL 以 `https://` 开头。

**一句话理解**：HTTPS 要同时解决三个问题——**别人看不到**（加密）、**别人改不了**（完整性）、**对面真的是它**（身份认证）。前两个靠加密算法，第三个靠**数字证书**；而 HTTPS 之所以不全程用“**安全但慢**”的非对称加密，是因为它只把非对称加密用在**交换钥匙**这一步，真正的大批量数据用**快得多的对称加密**来传。

> [!TIP] 相关阅读
> 明文版本见 [HTTP 协议](/networkAndBrowsers/http/http)；TLS 跑在 [TCP 协议](/networkAndBrowsers/transport/tcp) 之上（HTTP/3 则内建在 QUIC 里，见 [HTTP 协议 10.4](/networkAndBrowsers/http/http)）；握手时用到的头部（`Host`、`SNI`）见 [HTTP 请求头与响应头](/networkAndBrowsers/http/headers)；证书与加密在浏览器里的落地（HSTS、Secure Cookie、混合内容）见 [CSP、SRI 与 HSTS](/webSecurity/cspSriHsts) 与 [Cookie 与浏览器存储](/networkAndBrowsers/browser/cookieAndStorage)。

## 1. 什么是 HTTPS？

HTTPS 是在 HTTP 和 TCP 之间夹了一层 **TLS（Transport Layer Security）**：

```markdown
┌──────────────────────┐ ┌──────────────────────┐
│ 应用层 HTTP 报文 │ │ 应用层 HTTP 报文 │
└──────────────────────┘ ├──────────────────────┤
│ 安全层 TLS │ ← HTTPS 多出来的这一层
┌──────────────────────┐ ├──────────────────────┤
│ 传输层 TCP │ │ 传输层 TCP │
└──────────────────────┘ └──────────────────────┘
HTTP HTTPS
```

[width(13,23,64)]

| 目标         | 手段              | 对抗的攻击                               |
| :----------- | :---------------- | :--------------------------------------- |
| **机密性**   | 混合加密          | 窃听：抓包、公共 WiFi、运营商链路。      |
| **完整性**   | 消息认证码（MAC） | 篡改：中间人往页面里插广告、改转账账号。 |
| **身份认证** | 数字证书          | 伪装：钓鱼网站冒充银行。                 |

> [!NOTE] 一个常见的误解：HTTPS 不是“加密版的 HTTP”
> HTTPS **只改传输，不改语义**。方法、状态码、头部字段一个都没变，`fetch` 的用法也完全一样。所以 [HTTP 协议](/networkAndBrowsers/http/http) 里学的所有东西在 HTTPS 下依然成立——只是字节在网线上跑的时候被裹了一层密文。

## 2. 为什么需要 HTTPS？（HTTP 的三大风险）

在没有 HTTPS 之前，互联网上的数据几乎都是“**裸奔**”的，这就带来了致命的安全问题：

- **窃听风险 (Eavesdropping)**：黑客可以在数据传输的任何节点（如公共 WiFi、运营商路由器）截获你的账号密码。
- **篡改风险 (Tampering)**：黑客可以修改你收到的数据，比如在网页中插入广告，或者将你转账的账号改成他自己的（中间人攻击）。
- **伪装风险 (Pretending)**：你无法确认你访问的银行网站是不是真的银行，黑客可以搭建一个一模一样的“**钓鱼网站**”骗取你的信息。

**HTTPS 的三大防线** 就是专门对付这三个风险的：

- **加密 (Encryption)** -> 防窃听
- **数据签名 (Data Integrity)** -> 防篡改
- **数字证书 (Digital Certificate)** -> 防伪装

> [!NOTE] 顺序不能乱：先认证，再加密
> 很多人以为“**加密了就等于安全了**”。其实**加密和身份认证是两件独立的事**：如果加密用的是一个冒牌货给的公钥，那么密文只有那个冒牌货能解开——**你等于是在安全地跟骗子说话**。所以 TLS 握手里的第一步永远是**验证证书**，验证不通过就不会继续。

## 3. HTTPS 的核心原理：混合加密机制

HTTPS 为了同时兼顾**安全性**和**性能**，采用了一种非常巧妙的“**混合加密**”机制。要理解它，必须先懂两种基础加密方式：

### 3.1 对称加密 (Symmetric Encryption)

- **原理**：加密和解密使用**同一把钥匙（密钥）**。

![对称加密：客户端用共享密钥把数据加密，服务端用同一把共享密钥解密](/img/httpsSecond.jpg)

- **特点**：加密速度极快，适合加密大量数据。
- **致命弱点**：如何安全地把这把“**钥匙**”交给对方？如果黑客在传输钥匙的过程中截获了它，加密就形同虚设了。

![共享密钥在传递过程中被中间人截获，之后双方的所有通信都能被中间人解开](/img/httpsThird.jpg)

现代 HTTPS 用的对称加密算法是 **AES**（常见是 AES-128-GCM / AES-256-GCM）或 **ChaCha20-Poly1305**，它们不只是“**加密**”，还自带完整性校验（这类算法叫 **AEAD**，认证加密）——**改了密文任何一个字节，解密方都会直接失败而不是得到错误的数据**。

### 3.2 非对称加密 (Asymmetric Encryption)

- **原理**：拥有**两把钥匙**：一把公钥（Public Key），一把私钥（Private Key）。
  - **公钥**是公开的，任何人都可以获取。
  - **私钥**是自己死死捂住的，绝对不外传。
  - **核心法则**：用公钥加密的数据，**只有**对应的私钥才能解密。

![非对称加密：客户端用服务端的公钥加密数据，只有服务端手里的私钥能解开](/img/httpsFourth.jpg)

- **特点**：解决了密钥分发的问题，非常安全。
- **致命弱点**：加密/解密速度极慢（比对称加密慢几百倍甚至上千倍），只适合加密非常少量的数据。

![非对称加密的公钥在传递过程中被掉包，客户端实际上在用中间人的公钥加密](/img/httpsFifth.jpg)

### 3.3 数字签名：非对称加密的另一个方向

非对称加密还藏着第二种用法，它是 HTTPS 里另一根支柱——**数字签名**：

[width(9,25,66)]

| 用法     | 谁用钥匙            | 作用                     |
| :------- | :------------------ | :----------------------- |
| **加密** | 公钥加密 → 私钥解密 | 只有接收方能看懂内容。   |
| **签名** | 私钥签名 → 公钥验签 | 只有私钥持有者能发出它。 |

签名的过程是：**先对内容算一个摘要（哈希），再用私钥加密这个摘要**。校验方用公钥解出摘要，自己再算一遍内容摘要，两者一致就说明“**内容没被改过**”且“**确实是私钥持有者发的**”。

这正好补上光有加密挡不住 **“公钥被掉包”** 的漏洞（因为你无法确认手上的公钥是谁的），而数字证书就是“**用签名来担保公钥归属**”的东西。

### 3.4 HTTPS 的混合加密（扬长避短）

- **非对称加密用于“交换钥匙”：** 客户端和服务器在正式通信前，利用非对称加密（安全但慢），安全地协商并传递一把**随机生成的“对称密钥（会话密钥）”**。
- **对称加密用于“正式通信”：** 钥匙交换成功后，双方就用这把“**对称密钥**”来加密真正要传输的大量数据（速度快）。

简单来说：**用非对称加密来加密“**对称密钥**”，用对称密钥来加密“实际数据”。**

## 4. 防伪装的利器：数字证书与 CA 机构

### 4.1 问题的起点：中间人攻击 (MITM)

即使有了混合加密，还面临一个问题：黑客可以冒充服务器，发给你一个**假的公钥**。当你用这个假公钥加密了数据，黑客用自己的私钥就能解开了。我们假设不存在认证机构，任何人都可以制作证书，这带来的安全风险便是经典的 **中间人攻击 (MITM)** 问题。

![HTTPS 完整流程中中间人截获请求并用伪造的公钥冒充服务端](/img/middlePerson.png)

![中间人拿到服务端的公钥后，用服务端公钥加密自己伪造的数据，服务端解密后拿到的是虚假数据](/img/httpsSixth.jpg)

上图的攻击链是这样的：**中间人同时和两端建连**——对客户端，它出示自己的“**证书**”（或转发服务端的证书但自己截留密钥）；对服务端，它扮演一个普通客户端。于是两段信道各有一把密钥，中间人成了“**翻译官**”，**双方都以为自己在跟对方直接说话**。

### 4.2 证书里到底有什么

为了解决“**我是我**”的问题，HTTPS 引入了 **CA 机构（Certificate Authority，证书颁发机构）** 和 **数字证书**。

- **CA 的作用**：CA 就像互联网世界的“**公安局**”。网站站长需要把自己的公钥和身份信息提交给 CA，CA 审核通过后，会用 CA 自己的私钥对这些信息进行**数字签名**，打包成一个“**数字证书**”发给网站。
- **浏览器如何验证**：世界上权威的 CA 机构的公钥（根证书），早就预装在了你的操作系统和浏览器中。当你访问网站时，网站会出示它的证书。你的浏览器会用内置的 CA 公钥去验证这个证书的数字签名。如果验证通过，就证明这个网站的公钥是真实的，不是黑客伪造的。

一张证书的核心内容：

[width(19,81)]

| 字段              | 含义                                                                                                 |
| :---------------- | :--------------------------------------------------------------------------------------------------- |
| **Subject**       | 证书持有者（域名、组织名）。                                                                         |
| **Issuer**        | 签发这张证书的 CA。                                                                                  |
| **Validity**      | 生效 / 过期时间。过期的证书浏览器会直接报错。                                                        |
| **Public Key**    | **这张证书真正要担保的东西**——服务端的公钥。                                                         |
| **SAN**           | 这张证书覆盖哪些域名（`Subject Alternative Name`）。现在的证书**只看这里**，不看旧的 `Common Name`。 |
| **Serial Number** | 证书的唯一编号，吊销时用它定位。                                                                     |
| **Signature**     | CA 用自己私钥对整个证书内容做的签名。                                                                |

### 4.3 证书链与信任锚

现实中，**根 CA 不会直接签发网站证书**，中间隔了一层：

```markdown
根证书 (Root CA) ← 预装在系统/浏览器的信任库里，私钥离线保管
└── 中间证书 (Intermediate CA) ← 由根签发，日常用来签网站证书
└── 服务器证书 (Leaf) ← 网站自己的证书
```

验证时是**自下而上逐级验签**，直到验到一个系统信任的根证书为止，这条链就通了。**为什么要多一层中间证书？** 因为根证书的私钥必须离线保管、极度安全，不能天天拿出来签发；用中间证书分担签发工作，一旦中间证书泄露，只需吊销它而不必换掉整个根。

> [!NOTE] 部署 HTTPS 时最常见的坑：少了中间证书
> 服务器必须把**服务器证书 + 中间证书**一起按顺序发给客户端（叫 fullchain）。只发服务器证书，浏览器可能因为找不到中间证书而报 `unable to verify the first certificate`——**在部分浏览器里能打开、在手机上却打不开**，就是这么来的。

### 4.4 证书的三种类型

[width(32,30,38)]

| 类型                             | 验证内容                     | 典型来源                          |
| :------------------------------- | :--------------------------- | :-------------------------------- |
| **DV (Domain Validation)**       | 只验证你**拥有这个域名**。   | Let's Encrypt，免费、可自动续期。 |
| **OV (Organization Validation)** | 额外验证**组织的真实身份**。 | 付费，适合企业站。                |
| **EV (Extended Validation)**     | 更严格的线下审核。           | 付费，价格最高。                  |

### 4.5 证书吊销：签错了怎么办

证书有固定的有效期（现在主流是 90 天 ~ 1 年），但如果**私钥提前泄露**或**域名易主**，必须让证书立刻失效。三种机制：

[width(20,34,46)]

| 机制              | 做法                                                        | 优缺点                                                                     |
| :---------------- | :---------------------------------------------------------- | :------------------------------------------------------------------------- |
| **CRL**           | CA 定期发布“**已吊销证书列表**”，浏览器下载整个列表。       | 列表越来越大，下载成本高，已基本不用。                                     |
| **OCSP**          | 浏览器拿着证书编号**实时问 CA**“**这张还有效吗**”。         | 实时准确，但多一次往返、慢，而且**询问行为本身会泄露用户访问了哪个网站**。 |
| **OCSP Stapling** | **服务器**定期代问 CA，把带签名的结果随握手一起发给浏览器。 | 又快又不泄露隐私，是现在的推荐做法。                                       |

### 4.6 SNI：一台服务器怎么放多张证书

一个 IP 上跑着 `a.com` 和 `b.com` 两个站点，客户端在 TLS 握手时还没发 HTTP 请求，服务器怎么知道该出示哪张证书？

答案是 **SNI (Server Name Indication)**：客户端在握手的第一个消息（ClientHello）里就把**目标域名**带上（`server_name`）。没有 SNI，一个 IP 就只能配一张证书——这是早年“**HTTPS 站需要独立 IP**”的原因。

## 5. HTTPS 的建立过程（TLS 握手，TLS Handshake）

这发生在 TCP 三次握手**之后**，真正的 HTTP 数据传输**之前**。

### 5.1 经典握手流程（RSA 密钥交换）

1.  **Client Hello (客户端打招呼)**：
    - 客户端向服务器发送请求，包含：客户端支持的 TLS 版本、支持的加密算法套件（Cipher Suites）、一个**客户端生成的随机数 (Random1)**，以及 **SNI（目标域名）**。
2.  **Server Hello (服务器回应)**：
    - 服务器从中选择一个自己也支持的加密算法。
    - 生成一个**服务器端的随机数 (Random2)** 并发送给客户端。
    - **最重要的一步**：服务器将自己的 **数字证书（包含公钥）** 发送给客户端。
3.  **Certificate Verification (客户端验证证书)**：
    - 浏览器验证证书的合法性（是否过期、CA 是否受信任、**域名是否和 SAN 匹配**、是否被吊销）。如果验证失败，浏览器会弹出一个大大的红字警告（“**您的连接不是私密连接**”）。
4.  **Pre-master Secret (生成预主密钥)**：
    - 如果证书验证通过，客户端会生成**第三个随机数 (Pre-master Secret)**。
    - 客户端用证书里的**服务器公钥**对这个 Pre-master Secret 进行加密，并发送给服务器。
5.  **生成会话密钥 (Session Key)**：
    - 服务器收到密文后，用自己的**私钥**解密，得到 Pre-master Secret。
    - **奇迹发生**：现在客户端和服务器手里都有了三个相同的随机数（Random1 + Random2 + Pre-master Secret）。双方利用这三个随机数，通过相同的算法，**各自在本地计算出了一把相同的“对称密钥（会话密钥）”**。
6.  **加密通信开始**：
    - 钥匙协商完毕，双方互相发送一个 `Finished` 消息，表示握手结束。
    - 之后所有的 HTTP 请求和响应，都将使用这把协商好的**会话密钥进行对称加密**传输。

> [!NOTE] 为什么要有“三个随机数”？
> 因为随机数只要有一方能**独立地贡献不可预测的部分**，最终密钥就不可预测。`Random1` 防服务器伪造、`Random2` 防客户端伪造、`Pre-master` 由客户端提供并受公钥保护防止窃听——**任何一方都无法单方面决定密钥**。这是 TLS 设计里很关键的一个思路：**不要相信任何一方的随机性**。

![HTTPS 完整流程：先验证证书，再用非对称加密协商出随机数，最后用对称加密传输全部内容](/img/https.webp)

### 5.2 现代握手：ECDHE 与前向保密

“**用服务器公钥加密随机数**”的做法叫 **RSA 密钥交换**。它有一个致命缺陷：**密钥协商完全依赖服务器私钥**。也就是说——

> 如果攻击者今天抓下了全部流量，三年后弄到了服务器的私钥（服务器被入侵、备份泄露、证书私钥被卖掉），**他就能把三年前的流量全部解密**。

这就是“**先存后解 (harvest now, decrypt later)**”攻击。解决办法是换成 **ECDHE（椭圆曲线 Diffie-Hellman 临时密钥交换）**：

- 双方各自**临时生成一对密钥**，交换公开部分，各自算出同一个共享秘密；**临时私钥用完即丢**。
- 服务器的长期私钥只用来**签名**（证明“**我是我**”），**不再参与密钥的生成**。
- 于是长期私钥泄露也解不开历史流量——这个性质叫**前向保密 (Forward Secrecy / PFS)**。

**现代 TLS 1.2 的正确配置和 TLS 1.3 都强制使用这类前向保密的密钥交换**，RSA 密钥交换已被淘汰。

### 5.3 TLS 1.3：把握手压缩到 1-RTT

TLS 1.3（RFC 8446，2018）是一次大改，除了性能还砍掉了大量历史包袱：

[width(24,76)]

| 变化                   | 说明                                                                        |
| :--------------------- | :-------------------------------------------------------------------------- |
| **握手压缩到 1-RTT**   | 客户端在第一个消息里就带上密钥交换参数，省掉了一个来回。                    |
| **强制前向保密**       | 废除了 RSA 密钥交换，只保留 ECDHE/DHE。                                     |
| **只留 AEAD 加密算法** | 废除了 CBC 模式、RC4、以及不带认证的加密方式（这些都是历史漏洞高发区）。    |
| **握手本身被加密**     | 证书内容从 ServerHello 之后就开始加密传输，中间人连“用的什么证书”都看不到。 |
| **废除压缩与重协商**   | 它们都是历史攻击（CRIME、重协商攻击）的来源。                               |

### 5.4 会话复用与 0-RTT

每一次访问都做一次完整握手(还要做非对称加密运算)太贵了，所以 TLS 允许**把上一次协商的结果存起来复用**：

- **TLS 1.2 时代**：`Session ID`（服务器存）或 `Session Ticket`（把加密的会话信息交给客户端存）。
- **TLS 1.3**：统一为 **PSK (Pre-Shared Key)** 模式，恢复会话只需 0-RTT 或 1-RTT。
- **0-RTT（也叫 Early Data）**：如果之前连过，客户端可以在**第一个数据包里直接带上业务请求**，连握手都省了——这是“**秒开**”的关键。

> [!NOTE] 0-RTT 有重放风险
> 0-RTT 的数据可以被攻击者**截获后原样重发**，所以它**只能用于幂等请求**。把静态资源、首屏 HTML 放进 0-RTT 是安全的；把“**下单**”“**支付**”放进去就是安全事故。这也是为什么浏览器和服务器默认对 0-RTT 都比较克制。

## 6. HTTP 与 HTTPS 的核心对比

[width(14,19,67)]

| 维度           | HTTP                          | HTTPS                                                             |
| -------------- | ----------------------------- | ----------------------------------------------------------------- |
| **全称**       | 超文本传输协议                | 超文本传输安全协议                                                |
| **安全性**     | 明文传输，极不安全            | 密文传输，极度安全                                                |
| **端口号**     | `80`                          | `443`                                                             |
| **连接速度**   | 快（仅需 TCP 三次握手）       | 较慢（TCP 三次握手 + TLS 握手）                                   |
| **CPU 开销**   | 几乎没有                      | 握手期有非对称运算开销，数据传输期靠硬件 AES 加速，开销很小。     |
| **证书成本**   | 免费                          | 通常需要向 CA 机构付费申请（也有 Let's Encrypt 等免费方案）       |
| **SEO 表现**   | 一般                          | 搜索引擎（如 Google, Baidu）会优先收录和提升 HTTPS 网站的排名     |
| **浏览器态度** | Chrome 会明确标记“**不安全**” | Chrome 地址栏不再显示 `https://` 前缀，但“**不安全**”会红字警告。 |

> [!NOTE] “HTTPS 更慢”这个结论已经过时了
> 在 HTTP/2、TLS 1.3、会话复用、OCSP Stapling 都有了的今天，一次 HTTPS 请求相比 HTTP 多出的成本通常只有**首次连接的 1 个 RTT 和可忽略的 CPU 开销**。而 HTTP/2 和 HTTP/3 在浏览器上**几乎只在 HTTPS 下启用**，实际结果是：**上 HTTPS 之后网站往往更快**。

## 7. 前端能碰到的 HTTPS

HTTPS 不只是运维的事，它在浏览器里有一堆硬性规则，会直接决定某些功能能不能用。

### 7.1 HTTPS 的性能优化清单

[width(34,66)]

| 手段                              | 作用                                                                                                       |
| :-------------------------------- | :--------------------------------------------------------------------------------------------------------- |
| **会话复用 / Session Ticket**     | 再次连接时省掉完整握手，甚至 0-RTT。                                                                       |
| **TLS 1.3**                       | 握手从 2-RTT 降到 1-RTT，并砍掉不安全的算法。                                                              |
| **OCSP Stapling**                 | 服务器代查吊销状态，省掉浏览器那次额外的往返。                                                             |
| **CDN 边缘终止**                  | 在最靠近用户的节点完成 TLS 握手，把长链路留给 CDN 自己（见 [CDN](/networkAndBrowsers/fundamentals/cdn)）。 |
| **`preconnect` / `dns-prefetch`** | 提前完成 DNS 和 TLS 握手，让首个请求少等一个 RTT。                                                         |

### 7.2 混合内容 (Mixed Content)：HTTPS 页面里的 HTTP 资源

如果 HTTPS 页面里引用了 HTTP 的资源，安全上下文就被破坏了（攻击者可以篡改这段明文资源，往页面里注入脚本）。浏览器按危险程度处理：

- **主动混合内容**（`<script>`、`<iframe>`、`fetch`/XHR、CSS）——**直接阻止**，页面功能会直接坏掉。
- **被动混合内容**（`<img>`、`<video>`、`<audio>`）——历史上是警告，**现代浏览器已直接把请求升级成 HTTPS**，升不了就加载失败。

排查方法：开发者工具 Console 里搜 `Mixed Content`，或者用 CSP 的 `upgrade-insecure-requests` 一次性升级所有请求。**这类问题的典型症状是“本地开发一切正常，上线后某些图片或接口挂了”。**

### 7.3 Secure Context：没有 HTTPS 就用不了的 API

浏览器把一批**高权限 API** 限制在安全上下文里，只有 HTTPS（和 `localhost`）才允许调用：

- **Service Worker / PWA 离线缓存**（见 [Service Worker 与 PWA](/networkAndBrowsers/caching/serviceWorkerPwa)）
- **Geolocation** 定位
- **getUserMedia**（摄像头 / 麦克风）、`getDisplayMedia`（屏幕共享）
- **Web Crypto API**、**WebAuthn / Passkey**（见 [WebAuthn 与 Passkey](/webSecurity/webauthnPasskey)）
- **Push API**、**Clipboard API**（部分）、**Web Bluetooth / USB / Serial**
- **HTTP/2、HTTP/3 在浏览器上基本也只走 HTTPS**

### 7.4 抓包工具为什么能解密 HTTPS？

Charles、Fiddler、Charles 这类工具能看到明文，靠的不是“**破解了 TLS**”，而是**合法的中间人**：

1. 工具生成一张**自己的根证书**，让你把它装进系统/浏览器的信任库。
2. 你连它时，它对客户端出示**用这张根证书签的假证书**（域名也是你要访问的那个域名，所以校验能过）。
3. 它同时对真实服务器发起另一条 TLS 连接，用真实证书。
4. 于是它成了中间“**翻译官**”——**两段各自加密，中间明文可见**。

这正好从反面证明了 HTTPS 的安全性：**能解密的前提是“你在设备上主动信任了攻击者的根证书”**。这也是为什么不能随便安装来源不明的根证书、也不该在手机上忽略证书警告继续访问。

### 7.5 HSTS：让浏览器只走 HTTPS

如果用户第一次访问走的是 `http://`，服务器需要回一个 `301` 跳到 HTTPS——而这次**明文跳转本身是可以被劫持的**（攻击者可以把你导向一个假的 HTTPS 站）。**HSTS (HTTP Strict Transport Security)** 就是让浏览器记住“**这个域名以后只准用 HTTPS**”：

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

- `max-age`：记多久（秒）。设小了等于没设。
- `includeSubDomains`：子域名一并生效。
- `preload`：申请加入浏览器的**内置预加载列表**，让**第一次访问**就强制 HTTPS（这是唯一能防住首次明文劫持的办法）。

上线 HSTS 要格外小心：`max-age` 设成一年之后，**在过期前这个域名就真的只能用 HTTPS 了**——证书一旦出问题，用户连“**点继续访问**”的机会都没有。详见 [CSP、SRI 与 HSTS](/webSecurity/cspSriHsts)。

## 8. 常见问题 (FAQ) 与面试题

### 8.1 HTTP 和 HTTPS 的根本区别是什么？

- **安全性**：HTTP 明文传输，不安全；HTTPS 是加密传输，安全。
- **端口**：HTTP 默认使用 80 端口；HTTPS 默认使用 443 端口。
- **性能/耗时**：HTTPS 因为需要进行 TLS 握手和加解密计算，建立连接的过程比 HTTP 慢，对服务器 CPU 资源的消耗也略大。
- **费用**：HTTPS 需要向 CA 机构申请数字证书，高级别的证书通常需要付费。
- **本质**：**HTTPS = HTTP + TLS**，是同一个协议的两种传输方式，HTTP 的语义完全不变。

### 8.2 为什么 HTTPS 不全程使用非对称加密？

- **性能极差**。非对称加密（如 RSA）的加解密算法极其复杂，非常耗费 CPU 资源，速度极慢。如果网页上的每一张图片、每一段文字都用非对称加密，服务器会崩溃，用户的网页加载速度也会慢到无法忍受。
- 所以 HTTPS 只用非对称加密做两件“**量很小**”的事：**验证身份（证书签名）** 和 **协商出会话密钥**，剩下的大量数据交给对称加密。

### 8.3 如果 CA 机构被黑客攻破了怎么办？

- 这是一个系统性的灾难（虽然发生概率极低）。如果黑客拿到了 CA 的私钥，他就可以随意签发伪造的合法证书。一旦发现这种情况，操作系统和浏览器厂商会立即将该 CA 从信任列表中**吊销（Revoke）**，所有由该 CA 签发的证书将瞬间失效。历史上有过几次类似事件（如 DigiNotar 事件），导致该 CA 公司直接破产。
- 这也是“**中间证书**”存在的另一个意义：**万一出事，损失可以控制在一个中间证书的范围内**。

### 8.4 我自己用 OpenSSL 生成一个证书（自签发证书）可以用吗？

- **可以使用，但不受信任**。你可以自己生成公私钥和证书，用来加密数据是没问题的。但是，因为你不是权威的 CA 机构（浏览器不认识你），当用户访问你的网站时，浏览器依然会弹出大红色的安全警告。这种证书通常只用于公司内部的测试环境。
- 换个角度想：**“浏览器不认识”正是安全机制在正常工作**——它无法区分“**你自签的测试证书**”和“**攻击者的假证书**”，所以只能一律拒绝。抓包工具能让浏览器接受，是因为它把根证书装进了你的信任库。

### 8.5 什么是中间人攻击（MITM），HTTPS 能防住吗？

- **原理**：黑客在你和服务器之间拦截请求，对你伪装成服务器，对服务器伪装成你。
- **HTTPS 可以完美防御**，关键在于**数字证书的验证机制**。如果黑客拦截了请求并给了你一个他自己伪造的公钥（证书），由于这个证书没有经过权威 CA 签名，你的浏览器在验证时就会报错并阻止连接，从而粉碎了攻击。
- **但有两个前提**：① 用户没有点击“**继续访问**”忽略警告；② 设备上没有装上攻击者的根证书。这两点任意一个被攻破，MITM 就会成功——所以**看到证书警告时不要继续**，**不要安装来源不明的根证书**。

### 8.6 SSL 和 TLS 到底是什么关系？

- **SSL (Secure Sockets Layer)**：是最早由网景公司开发的安全协议，到了 3.0 版本后被标准化。
- **TLS (Transport Layer Security)**：是 SSL 的继任者和升级版。SSL 3.0 被标准化后，更名为 TLS 1.0。现在互联网上广泛使用的是 TLS 1.2 和 TLS 1.3，早期的 SSL 版本因为存在严重漏洞已经被完全废弃。大家常说的“**配置 SSL 证书**”，实际上配置的都是 TLS。
- 实践上要知道的版本节点：**TLS 1.0 / 1.1 已在 2021 年被 RFC 8996 正式宣告废弃**，主流浏览器会直接拒绝连接。所以“**支持哪些 TLS 版本**”这件事现在的正确答案只有 **TLS 1.2 和 1.3**。

### 8.7 前向保密 (Forward Secrecy) 是什么，为什么重要？

- **含义**：**服务器的长期私钥泄露，也不会导致此前的通信被解密**。
- **怎么做到**：每次连接都用一次性的 ECDHE 临时密钥来协商会话密钥，临时私钥用完即毁，长期私钥只用于签名。
- **为什么重要**：攻击者可以“**今天先抓包存起来，以后弄到私钥再慢慢解**”。没有前向保密，一台服务器三年后的入侵事故会让三年前的所有用户数据一起泄露；有了它，历史流量就永远是安全的。这也是 TLS 1.3 强制要求它的原因。

### 8.8 只做加密、不做证书校验，行不行？

不行，而且是**非常常见的安全误区**。加密只保证“**别人看不懂**”，但**不保证你在跟谁说话**。如果客户端无条件信任拿到的公钥（比如某些 App 直接忽略证书校验、`curl -k` 一把梭），那么攻击者只要在中间转发并替换公钥，就能把加密通道变成“**双方各跟攻击者加密**”——**看起来一切正常，实际上全程被监听**。

这就是为什么HTTPS的三件事(加密、完整性、身份认证)**缺一不可**,也是为什么App端还常见 **证书固定(Certificate Pinning)**:把服务器证书或公钥的指纹写死在客户端里,连系统信任库里的根证书都不再无条件相信。
