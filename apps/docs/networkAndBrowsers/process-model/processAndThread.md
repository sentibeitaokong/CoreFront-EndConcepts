# 进程与线程

在操作系统和软件工程领域，**进程 (Process)** 和 **线程 (Thread)** 是最基础也是最重要的两个概念。

## 1. 核心概念解析

### 1.1 进程 (Process)

- **定义**：进程是计算机中已运行程序的实体，是**操作系统进行资源分配和调度的基本单位**。
- **通俗理解**：你可以把进程想象成一个“**工厂**”。当你双击打开一个微信（或 Chrome 浏览器、Word 文档）时，操作系统就为你启动了一个进程。
- **组成部分**：每个进程都有自己独立的一块地盘（内存空间）。这个空间里存放着：
  - **代码段**：程序编译后的机器指令。
  - **数据段**：全局变量和静态变量。
  - **堆 (Heap)**：程序运行时动态分配的内存。
  - **栈 (Stack)**：函数调用的局部变量和返回地址。
  - **文件描述符 / 打开的文件列表**等系统资源。
- **独立性**：进程与进程之间是**相互隔离**的。微信的进程崩溃了，绝对不会影响到正在播放音乐的网易云进程。这是操作系统为了安全做出的保护机制。
- **进程控制块 (PCB)**：操作系统为每个进程维护的一份“**档案**”，记录 **PID**、进程状态、程序计数器、内存指针、打开的文件列表等。**PCB 是进程存在的唯一标志**——操作系统就是靠它来管理和调度进程的。
- **五种状态**：新建 → 就绪 → 运行 → 阻塞 → 终止。其中要分清是谁在推动状态流转：
  - **就绪 ⇄ 运行**：由**时间片**驱动。时间片用完就被换下（回到就绪），这是操作系统的**抢占**。
  - **运行 → 阻塞**：进程**自己**去等 I/O 或锁，主动让出 CPU。
  - **阻塞 → 就绪**：它等的事件完成了，重新排队。
  - **只有就绪态才能被调度上 CPU**——所以“**阻塞**”的进程再多也不影响别人跑，这正是 I/O 密集场景能靠多线程/多进程提吞吐的底层原因。

### 1.2 线程 (Thread)

- **定义**：线程是操作系统**能够进行运算调度的最小单位**。它被包含在进程之中，是进程中的实际运作单位。
- **通俗理解**：你可以把线程想象成工厂里的“**流水线工人**”。一个工厂（进程）里至少有一个工人（主线程），也可以有多个工人（多线程）同时干活。
- **资源共享**：同一个进程内的所有线程，**共享该进程的全部系统资源**（如代码、数据、堆、打开的文件）。
- **独立性**：虽然共享资源，但每个线程拥有自己独立的：
  - **程序计数器 (PC)**：记录当前线程执行到哪一行代码了。
  - **一组寄存器**：保存线程运行时的临时数据。
  - **线程栈 (Stack)**：保存每个线程自己函数调用的局部变量。
- **轻量级**：因为线程不需要拥有独立的内存空间（借用进程的），所以线程的创建、销毁和切换代价，远比进程小得多。因此线程被称为“**轻量级进程**”。
- **私有 vs 共享（记这一条就够）**：**私有**的是程序计数器、寄存器、线程栈——也就是**上下文切换时要保存的那一小撮**；**共享**的是代码段、数据段、堆、文件描述符等进程级资源。线程“**轻**”在私有部分很少，“**险**”在共享部分没有隔离。
- **三种线程模型**：
  - **1:1**：一个用户线程对应一个内核线程。**现代主流**（pthread、Java `Thread`），能真正并行，代价是切换要陷入内核。
  - **N:1**：多个用户线程挤在一个内核线程上。切换极快，但**一个线程阻塞就全员阻塞**，也用不上多核（早期绿色线程）。
  - **M:N**：混合模型，用户态调度器把 M 个协程摊到 N 个内核线程上（Go 的 goroutine 就是这一类，见 4.3）。

## 2. 进程与线程的详细对比

| 维度                | 进程 (Process)                                                                 | 线程 (Thread)                                                                        |
| :------------------ | :----------------------------------------------------------------------------- | :----------------------------------------------------------------------------------- |
| **根本属性**        | **资源分配**的最小单位。                                                       | **CPU 调度和执行**的最小单位。                                                       |
| **包含关系**        | 一个进程至少包含一个线程（主线程）。                                           | 一个线程必定属于某个进程。                                                           |
| **内存与资源**      | 每个进程拥有**独立**的地址空间和系统资源。                                     | 同一进程下的线程**共享**该进程的地址空间和资源。但每个线程有独立的栈和寄存器。       |
| **开销 (Overhead)** | **非常大**。创建、销毁进程需要操作系统分配/回收内存等资源。                    | **很小**。创建、销毁线程只需分配少量的栈空间。                                       |
| **上下文切换**      | **慢**。需要切换页表（虚拟内存映射），刷新 TLB 缓存，开销极大。                | **快**。不需要切换虚拟内存空间，只切换少量的寄存器和栈指针。                         |
| **通信机制 (IPC)**  | 困难且复杂。需要操作系统的介入（如管道、消息队列、共享内存、信号量、Socket）。 | 非常容易。由于共享内存空间，线程之间可以直接通过读写全局变量通信（但需要加锁同步）。 |
| **安全性/健壮性**   | **极高**。一个进程崩溃通常不会影响其他进程（隔离机制）。                       | **较差**。一个线程崩溃（如引发段错误段溢出），往往会导致整个进程随之崩溃。           |
| **典型 API**        | `fork()` / `spawn()`、Python `multiprocessing`、Node `cluster`                 | `pthread_create`、Java `Thread`、Node `worker_threads`                               |
| **预期数量级**      | 几十 ~ 几百个（再多内存就吃不住了）                                            | 几千 ~ 几万个（再往上就该换协程）                                                    |
| **调试难度**        | **较易**。边界清晰，崩溃点基本就是出事的那个进程。                             | **较难**。竞态、时序问题**难以复现**，同一个 bug 可能只在特定调度顺序下出现。        |

## 3. 什么时候用多进程？什么时候用多线程？

- **多进程适用场景**：
  - **需要极高稳定性和安全性的应用**：典型的例子是现代浏览器（如 Chrome）。每一个标签页（Tab）或插件都在一个独立的进程中运行。如果某个网页崩溃了，只会关掉那个标签页，其他网页和整个浏览器都不受影响。如果用多线程，一个恶意的 JavaScript 代码就能搞垮整个浏览器。
  - **CPU 密集型的任务（特别是 Python）**：由于 Python 中存在 GIL (Global Interpreter Lock，全局解释器锁) 的限制，Python 的多线程在处理计算密集型任务时无法真正利用多核 CPU（依然是串行执行）。此时，使用多进程 (Multiprocessing) 是唯一的解药，因为每个进程都有自己独立的 GIL。
  - **要把任务摊到多个 CPU 核上（Node.js）**：**一个进程只能用一个核**。Node 的单线程事件循环跑满一个核就上不去了，所以生产环境用 `cluster`（多进程共享端口）、`child_process`（子进程）或 `PM2` 的 cluster 模式把负载分到多个进程，有几个核就起几个实例。
  - **需要隔离“不可信代码”**：插件系统、在线 IDE、Electron 的渲染进程——把可能崩溃、可能作恶的代码关进单独进程，出事只杀它一个，主程序安然无恙。VS Code 把扩展跑在独立的**扩展宿主进程**里就是这个思路。
  - **构建、压缩等工程任务**：`thread-loader`、多进程压缩、多进程跑测试，本质都是把一个 CPU 密集任务拆给多个进程并行跑——名字里带 thread，实际用的是进程。

- **多线程适用场景**：
  - **I/O 密集型任务**：典型的如 Web 服务器处理并发请求（如下载文件、数据库查询、网络通信）。因为这些操作大部分时间都在等待数据返回（阻塞），在此期间 CPU 是空闲的。多线程可以充分利用这些等待时间，让其他线程继续处理别的请求。
  - **需要频繁共享大量数据的任务**：因为线程间共享内存空间，所以通信成本极低，不需要像进程那样通过复杂的机制来拷贝数据。
  - **前端：把长计算搬离主线程（Web Worker）**：JS 本身是单线程的（见 [事件循环](/js/advanced/async/eventLoop)），页面卡顿的根源就是主线程被计算占满。`Web Worker` 是浏览器给 JS 的真线程：把大数组处理、加解密、图片编解码丢进去，主线程继续响应点击和渲染。三个必须记住的限制——Worker **碰不到 DOM**、数据默认靠 `postMessage` **结构化克隆**（大对象有拷贝成本，可用 **Transferable** 转移所有权零拷贝），跨线程共享内存要 `SharedArrayBuffer`（页面需开跨源隔离，Node 侧的对应方案是 `worker_threads`）。
  - **服务端：线程池处理并发请求**：Tomcat、JVM Web 应用用固定大小的线程池接请求，每个请求占一个线程、大部分时间在等数据库和下游服务（I/O 密集），因此池子可以远大于 CPU 核数。

[width(48,20,32)]

| 任务特征                                       | 选谁                | 原因                                           |
| ---------------------------------------------- | ------------------- | ---------------------------------------------- |
| 大部分时间在**等**（网络、磁盘、数据库）       | **多线程 / 异步**   | 等待时线程让出 CPU，拿这段时间去干别的活       |
| 大部分时间在**算**（CPU 密集）                 | **多进程 / Worker** | 要的是多核并行；单核上加线程也快不了（见 4.5） |
| **怕它崩、怕它脏**（不可信代码、插件、多租户） | **多进程**          | 用进程隔离兜住事故，崩一个不影响其他           |
| **要频繁共享大数据**                           | **多线程**          | 共享内存，省掉跨进程拷贝                       |

> 真实工程里基本都是**混用**：用**进程**划分隔离边界，用**线程**划分同一边界内的工作单元。

## 4. 常见问题 (FAQ) 与面试题

### 4.1 什么是线程安全？如何保证线程安全？

- **概念**：当多个线程同时访问同一个共享资源（如修改同一个全局变量）时，如果不加任何控制，就会产生数据错乱或不可预期的结果。如果一段代码在多线程环境下运行，其结果和单线程环境完全一致，这就是线程安全的。
- **保证方式**：
  - **互斥锁 (Mutex) / 同步机制**：当一个线程在修改数据时，把资源锁住，其他线程必须排队等待。这是最常用的方法（如 Java 中的 `synchronized` 关键字或 `ReentrantLock`）。
  - **使用线程局部变量 (ThreadLocal)**：每个线程在本地维护该变量的副本，互不干扰，从而避免共享（空间换时间的策略）。
  - **无锁编程 (Lock-Free)**：利用底层的 CAS (Compare-And-Swap) 原子操作。

### 4.2 什么是死锁 (Deadlock)？产生的条件是什么？如何避免？

- **概念**：两个或多个线程（或进程）互相持有对方需要的锁，并在等待对方释放锁。结果大家都卡死在那里，谁也无法继续执行。
  - _比喻_：A 拿着钥匙，想要开门；B 守在门边，想要拿钥匙。两人都不肯松手，于是僵持不下。
- **产生死锁的四个必要条件**（缺一不可）：
  - **互斥条件**：一个资源每次只能被一个线程使用。
  - **请求与保持条件**：一个线程因请求被占用的资源而阻塞时，对自己已经获得的资源保持不放。
  - **不剥夺条件**：线程已获得的资源，在未使用完之前，不能被其他线程强行剥夺。
  - **循环等待条件**：多个线程之间形成一种头尾相接的循环等待资源的关系。
- **如何避免/预防死锁**（核心是破坏上面四个条件之一）：
  - **破坏互斥条件**：不可行，锁的意义就是互斥。
  - **破坏请求与保持**：规定线程在开始执行前，必须一次性申请它需要的所有资源。如果申请不到，就什么也不拿，干等着。（缺点：资源利用率极低）。
  - **破坏不剥夺条件**：如果一个已经持有部分资源的线程去申请新资源被拒绝，它必须主动释放自己当前持有的所有资源，过一会再重新尝试。（缺点：实现复杂，且可能导致线程反复尝试而做无用功，即“**活锁**”）。
  - **破坏循环等待条件（最实用）**：对系统中所有的资源进行编号，规定所有线程必须严格按照编号的**递增顺序**来申请锁。这样就永远不会出现循环等待的情况。

### 4.3 什么是协程 (Coroutine)？它和线程的区别是什么？

协程是一个更加轻量级的概念，有时被称为“**用户态的线程**”。

- **调度者不同**：
  - **线程**是由**操作系统内核 (OS Kernel)** 进行调度和管理的，切换成本较高。
  - **协程**是由**程序员在应用代码层面 (User Space)** 通过程序库（如 Python 的 `asyncio`、Go 的 `goroutine`）自行控制调度的。操作系统根本不知道协程的存在。
- **切换开销极小**：因为协程的切换完全在用户态进行，不需要陷入内核态，不需要保存和恢复复杂的寄存器状态，只需要保存极少的上下文信息。所以一台机器上可以轻松创建几十万甚至上百万个协程（如 Golang），而线程通常只能创建几千个。
- **并发模型**：线程是抢占式的并发（操作系统随时可以中断你），协程通常是协作式的并发（协程主动让出执行权 `yield/await` 给别的协程）。

### 4.4 上下文切换 (Context Switch) 到底在切换什么？为什么进程切换比线程切换慢得多？

- **上下文切换在切换什么**：当 CPU 从执行任务 A 切换到任务 B 时，它必须保存任务 A 当前的状态（比如程序计数器指到哪行代码了、各个寄存器里存的临时变量是什么），然后加载任务 B 之前保存的状态。这就叫上下文切换。
- **为什么进程切换更慢**：
  - 对于**线程切换**，由于它们属于同一个进程，**共享同一个虚拟内存空间**。所以只需要切换极少数的寄存器和栈指针。
  - 对于**进程切换**，由于每个进程有自己独立的虚拟内存空间。切换进程时，不仅要切换寄存器，更要命的是**必须切换页表 (Page Table)**，从而导致 **TLB (Translation Lookaside Buffer，页表缓存) 彻底失效并被清空**。TLB 的失效会导致接下来的一段时间内，所有的内存访问都变慢（因为要去查慢速的主存），这是进程切换开销巨大的根本原因。

### 4.5 单核 CPU 上开多线程有意义吗？

**有，而且这是最容易答错的一题。** 多线程的价值要分两层看：

- **想真正“同时算”，必须多核**：CPU 密集任务在单核上开多线程并不会变快，切换本身还要额外花钱。
- **但 I/O 密集任务在单核上收益巨大**：线程等网络/磁盘时会**让出 CPU**（进入阻塞态），操作系统立刻切去跑别的线程，CPU 不至于空转。所以单核时代的多线程是为了「**不让 CPU 闲着**」，多核时代才是为了「**同时算**」。

顺带记住这两个词的区别：**并发 (Concurrency) ≠ 并行 (Parallelism)**。并发是「交替推进多个任务」，单核也能做到；并行是「同一时刻真的一起跑」，必须多核。

### 4.6 为什么 JavaScript 是单线程的？那前端还需要懂多线程吗？

JS 设计成单线程是为了简单：如果多个线程同时操作 DOM，就得处理锁、渲染顺序和竞态，复杂度会爆炸（见 [事件循环](/js/advanced/async/eventLoop)）。所以 JS 选了另一条路——**用事件循环 + 异步回调在单线程里实现并发**。

但“**JS 单线程**”说的是**执行 JS 的那部分**，浏览器整体是多进程 + 多线程的：

- **多进程**：渲染进程、GPU 进程、网络进程、插件进程各自独立；
- **渲染进程内部的多线程**：主线程（JS 执行 + 渲染）、合成线程、光栅化线程、定时器线程，以及你自己创建的 Worker 线程。

对前端来说，“**用上多线程**”主要是三条路：**Web Worker**（真并行计算）、**分片 + `requestIdleCallback`**（不换线程，只是把长任务切开、主动让出主线程）、以及**把重计算推给服务端或 WASM**。

### 4.7 线程是不是越多越好？线程池解决了什么？

不是。线程数超过 CPU 核心数之后，收益递减而成本递增：

- 每个线程都要占**栈空间**（默认约 1MB），几千个线程就是几个 GB；
- 线程一多，**上下文切换本身**会吃掉大量 CPU，极端情况下切线程的开销比干活还大（**thrashing**）。

所以服务端普遍用**线程池**：预先创建固定数量的线程，任务排队进去复用它们，避免频繁创建销毁、也避免无上限膨胀。两个核心参数是**核心线程数**与**最大线程数**；粗略经验是——**CPU 密集**任务的池子设成「核数 + 1」，**I/O 密集**可以大得多（因为线程大部分时间在等）。

### 4.8 多进程和多线程能混用吗？工程里一般怎么组合？

能，而且现代大型应用几乎都是混用：

[width(26,74)]

| 组合方式              | 典型例子                                                             |
| --------------------- | -------------------------------------------------------------------- |
| 多进程 + 每进程多线程 | Chrome：每个标签页一个渲染进程，进程内再跑主线程 / 合成线程 / Worker |
| 多进程 + 进程内单线程 | Node.js `cluster`：每个进程一个事件循环，主进程只负责分发            |
| 单进程 + 多线程       | 传统 Java Web 应用：一个 JVM 进程 + 线程池处理请求                   |

**组合的通用思路**：用**进程**划分「隔离边界」（谁崩了不影响谁、以及怎么把负载摊到多个核），用**线程**划分「同一边界内的工作单元」（能共享内存、通信便宜）。
