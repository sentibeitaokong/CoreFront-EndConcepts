# UDP 协议

**UDP** (User Datagram Protocol，用户数据报协议) 是一种**无连接**的、**不可靠**的、基于报文的**传输层**通信协议。在 OSI 模型中，它和 TCP 一样位于第四层（传输层），介于应用层和网络层之间。

**一句话理解**：UDP 把 TCP 里所有“**为了可靠而付出的代价**”全部砍掉，只留下**端口寻址**这一件事——所以它快、简单、开销小，而“**可靠**”这件事被整个推给了应用层自己决定要不要做。

> [!TIP] 相关阅读
> UDP 的对照组是 [TCP 协议](/networkAndBrowsers/transport/tcp)，它所在的层次见 [OSI 七层模型](/networkAndBrowsers/fundamentals/osi)，它最经典的用途是 [DNS 解析](/networkAndBrowsers/fundamentals/dns)，而 HTTP/3 的底座 QUIC 建在它之上（见 [实时通信](/networkAndBrowsers/realtime/realtimeCommunication) 与 [HTTP 协议](/networkAndBrowsers/http/http)）。

## 1. 什么是 UDP？

UDP 做的事可以用一句话说完：**拿到应用层交下来的一段数据，加 8 字节首部，交给 IP 层发出去；收到一个包，剥掉 8 字节首部，交给对应端口上的应用。** 中间没有排队、没有确认、没有重传、没有等待，也没有任何需要记住的“**连接状态**”。

正因为什么都不记，UDP 的“**无连接**”有两个容易被忽略的推论：

- **服务端不需要为每个客户端维护状态**。同一台服务器扛十万个 UDP 客户端的内存开销，远小于扛十万条 TCP 连接（每条 TCP 连接都要维护一整套 TCB：序号、窗口、定时器、重传队列）。这是 DNS 服务器、NTP 服务器愿意用 UDP 的重要原因。
- **“连接”这个概念在 UDP 里是假的**。你发出的每个包都独立携带完整的收发地址（源 IP、源端口、目的 IP、目的端口），内核不保证它们走同一条路径，也不保证对方是同一个进程。

## 2. UDP 的核心特性

- **面向无连接**：发送数据之前不需要建立连接（没有三次握手），发送结束后也没有连接释放（没有四次挥手）。**代价是“首包即数据”**：TCP 的第一个包是 SYN，UDP 的第一个包就是你要发的内容，这也是它省下一个 RTT（Round-Trip Time，往返时间）的地方。
- **不可靠交付**：它不保证数据包能成功到达目的地，也不保证按序到达，更没有重传机制。数据发出去后，UDP 就不再管了。**注意“不可靠”不等于“一定丢”**：在局域网或质量好的链路上，UDP 的丢包率可能低到测不出来；它是**不做保证**，而不是**故意做坏**。
- **面向报文**：UDP 对应用层交下来的报文，既不合并，也不拆分，而是**保留这些报文的边界**。应用层交给 UDP 多长的报文，UDP 就发多长。**这是 UDP 与 TCP 最本质的差别**：一次 `send` 对应一次 `recv`，边界天然存在，所以 UDP 不存在粘包问题。
- **无拥塞控制与流量控制**：UDP 永远以恒定的速度发送数据，不管网络是否拥堵。**这既是优点也是危险**：优点是不会因为丢包而自我降速（画面不会突然糊成一片），危险是它可能把中间链路挤爆、顺带伤害同一链路上的 TCP 流量。
- **支持一对一、一对多（广播/多播）通信**：这是 TCP 做不到的。TCP 要维护连接状态，因此只能严格一对一；UDP 每个包自带地址，所以既能发给单个目标，也能发给局域网里所有设备（广播）、或发给一组加入同一组的设备。
- **首部开销极小**：只有 8 个字节，比 TCP 的 20 字节轻量得多。**对 DNS 这种“请求几十字节、响应几百字节”的协议来说，省下的 12 字节不是小事**——它占比可观，而且省掉的不只是带宽，还有处理每个包时的解析开销。

## 3. 一次 UDP 通信长什么样

![UDP 通信流程与 Socket 调用时序](/img/udp.png)

对比 TCP 的时序图会立刻看出差别：**没有三次握手，也没有四次挥手**，双方各自 `bind` 完就能直接收发。

[width(9,40,51)]

| 步骤 | 服务端                              | 客户端                                              |
| :--- | :---------------------------------- | :-------------------------------------------------- |
| 1    | `socket()` 创建套接字               | `socket()` 创建套接字                               |
| 2    | `bind()` 绑定固定端口（如 53）      | 通常**不 bind**，首次 `send` 时内核自动分配临时端口 |
| 3    | `recvfrom()` 阻塞等待数据           | `sendto()` 直接发送，不等待任何人同意               |
| 4    | 收到后从 `rinfo` 里拿到对端地址     | `recvfrom()` 阻塞等待响应                           |
| 5    | `sendto()` 回包                     | 收到即处理，收不到就自己决定要不要重试              |
| 6    | 无连接可关，用完 `close()` 释放句柄 | 同左                                                |

```js
import dgram from 'node:dgram'

// server.js：绑定端口，收到什么就回什么
const server = dgram.createSocket('udp4')
server.on('message', (msg, rinfo) => {
  // 每个包都自带来源地址，所以服务端不需要“记住”这个客户端
  console.log(`收到 ${msg.toString()} 来自 ${rinfo.address}:${rinfo.port}`)
  server.send('pong', rinfo.port, rinfo.address)
})
server.bind(41234) // UDP 服务端必须 bind，因为客户端要知道往哪个端口发

// client.js：不需要 connect，也不需要 bind
const client = dgram.createSocket('udp4')
// 第一次 send 时内核自动分配一个临时端口，之后复用它
client.send('ping', 41234, '127.0.0.1')

client.on('message', msg => {
  console.log('收到响应:', msg.toString())
  client.close()
})
```

## 4. UDP 报文首部结构 (仅 8 字节)

UDP 的简洁在其首部体现得淋漓尽致。

[width(31,10,59)]

| 字段名                          | 长度  | 说明                                                  |
| :------------------------------ | :---- | :---------------------------------------------------- |
| **源端口 (Source Port)**        | 16 位 | 发送方的进程端口号。                                  |
| **目的端口 (Destination Port)** | 16 位 | 接收方的进程端口号。                                  |
| **长度 (Length)**               | 16 位 | UDP 用户数据报的长度（包含首部和数据），最小值为 8。  |
| **校验和 (Checksum)**           | 16 位 | 检测 UDP 数据报在传输中是否有错。如果有错，直接丢弃。 |

对比 TCP 首部：8 字节对 20~60 字节。所有让 TCP 变“**可靠**”的东西——序列号、确认号、窗口、标志位、选项——**在 UDP 首部里一个都没有**。

## 5. 面向报文：边界、顺序与丢失

UDP 是**面向报文**的，意思是：**一次 `send` 就是一个完整的数据报，一次 `recv` 就刚好收到一个完整的数据报**。这个特性带来三条和 TCP 完全相反的行为：

[width(9,44,47)]

| 行为         | UDP                                                          | TCP                                         |
| :----------- | :----------------------------------------------------------- | :------------------------------------------ |
| **边界**     | 天然保留：发 3 个包就收 3 次，绝不会合成一次                 | 无边界：3 次 `write` 可能被合成 1 次 `read` |
| **顺序**     | 不保证：后发的可能先到，绕路走完全正常                       | 严格有序：乱序会在接收端缓存里重新排好      |
| **丢失**     | 不保证：丢一个是一个，丢哪个、丢几个都不知道                 | 保证不丢：没确认就重传，直到对方收下        |
| **接收缓冲** | 一次 `recv` 只取走**一个数据报**，剩下的要靠调用方自己循环取 | 读多少取多少，可以按任意长度切分            |

- **应用层的缓冲区必须足够大**。一次 `recv` 只能拿到一个数据报，如果传入的缓冲区比数据报小，**多出来的部分会被直接丢弃**（不是截断保留，是丢掉）——你必须保证缓冲区能装下最大的那个报，而且要按**协议规定的最大报文**来分配：留小了会被静默截断，而这在测试环境里往往看不出来，因为测试数据总是很小。
- **丢包和乱序要自己在应用层处理**。要顺序就给每个包编号、自己在接收端排；要减缓缓冲可以加抖动缓冲（jitter buffer）；要可靠性就得自己实现确认与重传。

## 6. 报文能有多大：MTU 与分片

**理论上**：UDP 长度字段是 16 位，最大值 65535 字节（含 8 字节首部，所以数据部分是 65527 字节）。

**实际上**：受限于底层 IP 层和以太网的 **MTU（最大传输单元，通常是 1500 字节）**。为了让整个数据报能装进一个链路层帧里，数据部分应该控制在：

```markdown
IPv4: 1500 − 20(IP 首部) − 8(UDP 首部) = 1472 字节
IPv6: 1280 − 40(IP 首部) − 8(UDP 首部) = 1232 字节
```

超出这个大小会发生什么？**IP 层会分片**，把一个大 UDP 报切成多个 IP 分片分别发送。这是要尽量避免的：

- 一次 UDP 发送会产生多个包，**丢掉其中任何一个，整个数据报就报废了**（而 IP 层不会重传，UDP 也不会）——丢包概率被放大了好几倍。
- 分片与重组要在每一跳路由器或最终主机上做，开销更大、更容易被防火墙拦截。
- IPv6 里路由器**不再允许分片**（只有源端可以），所以对路径 MTU 的探测（PMTUD）变得必需；如果 ICMP 报文被拦截，就会出现“**小包能通、大包全丢**”的黑洞现象，而且很难查。

所以实践中的经验值是：**要发超过 1472 字节的数据，要么在应用层自己拆成多个小包（并自己加上序号以便重组），要么改用 TCP。** 这也是为什么 QUIC 在应用层自己做了分段——它必须知道每个包的大小上限，才能避开 IP 分片。

## 7. 没有流量控制与拥塞控制意味着什么

UDP 既不问对方“**你还收得下吗**”（流量控制），也不问网络“**还挤得下吗**”（拥塞控制）。后果是双向的：

**对接收方**：既然没有流量控制，如果发送方拼命发，而接收方来不及从内核缓冲区读取数据，**缓冲区就会满**。一旦满了，后续到达的 UDP 包会被系统**直接丢弃**——而且丢在接收端，发送方毫不知情（它可能连 ACK 都没有）。内核缓冲区大小由 `SO_RCVBUF` 决定，对高性能的 UDP 服务需要显式调大。

**对发送方**：既然没有拥塞控制，UDP 会以恒定速率发送，**丢包了也不会降速**。这正是实时音视频想要的——丢两帧远好过突然降码率导致画面糊掉。但反过来说，**UDP 流量是没有“礼貌”的**：同一链路上它会把 TCP 流量挤到边上，因为 TCP 看到丢包就退让，UDP 不会。这就是为什么浏览器和操作系统会对 WebRTC 之类的 UDP 流量做带宽估计与限速——礼让必须由应用层自己实现。

## 8. UDP 的典型应用场景

为什么在明知不可靠的情况下，我们还要使用 UDP？答案是：**低延迟和实时性**。

- **实时流媒体/视频会议 (VoIP)**：在语音通话或直播中，丢掉一两个数据包（画面花一下或声音断一下）是可以接受的，但如果因为等待重传而导致长达数秒的延迟，通话就没法进行了。
- **在线游戏**：在快节奏游戏中（如 FPS 或 MOBA），即时位置信息比历史位置更重要。丢了旧包没关系，只要下一个新包能快点到就行。
- **DNS (域名系统)**：查询域名的请求很短。如果用 TCP，握手就需要 3 个包，查询才 1 个包，太浪费了。用 UDP 一问一答，效率最高。
- **广播与多播**：例如局域网内的设备发现、视频广播。TCP 无法实现一对多。
- **简单网络协议**：如 DHCP（动态主机配置）、SNMP（简单网络管理）、TFTP（简单文件传输）。

[width(11,11,78)]

| 协议 | 端口  | 为什么选 UDP                                        |
| :--- | :---- | :-------------------------------------------------- |
| DNS  | 53    | 一问一答、请求极小，省掉握手收益最大                |
| DHCP | 67/68 | 客户端此时**还没有 IP 地址**，根本没法建立 TCP 连接 |
| NTP  | 123   | 单次交互，靠多次采样算时间差，丢一次重试即可        |
| SNMP | 161   | 周期性上报，丢一次下次再来                          |
| TFTP | 69    | 协议极简（适合固件/引导阶段），可靠性自己做         |
| RTP  | 动态  | 音视频流，宁可丢帧也不等重传                        |

## 9. DNS 是怎么同时用上 UDP 和 TCP 的

DNS 是“**按场景挑传输层**”最好的教材：同一个协议、同一个 53 端口，两种用法各司其职。**常规查询走 UDP；凡是“装不下”或“必须完整”的场合，退回 TCP**。UDP 的“**快**”和 TCP 的“**完整**”在这里是配合关系，而不是二选一。

[width(26,42,32)]

| 场景                                     | 走哪个                                   | 为什么                                               |
| :--------------------------------------- | :--------------------------------------- | :--------------------------------------------------- |
| 常规查询                                 | **UDP 53**                               | 一问一答、请求通常只有几十字节，省掉三次握手收益最大 |
| 响应太大装不下                           | 先 UDP，**收到 `TC=1` 后用 TCP 53 重查** | 服务端主动截断并置位截断标志，回退由客户端负责       |
| 主从同步整个区域（区域传输 AXFR / IXFR） | **TCP 53**                               | 数据量大且必须完整有序，传一半没有任何意义           |
| 带 DNSSEC 签名的响应                     | **常常落到 TCP**                         | 签名让响应明显膨胀，容易顶穿 UDP 的协商上限          |
| 加密查询（DoT / DoH）                    | **TCP 853 / TCP 443**                    | 加密与完整性校验本身就依赖一条有序可靠的字节流       |

- **为什么默认是 UDP**：TCP 要先花 3 个包完成握手，才能发出那 1 个包的查询，等于 **2 个 RTT** 才拿到答案；UDP 一问一答只要 **1 个 RTT**。域名解析在关键路径上，这一个往返会直接换算成首屏时间。
- **回退是有代价的**，所以在尽量避免。`TC=1` 意味着用户要多等一个往返，于是现代解析器普遍启用 **EDNS0**，把 UDP 载荷上限从 512 字节协商到 4096 字节，让绝大多数响应不必退回 TCP。
- **换到 TCP 之后，边界立刻消失**。UDP 上“**一次 `recv` 就是一个完整 DNS 报文**”，而 TCP 是字节流，所以 RFC 1035 规定改用 TCP 承载时要在每个报文前面加 **2 字节长度前缀**。
- **UDP 的不可靠，代价由应用层补**：客户端要自己起超时重试，还要用报文里的**查询 ID** 去核对响应是不是自己那份——没有握手，就只能靠这个 ID 认出对方。

## 10. 安全面：源地址伪造与放大攻击

UDP 的一大安全弱点是它**没有握手**：TCP 必须先完成三次握手、期间双方要交换并验证序列号，而 UDP 的第一个包就会直达服务端并触发响应。这带来两个可被滥用之处：

- **源地址可以随意伪造**。攻击者把 UDP 包的源 IP 伪造成受害者的 IP，服务端完全无法分辨，只会把响应发给那个被伪造的地址。TCP 做不到这一点，因为伪造的源地址收不到 SYN+ACK，握手就完不成（这也是 SYN cookies 能缓解 SYN Flood、而 UDP 没有对应防线的原因）。
- **放大效应**：某些 UDP 服务的“**响应**”远大于“**请求**”。攻击者用极小的代价（一个几十字节的伪造请求）就能诱导服务器向受害者发出成百上千倍的响应包，经典的可放大服务包括 DNS、NTP（`monlist` 命令）、Memcached。这类攻击叫**反射放大**：借第三方服务器之手打向受害者，既隐藏了真实攻击者，又用一份请求换来几十上百份流量。

**防御方向也是从这两点切入的**：服务端关闭不必要的 UDP 服务、限制单 IP 请求速率、对响应做大小上限，并**丢弃源地址明显不合法的包**（如来自公网的私有网段地址）；受害端基本只能靠上游运营商清洗流量，所以提前约定好应急流程比事后救火重要；协议层面则把“**一次请求换一次响应**”改成多步验证（DNS 引入 Cookie 机制就是这个原因）。这里列出它，是因为这是理解 UDP 设计取舍的重要一面——**同样的“无连接”特性，既是 DNS 能高效工作的原因，也是它被拿来做放大器的原因**。

## 11. UDP vs. TCP 深度对比

[width(18,39,43)]

| 特性              | UDP                                                  | TCP                                                |
| :---------------- | :--------------------------------------------------- | :------------------------------------------------- |
| **连接性**        | **无连接**                                           | 面向连接                                           |
| **可靠性**        | **不可靠**（尽力而为）                               | 可靠（保证送达、不乱序）                           |
| **传输方式**      | 面向报文（保留数据边界）                             | 面向字节流（无边界）                               |
| **传输速度**      | **极快**（无握手开销）                               | 较慢（机制复杂）                                   |
| **首部开销**      | **8 字节**                                           | 20 ~ 60 字节                                       |
| **流量/拥塞控制** | 无                                                   | 有                                                 |
| **资源消耗**      | 低（服务端不为每个客户端存状态）                     | 高                                                 |
| **通信方式**      | 一对一、一对多（广播 / 多播）                        | 只能一对一                                         |
| **适用场景**      | 实时视频、在线游戏、DNS、直播                        | 文件传输、邮件、网页浏览                           |
| **优点**          | 简单、快速、开销小、支持广播/多播                    | 稳定、有序、有重传与拥塞控制、可感知连接状态       |
| **缺点**          | 不可靠、无流量与拥塞控制、源地址易被伪造（放大攻击） | 速度慢、开销大、容易被攻击（三次握手 → SYN Flood） |

## 12. 常见问题 (FAQ) 与面试热点

### 12.1 UDP 会发生粘包吗？

- **答案：绝对不会。**
- **原因**：粘包是 TCP 这种“**面向字节流**”协议特有的问题。UDP 是“**面向报文**”的，它有明确的数据边界。发送方发一个包，接收方就收一个完整的包，不会出现多个包粘在一起的情况。
- **顺带一提**：UDP 不会粘包，但会“**丢包**”和“**截断**”——如果接收缓冲区比数据报小，超出的部分会被丢弃，所以缓冲区一定要按最大可能的数据报大小来分配。

### 12.2 既然 UDP 不可靠，那 DNS 丢包了怎么办？

- DNS 客户端在发出请求后会启动一个超时定时器。如果在一定时间内没有收到 UDP 响应，客户端会**再次发起请求**。这种简单的重试机制对于 DNS 这种轻量级交互来说成本非常低。
- 实际上系统会对多个 DNS 服务器**并发或依次**尝试，所以单台服务器丢包通常不会让解析失败，只是变慢。真正需要在意的是“**慢**”而不是“**丢**”——重试意味着用户要多等一个超时周期。

### 12.3 既然 UDP 有这么多问题，为什么还要用它？

一句话：**因为它不替你做决定。** TCP 帮你决定了“**必须可靠、必须有序、必须礼让拥塞**”——这些决定在网页、文件传输里都是对的，但在实时音视频里是错的：等待重传的那几百毫秒，比丢一帧的代价大得多。UDP 把所有这些决定权交回给应用层，让应用按自己的场景（要延迟还是要完整）来权衡。

### 12.4 TCP 和 UDP 可以在同一个端口上共存吗？

- **可以。** 端口是**每个传输层协议各自一套**的：`TCP 53` 和 `UDP 53` 是两个互不冲突的监听点，DNS 正是这样同时提供两种方式。同理，`TCP 443` 跑的是 HTTPS，而 HTTP/3 用的是 `UDP 443`。判断一个端口有没有被占用时，必须说清是 TCP 还是 UDP。
