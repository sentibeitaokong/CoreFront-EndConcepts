# TCP 协议

**TCP** (Transmission Control Protocol，传输控制协议) 是一种面向连接的、可靠的、基于字节流的**传输层**通信协议。在 OSI 模型中，它位于第四层（传输层），介于应用层（如 HTTP/HTTPS）和网络层（如 IP 协议）之间。

**一句话理解**：如果说 IP 协议负责把数据包从地球的一端“**尽力而为**”地送到另一端（不保证送达），那么 **TCP 协议就是那个负责查收、排队、补发，并最终把完整数据亲手交给应用程序的“快递总管”**——HTTP、SSH、数据库连接之所以能像读写本地文件一样收发数据，是因为 TCP 在下面替它们扛住了网络的全部不确定性。

> [!TIP] 相关阅读
> TCP 所在的层次见 [OSI 七层模型](/networkAndBrowsers/fundamentals/osi)，它依赖的下层寻址与路由见 [IP 协议](/networkAndBrowsers/fundamentals/ip)，它最典型的用户是 [HTTP 协议](/networkAndBrowsers/http/http)，它的对照组是 [UDP 协议](/networkAndBrowsers/transport/udp)。

## 1. TCP 解决什么问题

IP 层只承诺“**尽力而为**”（best effort）。一个数据包要穿过几十台路由器，一路上可能遇到四种麻烦：

- **丢包**：路由器队列满了就直接丢，不通知任何人。
- **乱序**：同一批数据包可能各走各的路径，到达顺序和发送顺序无关。
- **重复**：一旦发生重传，接收方就可能收到同一份数据的多份副本。
- **收不住**：发送方比接收方快，或者整条链路堵了，多出来的数据只能被丢弃，而且越猛发丢得越多。

TCP 的全部机制都是为了在这几种不确定之上，给应用层一个确定的结果，核心只有四件事：

- **给每个字节编号**（序列号）——乱序和重复都能靠编号复原。
- **要求对方确认收到**（ACK）——不知道有没有丢，重传就无从谈起。
- **没确认就重发**（超时重传、快速重传）——把丢掉的补上。
- **按对方的接收能力和网络的拥堵程度调整发送速度**（流量控制、拥塞控制）。

## 2. TCP 的五大核心特性

- **面向连接**：通信双方在交换数据之前，必须先通过三次握手建立一条虚拟的逻辑连接；通信结束后还要四次挥手释放它。连接不是一根真实的线，而是双方内核里各存的一份状态。
- **可靠传输**：TCP 保证数据能够**无损坏、无丢失、无重复、按序**到达接收端。这四条承诺分别对应校验和、确认重传、去重、序列号四个机制。
- **全双工通信**：连接一旦建立，双方都可以同时发送和接收数据。也正因为全双工，关闭连接要两个方向各关一次。
- **面向字节流**：TCP 不关心应用层发来的是什么消息，它只把数据看成一连串无结构的字节流。这既是它灵活的地方，也是“**粘包**”问题的根源。
- **流量与拥塞控制**：根据接收方的处理能力和整个网络的拥堵情况，动态调整发送速度。前者管“**别撑爆对方**”，后者管“**别压垮网络**”。

## 3. 连接的标识：端口与四元组

TCP 是面向连接的，但连接本身没有名字——**一条 TCP 连接由四元组唯一确定**：

```markdown
源 IP ＋ 源端口 ＋ 目的 IP ＋ 目的端口
```

- **IP 定位到机器，端口定位到机器上的进程**。端口是 16 位整数，按用途分三段：0–1023 是系统端口（80、443、22），1024–49151 是登记端口，49152–65535 是客户端临时端口（ephemeral port），由内核在建立连接时随机分配。
- 服务器在 80 端口 **LISTEN** 的那个套接字并不承载数据，它只负责接收握手请求；握手完成后内核会**新建一个套接字**（也就是 `accept()` 返回的那个）来承载这条连接。
- 所以 `127.0.0.1:54321 → 93.184.216.34:443` 和 `127.0.0.1:54322 → 93.184.216.34:443` 是两条互不干扰的连接。判断“**是不是同一条连接**”，看的从来不是“**哪个客户端**”，而是这四项的组合——这既是一台服务器能同时扛住几万条连接的原因，也是它的上限所在。

## 4. 报文段（Segment）首部解剖

TCP 把所有控制信息都放在首部里：**固定部分 20 字节，加上最多 40 字节选项，最长 60 字节**。

![TCP 报文段头部字段结构图](/img/tcpFirst.png)

[width(21,14,65)]

| 字段              | 长度      | 作用                                                                               |
| :---------------- | :-------- | :--------------------------------------------------------------------------------- |
| 源端口 / 目的端口 | 各 16 位  | 配合 IP 定位到具体进程，见上一节的四元组                                           |
| **序列号 (SEQ)**  | 32 位     | 本段第一个字节的编号，解决**乱序**与重复                                           |
| **确认号 (ACK)**  | 32 位     | 期望收到的下一个字节编号，解决**丢包**                                             |
| 标志位            | 6 位      | SYN 发起连接、FIN 结束连接、ACK 让确认号生效、RST 强制重置、PSH 催促交付、URG 紧急 |
| 窗口大小          | 16 位     | 流量控制：告诉对方“**我还能再收多少字节**”                                         |
| 校验和            | 16 位     | 校验首部、数据，以及一个由 IP 层信息拼出来的**伪首部**，出错直接丢弃               |
| 紧急指针          | 16 位     | 配合 URG 使用，指向紧急数据的末尾（如今基本不用）                                  |
| 选项              | 0–40 字节 | 协商 MSS、窗口扩大因子、SACK、时间戳等（详见第 13.3、13.4 节）                     |

![序列号解决乱序、确认号解决丢失、标志位承载不同语义](/img/tcpSecond.png)

这里要建立一个贯穿全文的关键认识：**序列号是“字节的编号”，不是“包的编号”**。TCP 不关心应用层发了几条消息，它眼里只有一连串字节。

## 5. 三次握手（建立连接）

![三次握手与双方状态迁移](/img/tcpThird.png)

握手要做两件事：**同步双方的初始序列号（ISN）**，并**确认双方的收发能力都正常**。

[width(13,23,38,26)]

| 次序   | 方向            | 报文                           | 说明                                   |
| :----- | :-------------- | :----------------------------- | :------------------------------------- |
| 第一次 | 客户端 → 服务端 | `SYN=1, seq=x`                 | “**我想建立连接，我的初始序列号是 x**” |
| 第二次 | 服务端 → 客户端 | `SYN=1, ACK=1, seq=y, ack=x+1` | “**同意，我的序列号是 y；x 我收到了**” |
| 第三次 | 客户端 → 服务端 | `ACK=1, seq=x+1, ack=y+1`      | “**y 我也收到了**”                     |

状态迁移：客户端 `SYN_SENT` → `ESTABLISHED`；服务端 `LISTEN` → `SYN_RCVD` → `ESTABLISHED`。

至于为什么必须是三次、而不是两次或四次，见第 13.1 节。

## 6. 四次挥手（断开连接）

![四次挥手与双方状态迁移](/img/tcpFourth.png)

关闭比建立多一步，原因在于 **TCP 是全双工的**：客户端不发数据了，不代表服务端也不发了，所以两个方向要各关一次。

[width(13,23,23,41)]

| 次序   | 方向            | 报文             | 状态变化                                                             |
| :----- | :-------------- | :--------------- | :------------------------------------------------------------------- |
| 第一次 | 客户端 → 服务端 | `FIN=1, seq=x`   | 客户端进入 `FIN_WAIT_1`                                              |
| 第二次 | 服务端 → 客户端 | `ACK=1, ack=x+1` | 服务端进入 `CLOSE_WAIT`，客户端进入 `FIN_WAIT_2`                     |
| 第三次 | 服务端 → 客户端 | `FIN=1, seq=y`   | 服务端进入 `LAST_ACK`                                                |
| 第四次 | 客户端 → 服务端 | `ACK=1, ack=y+1` | 客户端进入 `TIME_WAIT`（等 2MSL 后 `CLOSED`），服务端收到即 `CLOSED` |

第二次和第三次之间是一个**半关闭**状态：客户端已经不能再发数据，但服务端还能把剩下的数据发完。这就是“**挥手四次**”没法合并成三次的原因——**FIN 只表示“我这边没有新数据了”，不代表“我不能再收数据”**。

## 7. 可靠传输：序列号、确认与重传

下表中会出现两个时间量：**RTT（Round-Trip Time，往返时间）** 是一个包从发出到收到对方确认所花的时间；**RTO（Retransmission Timeout，重传超时）** 是“**发出后最多等多久还没收到确认就重发**”的时间上限。

[width(13,22,65)]

| 机制            | 解决的问题       | 做法                                                       |
| :-------------- | :--------------- | :--------------------------------------------------------- |
| 序列号 + 校验和 | 乱序、重复、损坏 | 每个字节编号，收下后按序拼接、按号去重，校验不过直接丢弃   |
| 累积确认        | 丢包             | 确认号 n 表示“**n 之前的字节我全收到了**”                  |
| 超时重传        | 丢包             | 发出后等 ACK，超过 RTO 就重发；RTO 由往返时间 RTT 动态估算 |
| 快速重传        | 丢包（不等超时） | 连续收到 3 个重复 ACK，说明中间缺了一个包，立刻重传        |
| 流量控制        | 撑爆接收方       | 用首部的窗口大小声明自己的剩余缓冲                         |
| 拥塞控制        | 压垮网络         | 发送方用拥塞窗口推断网络的承载能力                         |

## 8. 流量控制：滑动窗口

**痛点**：发送方发得太快，接收方缓存满了处理不过来，只能丢包；而丢包又会触发重传，形成恶性循环。

**机制**：接收方在每次回复 ACK 时，通过首部的 `Window Size` 告诉发送方自己剩余的缓存空间（**接收窗口 rwnd**）。发送方据此调整发送量：如果窗口为 0，就停止发送，并定期发送**窗口探测包**，等对方腾出空间。

“**滑动窗口**”这个名字的由来，是把发送方的数据看成一串连续的字节，用三个指针划出四段：

```markdown
[ 已发送且已确认 | 已发送未确认 | 可发送（窗口内） | 不可发送（窗口外） ]
↑ ↑ ↑
窗口左沿 下一个要发的位置 窗口右沿
```

收到新的确认后，窗口整体向前“**滑动**”，新的字节进入可发送区间。**窗口大小不是固定的**，它既随接收方缓存剩余空间变化，也受拥塞控制影响。

## 9. 拥塞控制：别压垮网络

流量控制管的是“**对面那台机器**”，拥塞控制管的是“**中间那张网**”。接收窗口再大，如果中间链路堵了也没用。

发送方维护一个**拥塞窗口 cwnd**，靠丢包来反推网络的承载能力。**实际能发多少 = min(接收窗口 rwnd, 拥塞窗口 cwnd)**。经典算法分四个阶段：

[width(13,56,31)]

| 阶段         | 做什么                                               | 什么时候进入             |
| :----------- | :--------------------------------------------------- | :----------------------- |
| **慢启动**   | cwnd 从 1 开始，每经过一个 RTT 翻一倍（指数级增长）  | 连接刚建立，或超时重传后 |
| **拥塞避免** | cwnd 超过阈值 ssthresh 后改为线性增长（每 RTT 加一） | cwnd ≥ ssthresh          |
| **快速重传** | 收到 3 个重复 ACK 就立刻重传丢失的包，不等超时       | 连续收到 3 个重复 ACK    |
| **快速恢复** | ssthresh 减半、cwnd 调小，直接进入拥塞避免           | 触发快速重传之后         |

关键在于**区分两种丢包信号，它们的含义完全不同**：

- **超时重传**（RTO 到期）：说明情况已经糟到连 ACK 都回不来了。TCP 反应最激烈——`ssthresh` 减半，cwnd 直接回到 1，重新慢启动。
- **3 个重复 ACK**：说明对方还在正常收包，只是中间丢了一个，属于“**轻微拥堵**”，只需把窗口减半、进入快速恢复。

现代内核早就不只用这四个经典阶段了：**CUBIC**（Linux 默认）用三次函数让窗口在接近上次拥塞点时增长得更谨慎；**BBR**（Google）**不以丢包为信号**，而是主动测量带宽和最小 RTT 来建模管道容量。

## 10. 面向字节流：粘包与拆包

**现象**：应用层发了两个小包，TCP 可能合并成一个大包发（粘包）；发了一个大包，TCP 可能拆成几个小包发（拆包）。接收端不知道数据的边界在哪。

**原因**：这不是 TCP 的缺陷，而是**面向字节流**的必然结果。TCP 只保证字节的顺序，不保证应用层的消息边界；它按 MSS 切分、按窗口发送、按拥塞窗口调速，合并与拆分都是正常行为。

浏览器里能看到完全一样的现象——`fetch` 的响应体就是这样一段没有边界的流：

```js
const reader = (await fetch('/api/stream')).body.getReader()
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  console.log(value.byteLength) // 每次多少字节？由网络决定，跟服务端写了几次无关
}
```

所以**边界只能由应用层自己建立**，常见三种做法：

:::code-group

```js [长度前缀]
// 最通用：包头用固定几个字节声明"后面还有多少字节"
// HTTP 的 Content-Length、gRPC、Protobuf 的 length-delimited 都是这个思路
function parse(buffer) {
  const messages = []
  let offset = 0
  while (offset + 4 <= buffer.length) {
    const length = buffer.readUInt32BE(offset) // 前 4 字节是长度
    if (offset + 4 + length > buffer.length) break // 还没收全，等下一批数据
    messages.push(buffer.subarray(offset + 4, offset + 4 + length))
    offset += 4 + length
  }
  return { messages, rest: buffer.subarray(offset) } // 剩下的字节留到下次
}
```

```js [分隔符]
// 用一个不会出现在内容里的字符序列划界
// HTTP 头用 \r\n、SSE 用 \n\n、NDJSON 用 \n
function parse(text) {
  const messages = []
  let rest = text
  let index = rest.indexOf('\n\n') // SSE 的消息分隔符
  while (index !== -1) {
    messages.push(rest.slice(0, index))
    rest = rest.slice(index + 2)
    index = rest.indexOf('\n\n')
  }
  return { messages, rest } // rest 可能是一条被截断的消息，留到下次
}
```

```js [定长]
// 最简单：每条消息长度固定，读满即一条
// 代价是浪费空间，且长度变化就要改协议，只适合格式极稳定的场景
const SIZE = 64
function parse(buffer) {
  const messages = []
  for (let offset = 0; offset + SIZE <= buffer.length; offset += SIZE) {
    messages.push(buffer.subarray(offset, offset + SIZE))
  }
  return { messages, rest: buffer.subarray(messages.length * SIZE) }
}
```

:::

三种做法的共同点是**缓冲区 + 边界判定 + 剩余数据留到下次**：收到数据先追加到缓冲区，能拼出完整消息就取走，拼不出就等下一批。**不要假设“一次 `read` 就是一条消息”**，这是实践中最常见的错误。

## 11. 队头阻塞与 HTTP 的演进

因为 TCP 承诺对应用层“**严格按序交付**”，**一个包丢了，排在它后面的数据即使已经到达也只能等着**——哪怕那些数据跟丢失的包毫无关系。这就是队头阻塞（Head-of-Line Blocking，HOL），也是 HTTP 版本演进的主线：

[width(19,32,49)]

| 版本          | 怎么处理队头阻塞                                     | 结果                                                       |
| :------------ | :--------------------------------------------------- | :--------------------------------------------------------- |
| HTTP/1.0      | 一条连接一个请求，用完就关                           | 握手开销巨大，所以后来有了长连接和并行连接                 |
| HTTP/1.1      | 多开几条 TCP 连接绕开（浏览器对同域名通常并发 6 条） | 治标不治本，且“**6 条**”本身成了网站优化的枷锁（域名分片） |
| HTTP/2        | 多路复用：所有请求走一条 TCP 连接                    | **反而放大了问题**：丢一个包，整条连接上的所有请求一起卡住 |
| HTTP/3 (QUIC) | 把有序性从“**整条连接**”缩小到“**每条流**”           | 一条流丢包不影响其他流，同时绕开了中间设备对 TCP 的冻结    |

这也是“**为什么已经有了 TCP，还要在 UDP 上重造一个 QUIC**”的核心答案：TCP 已经把“**整条连接严格有序**”写进了协议语义和无数中间设备的行为里，改不动了；QUIC 干脆把可靠性、加密、多路复用全部搬到用户态的 UDP 之上重新实现。

## 12. 用在哪里：典型场景与选型

### 12.1 典型应用场景

TCP 用“**握手、确认、重传、有序**”换来了一件事：**应用层可以把网络当成一条可靠的管道来读写。** 凡是需要这件事的场景，就是 TCP 的战场：

- **网页与接口请求**（HTTP/1.1、HTTP/2）：一个字节都不能错、不能少，否则页面渲染就是错的；连接复用（Keep-Alive）正是为了省掉反复握手的开销。
- **长连接与实时推送**（WebSocket、SSE）：建立在一条 TCP 连接之上，双向传输且必须按序，消息顺序就是业务语义。
- **数据库连接**：事务与查询结果不允许乱序或缺失；连接池里复用的就是 TCP 连接，池子耗尽的本质是连接数上不去。
- **服务间调用**（gRPC / RPC 框架）：请求—响应语义天然要求可靠有序；延迟敏感的部分靠连接复用和 `TCP_NODELAY` 去挤那几十毫秒。
- **文件传输与下载**（FTP、对象存储大文件、断点续传）：完整性绝对优先，慢一点可以接受——这也是它和音视频最大的区别。
- **邮件与终端**（SMTP/IMAP、SSH）：一问一答、逐条对应，任何一条命令丢失都会让后续全部错位。

反过来，**迟到就等于没有**的场景（语音、直播画面、游戏位置）不该用 TCP：等待重传的那几百毫秒，比丢一帧的代价大得多，这类场景见 [UDP 协议](/networkAndBrowsers/transport/udp)。

### 12.2 前端现象对照

[width(25,38,37)]

| 前端现象                             | TCP 层的原因                                              | 对应做法                                                 |
| :----------------------------------- | :-------------------------------------------------------- | :------------------------------------------------------- |
| 首屏慢，但服务器本身响应很快         | 每次新建连接要付 1 个 RTT 握手（HTTPS 还要叠加 TLS 握手） | 连接复用（`keep-alive`）、CDN 拉近距离、预连接           |
| 大文件下载，前几秒速度是慢慢涨上来的 | 慢启动：cwnd 从 1 开始指数增长                            | 无需处理；历史上“**域名分片**”就是为了多开几条并行慢启动 |
| HTTP/2 下，一张图片丢包拖慢整页      | TCP 的队头阻塞是**连接级**的                              | HTTP/3 + QUIC                                            |
| 弱网下偶发卡顿，一次就是 200ms 起    | 丢包后触发重传，最小 RTO 是 200ms                         | 减少往返次数、图片与接口做本地缓存                       |
| 请求发了很久也不失败，最后才报超时   | TCP 要重传十几次、十几分钟才放弃                          | 应用层自己设超时（`AbortController`、接口超时）          |

### 12.3 与 UDP 的对比

| 维度         | TCP                                                | UDP                           |
| :----------- | :------------------------------------------------- | :---------------------------- |
| **连接性**   | 面向连接（需握手）                                 | 无连接（直接发）              |
| **可靠性**   | 极高（保证不丢包、不乱序）                         | 不可靠（尽力而为，可能丢包）  |
| **传输方式** | 面向字节流（无边界）                               | 面向报文（保留边界）          |
| **首部开销** | 20–60 字节                                         | 8 字节                        |
| **控制机制** | 有流量控制与拥塞控制                               | 都没有                        |
| **通信方式** | 只能一对一                                         | 一对一、一对多（广播 / 多播） |
| **适用场景** | 网页浏览、文件下载、邮件、数据库                   | 视频会议、直播、在线游戏、DNS |
| **缺点**     | 速度慢、开销大、容易被攻击（三次握手 → SYN Flood） | 不可靠、不稳定、容易丢包      |

## 13. 常见问题 (FAQ) 与面试热点

### 13.1 为什么握手是三次，而不是两次或四次？

- **两次不行**：两次只能确认“**客户端能发、服务端能收**”，服务端无法确认“**客户端能收**”。更要紧的是，网络中可能滞留一个**早已失效的旧 SYN**：若只握手两次，服务端一收到就分配资源并建立连接，而这个连接对客户端毫无意义（SYN Flood 攻击利用的正是这一点）。第三次握手把资源开销推迟到确认之后。
- **四次没必要**：第二次和第三次都是服务端在“**同意**”，可以合并进同一个报文（`SYN+ACK`），没必要拆成两趟。

### 13.2 为什么主动关闭方要等 2MSL（TIME_WAIT）才能彻底关闭？

MSL 是“**报文在网络中能存活的最长时间**”，2MSL 就是一个来回的上限。等它有两个原因：

- **保证最后的 ACK 能送达**：如果第四次挥手的 ACK 丢了，服务端会重发 FIN，客户端在 2MSL 内可以再次回复 ACK。否则服务端会一直停在 `LAST_ACK`。
- **清理网络中的残留报文**：让本次连接产生的所有报文在网络中消亡，防止它们去干扰下一个分配了相同四元组的新连接。

### 13.3 MSS 和 MTU 是什么关系？

- **MTU**（最大传输单元）是**链路层**的限制：以太网通常是 1500 字节，指一个帧能承载的最大载荷。
- **MSS**（最大段长度）是**一个 TCP 段里能装的数据量**：`MSS = MTU − IP 首部 − TCP 首部 = 1500 − 20 − 20 = 1460` 字节（IPv6 下 IP 首部是 40 字节，所以是 1440）。
- MSS 在握手时由双方各自声明、取较小值，意义是**避免 IP 分片**：分片会让每个分片都带一份 IP 首部，而且丢一片就得整个重传。IPv6 里路由器不再允许分片，所以路径 MTU 发现（PMTUD）变得必需；如果 ICMP 被防火墙拦掉，就会出现“**小包能通、大包卡死**”的黑洞现象。

### 13.4 序列号只有 32 位，高速网络下会不会很快用完？

- **会回绕**。32 位能表示约 4.3 GB 字节；在 10 Gbps 的链路上，**4 秒钟就能发完一轮**。
- 回绕本身是允许的（序列号按模 $2^{32}$ 运算），真正的风险是“**旧连接的残留报文混进新连接**”。防它的机制是 **PAWS**：配合首部的时间戳选项，丢弃时间戳过旧的报文——这也是时间戳选项在现代内核里默认开启的原因。

### 13.5 TCP 的 Keep-Alive 和 HTTP 的 Keep-Alive 是一回事吗？

**不是，只是名字撞了**：

- **HTTP Keep-Alive**（`Connection: keep-alive`）：**应用层**的行为，一个请求响应完成后不关闭 TCP 连接，留给下一个请求复用。省下的是重复握手的开销，是性能优化手段。
- **TCP Keep-Alive**：**传输层**的保活探测。连接空闲超过 `tcp_keepalive_time`（Linux 默认 **2 小时**）后，内核发探测包确认对方还活着，连续多次无响应才关闭。目的是**探测死连接、释放资源**，不是性能优化。

### 13.6 如果直接拔掉网线，TCP 连接会立刻断开吗？

- **不会立刻断开**。拔网线是物理层行为，操作系统 TCP 层无法瞬间感知。
- 如果双方**正在发数据**，发送方会触发超时重传，重传十几次失败后才会断开（Linux 默认大约十几分钟）。
- 如果双方**空闲**，连接会一直保持，直到 TCP Keep-Alive（默认 2 小时）触发探测包，发现不通后才会断开。
