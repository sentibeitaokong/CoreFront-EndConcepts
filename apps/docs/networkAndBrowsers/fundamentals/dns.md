# DNS（域名系统）

DNS（Domain Name System，域名系统）是互联网的基础设施，被称为“**互联网的电话簿**”。它的核心作用是将人类易于记忆的**域名**(如 `www.google.com`)翻译成计算机网络通信所需的数字 **IP 地址**(如 `142.250.190.4`）。没有 DNS，我们在上网时就必须记住一长串枯燥的数字，互联网的普及和易用性将大打折扣。

**一句话理解**：**DNS 是一个分布式的、带缓存的“域名 → IP”查询系统——它的所有设计（层级、缓存、UDP、TTL）都在为同一个目标服务：让这个查询又快又不依赖任何一台中心服务器。**

## 1. 域名是怎么组织的（树状层级）

理解 DNS 的解析过程之前，先要理解域名的读法。域名是从**右往左**逐级细分的：

```markdown
                     .                        ← 根域（Root，通常省略不写，但完整域名以它结尾）
                     |
        ┌────────────┼────────────┐
       .com         .org          .cn        ← 顶级域名 TLD
        |
     example                                  ← 二级域名（你花钱注册的就是这一段）
        |

┌────┴────┐
www api ← 子域 / 主机名
```

- **完整域名 (FQDN)** 其实以一个点结尾：`www.example.com.`，最后那个点就是根域。日常书写、浏览器输入时都会省略它，但配置 DNS 记录时这个“**是否有尾点**”的差别很关键（没有尾点会被自动补上当前域）。
- **层级越靠右越“权威”**：`.com` 的管理者不关心 `example.com` 的服务器在哪，它只知道“**`.com` 下所有域名的权威服务器该去问谁**”。这种**逐级授权 (Delegation)** 是 DNS 能分布式扩展的根本原因。
- **同一个域名不同前缀可以是完全不同的主机**：`www.example.com` 和 `api.example.com` 是两条独立的记录，可以指向完全不同的服务器（甚至不同的云厂商）。
- **通配符解析**：配置一条 `*.example.com` 的记录，就能让任意前缀都命中同一个 IP，常用于多租户站点（`a.example.com`、`b.example.com`）。

## 2. DNS 的核心组件（服务器层级）

DNS 并不是一台巨大的服务器，而是一个**分布式的数据库系统**，呈现出一种倒置的树状层级结构。了解这些“**角色**”，是理解解析过程的前提：

- **DNS 客户端 (DNS Resolver/Client)**：通常是你的电脑操作系统或浏览器，负责发起 DNS 查询请求。严格说这一侧叫 **Stub Resolver（存根解析器）**——它自己什么都不会，只会把请求转给本地 DNS。
- **本地 DNS 服务器 (Local DNS Server / Recursive Resolver)**：也叫递归解析器。通常由你的网络运营商（ISP，如电信、联通）提供，或者你手动设置的公共 DNS（如 Google 的 `8.8.8.8` 或阿里的 `223.5.5.5`）。它是你设备的第一联络人，负责“**跑腿**”帮你找到最终答案。
- **根域名服务器 (Root Name Server)**：处于 DNS 树的最顶端。全球有 13 组根服务器（用 A 到 M 命名）。它们不直接知道具体域名的 IP，但它们知道所有的“**顶级域名服务器**”的地址。
- **顶级域名服务器 (TLD Name Server)**：负责管理特定的顶级域名（如 `.com`, `.org`, `.cn`）。例如，`.com` 的 TLD 服务器知道所有以 `.com` 结尾的域名的“**权威服务器**”在哪里。
- **权威域名服务器 (Authoritative Name Server)**：这是 DNS 查询的终点。它是某个具体域名（如 `baidu.com`）的实际管理者，保存着该域名下所有子域名（如 `www.baidu.com`）与 IP 地址的真实映射关系（DNS 记录）。

> [!NOTE] 为什么根服务器“只有 13 组”？
> 这是早期 DNS 的历史约束：UDP 报文限制 512 字节，而根服务器的地址列表必须能装进一个响应包里，13 组（每组约 30 字节）正好卡在这个上限内。但 **“13 组”不等于“13 台机器”**——每一组都在全球通过 **Anycast（任播）** 部署了几十到上百个镜像实例，总计数千台，用户会被路由到网络拓扑上最近的那个。所以“**13 组根服务器被打掉互联网就瘫痪**”是个流传很广的误解。

## 3. DNS 解析的详细步骤（Step-by-Step）

### 3.1 本地缓存查找

为了提高速度和减少网络负担，DNS 采用了多级缓存机制。

[width(21,23,56)]

| 缓存位置        | 由谁维护          | 说明                                                                                                                |
| :-------------- | :---------------- | :------------------------------------------------------------------------------------------------------------------ |
| 浏览器 DNS 缓存 | 浏览器自己        | 最先被查询，通常只有几十秒（Chrome 默认 60 秒），可在 `chrome://net-internals/#dns` 查看与清空                      |
| `hosts` 文件    | 你手工配置        | `Linux/macOS` 在 `/etc/hosts`，Windows 在 `C:\Windows\System32\drivers\etc\hosts`；永不过期，优先级高于一切网络查询 |
| 操作系统缓存    | 操作系统 DNS 服务 | 受记录 TTL 约束，`hosts` 与它都在本机完成，两者谁先谁后各系统实现略有差异                                           |
| 本地 DNS 服务器 | ISP 或公共 DNS    | 缓存影响面最大的一层，TTL 到期前所有用它的人都拿着同一份旧答案                                                      |

命中任何一层，解析就结束了，后面的步骤都不会发生。**“我明明改了记录怎么还不生效”绝大多数时候就是这四层缓存中的某一层还在生效**。

### 3.2 网络查询

如果在本地电脑上没找到，操作系统就会向配置的**本地 DNS 服务器 (Local DNS)** 发送查询请求。

1. **本地 DNS 缓存**：本地 DNS 服务器收到请求后，首先查自己的缓存。如果有，直接返回给用户，解析结束。
2. **向根域名服务器求助（迭代查询开始）**：如果本地 DNS 也没有缓存，它就会以客户端的身份，向**根域名服务器**发起请求：“你知道 `www.example.com` 的 IP 吗？”
3. **根服务器的指引**：根服务器查看后缀是 `.com`，回答说：“**我不知道具体的 IP，但我把管理 `.com` 的顶级域名服务器 (TLD) 的地址给你，你去问它。**”
4. **向 TLD 服务器求助**：本地 DNS 拿着地址，去问 `.com` 的 TLD 服务器：“**你知道 `www.example.com` 的 IP 吗**？”
5. **TLD 服务器的指引**：TLD 服务器查了一下，回答说：“**我不知道具体的 IP，但我知道 `example.com` 这个域名的权威域名服务器的地址，你去问它。**”
6. **向权威服务器求助（找到真理）**：本地 DNS 终于找到了 `example.com` 的权威服务器，发问：“**请告诉我 `www.example.com` 的 IP 是多少**？”
7. **权威服务器的最终答复**：权威服务器查阅自己的记录（A 记录或 CNAME 记录），发现对应的 IP 是 `192.0.2.1`，于是将这个结果返回给本地 DNS。
8. **本地 DNS 缓存并返回**：本地 DNS 收到最终的 IP 地址后，做两件事：
   - 把这个结果**存入自己的缓存**中（根据记录的 TTL 时间决定存多久），方便下次有人问。
   - 把 IP 地址**返回给你的电脑**。
9. **浏览器发起连接**：你的浏览器拿到 IP 地址 `192.0.2.1`，开始与该服务器建立 TCP 连接（三次握手），并发送 HTTP 请求，最终你看到了网页。

![DNS 解析过程中缓存查找与递归迭代查询的示意图](/img/dns.webp)

**注意一个容易被忽略的细节**：第 2–6 步里，每一次“**去问下一级**”都是**本地 DNS 自己在跑**，你的电脑从头到尾只跟本地 DNS 说了一句话。这就是递归查询与迭代查询的分界。另外，如果 CNAME 指向了别的域名（比如接了 CDN），本地 DNS 还要**顺着别名继续解析一轮**，直到拿到最终的 A 记录——这也是接 CDN 后解析变慢的常见原因。

### 3.3 查询模式

在上述过程中，包含了两种不同的查询模式：

[width(25,20,55)]

| 查询方式                 | 一句话                           | 谁在用 / 有什么后果                                                                         |
| :----------------------- | :------------------------------- | :------------------------------------------------------------------------------------------ |
| **递归查询 (Recursive)** | “**帮人帮到底**”                 | 你的电脑 → 本地 DNS。电脑只要最终 IP，本地 DNS 必须负责查出结果，查不到就报失败             |
| **迭代查询 (Iterative)** | “**我不知道，但能给你指条明路**” | 本地 DNS → 根 / TLD / 权威服务器。这些服务器通常只回“**下一步该问谁**”，让本地 DNS 自己跑腿 |

**为什么这样设计**：把“**跑腿**”这件事集中给少数本地 DNS 服务器做，根服务器和 TLD 服务器只需要回答“**指路**”这种极轻量的请求，才能扛住全球的查询量。**代价是本地 DNS 成了天然的集中点和攻击目标**——DNS 劫持、缓存污染都发生在这里。

## 4. 常见的 DNS 记录类型

[width(13,20,67)]

| 记录类型  | 全称 / 别名                           | 作用与常见用途                                                     |
| :-------- | :------------------------------------ | :----------------------------------------------------------------- |
| **A**     | Address                               | 将域名映射到 **IPv4** 地址，最常见的一条                           |
| **AAAA**  | ——                                    | 将域名映射到 **IPv6** 地址（`A` 的四倍长，故得名）                 |
| **CNAME** | Canonical Name                        | 别名记录，把一个域名指向**另一个域名**。接 CDN、接对象存储都靠它   |
| **MX**    | Mail Exchanger                        | 邮件交换记录，告诉发送方 `@example.com` 的邮件该投给哪台邮件服务器 |
| **NS**    | Name Server                           | 指明这个域名由哪几台权威服务器负责解析（逐级授权的落点）           |
| **TXT**   | Text                                  | 文本记录，通常用于 SPF（防伪造邮件）、DKIM、验证域名所有权         |
| **SRV**   | Service                               | 声明某个服务的主机和端口，微服务、SIP、部分 IM 协议在用            |
| **CAA**   | Certification Authority Authorization | 限制“**只允许哪家 CA 给你的域名签发证书**”，防证书误签发           |
| **PTR**   | Pointer                               | 反向解析：从 IP 查域名。邮件服务器反垃圾、日志分析常用             |

- **CNAME 不能与其他记录共存**：一个名字如果设了 CNAME，就不能再有 A、MX、TXT 等记录（否则解析结果有歧义）。所以 `example.com` 这个“根域名”按标准**不能**直接设 CNAME——它必须留着 NS 和 MX。想用根域名接 CDN，需要服务商支持 **CNAME 拉平 / ALIAS / ANAME** 这类变通方案。
- **CNAME 是一条链条**：`www.example.com` → `example.cdn.com` → 最终 A 记录，多一层就多一次查询。链条过长还会触发服务商的链长限制。

## 5. DNS 跑在什么协议上

DNS 的报文本可以跑在多种传输方式上，默认是 **UDP 53 端口**：

- **为什么默认用 UDP**：一次查询的请求和响应通常都能塞进一个很小的包（早期上限 512 字节），UDP 无需三次握手，省掉一个往返，延迟明显更低。
- **什么时候切换成 TCP**：响应太大装不下时，服务器会把响应头里的 **TC（Truncated）标志**置位，客户端看到后自动改用 **TCP 53** 重试；主从服务器之间同步整个区域数据（**区域传输**）时也必须用 TCP，因为要保证完整和可靠。
- **EDNS0**：它把 UDP 载荷的上限从 512 字节协商到 4096 字节，让大多数响应不必再退回 TCP，同时支持携带客户端子网。
- **加密版本**：明文 DNS 有被监听和篡改的天然缺陷，于是出现了两种加密方案——**DoT (DNS over TLS)** 使用独立的 **853 端口**，**DoH (DNS over HTTPS)** 直接把查询伪装成普通 HTTPS 流量走 **443 端口**，因此在受管控的网络里更难被单独识别和阻断。现代浏览器（Chrome、Edge、Firefox）都支持开启。

## 6. DNS 与前端、CDN 的关系

DNS 不只是“**运维的事**”，它直接决定了前端资源的加载速度和发版后的生效时间。

### 6.1 CNAME 是接入 CDN 的第一步

你在 DNS 控制台把 `www.example.com` 的 A 记录改成指向 CDN 厂商给你的调度域名（如 `example.cdnprovider.com`），后续的解析就被“**转交**”给了 CDN 的智能调度系统（见 [CDN](/networkAndBrowsers/fundamentals/cdn)）。**这一步之后，你的域名解析结果会因地区、运营商而异**，不再是一个固定 IP。

### 6.2 DNS 轮询：最朴素的负载均衡

同一个域名配多条 A 记录（如 `1.1.1.1`、`2.2.2.2`），解析时按顺序轮流传给不同用户，就是一个零成本的负载均衡方案。它的**缺点很明显**：不感知后端健康状态（一台挂了照样分配到）、不精确（本地 DNS 的缓存会让分配比例失真）。所以生产环境更常用 GSLB（全局负载均衡）替代。

### 6.3 让调度更准：GSLB 与 ECS

- **GSLB (Global Server Load Balancing)**：CDN 厂商的智能 DNS，它按用户的地理位置、所属运营商、各节点的实时负载来决定返回哪个 IP。
- **ECS (EDNS Client Subnet)**：本地 DNS 可能会用自己机房的位置去请求解析，导致 CDN 把“**上海的节点**”分给了北京的用户。ECS 允许递归解析器把用户的**真实子网**一并带上，让调度回到用户身边。

### 6.4 移动端的 HTTPDNS

在移动网络里，Local DNS 被劫持、调度不准是常态，于是出现了 **HTTPDNS**：App 不走系统 DNS，而是直接通过 HTTPS 向 DNS 服务商（或自家的解析服务）查询，拿到 IP 后自己组装请求（并在 `Host` 头里带上域名）。它绕开了运营商 Local DNS 的劫持与缓存，是移动端 App 的标配优化之一。

### 6.5 TTL(生存时间)决定了你发版/切流量的速度

- 上线前**提前调小 TTL**（比如从 3600 秒改到 60 秒），等旧 TTL 过期后再切换 IP，用户受影响的时间就从“**一小时**”缩短到“**一分钟**”。
- 切换完成后**再调回较大的 TTL**，让缓存多干活、少查询。
- 多数 DNS 服务商对免费版有 TTL 下限（常见 600 秒），想用极短的 TTL 通常要付费。

## 8. 常见问题 (FAQ) 与面试题

### 8.1 为什么 DNS 解析通常使用 UDP 协议而不是 TCP？

- **速度快，开销小**：DNS 查询和响应通常数据量很小（小于 512 字节），一个包就能装下。UDP 是无连接的，不需要像 TCP 那样进行耗时的三次握手建连过程，大大降低了延迟。
- **例外情况**：虽然通常用 UDP，但在以下情况也会**使用 TCP**：
  - 返回的响应数据包太大，超过了 512 字节（UDP 会被截断），客户端会看到 TC 标志并改用 TCP 重新发起请求。
  - DNS 服务器之间进行**区域传输**（主从服务器同步大量 DNS 数据）时，为了保证数据的可靠性和完整性，必须使用 TCP。

### 8.2 什么是 DNS 劫持？如何防止？

- **定义**：攻击者通过某种手段（如篡改路由器配置、入侵本地网络、恶意软件修改 hosts 文件），将用户的 DNS 请求拦截，并返回一个**伪造的 IP 地址**。结果就是用户本来想访问正规银行网站，却被引到了长得一模一样的钓鱼网站。
- **防范**：
  - 手动设置可靠的公共 DNS（如 114.114.114.114）。
  - 使用 **DNS over HTTPS (DoH)** 或 **DNS over TLS (DoT)** 技术。这些技术将 DNS 查询报文加密传输，防止中间人监听和篡改，现代浏览器（如 Chrome, Edge）已经支持开启此功能。
  - 移动端 App 采用 **HTTPDNS**，从根上绕开运营商 Local DNS。

### 8.3 什么是 DNS 缓存污染（DNS Cache Poisoning）？

- 与劫持类似，但污染是针对**本地 DNS 服务器**的攻击。攻击者向本地 DNS 服务器注入一条伪造的 DNS 记录。由于本地 DNS 会缓存记录，这会导致该区域内所有使用这个本地 DNS 的用户，在访问特定域名时都被引导至错误的 IP。
- **为什么难防**：DNS 用的是无连接的 UDP，服务器无法确认响应是否真的来自权威服务器，早期只要伪造的响应先到就会被采信。现代防护手段包括**随机化查询源端口与事务 ID**、**0x20 编码**，以及 **DNSSEC**——用数字签名证明“**这条记录确实来自权威服务器**”。

### 8.4 常见的 DNS 记录类型有哪些？

最需要记住的是四条：**A / AAAA 给地址、CNAME 给别名、MX 管邮件、NS 管授权**。

### 8.5 TTL 是什么意思？

- **TTL (Time To Live)**：生存时间。在 DNS 记录中，它表示这条记录在本地 DNS 或客户端缓存中可以**存留的时间**（单位通常是秒）。
- TTL 设置得越**大**，缓存命中率越高，解析速度越快，DNS 服务器压力越小；但如果 IP 发生变更，生效时间就越慢。
- TTL 设置得越**小**，IP 变更生效越快；但会增加 DNS 解析的请求频率和延迟。

### 8.6 为什么有时候修改了域名的解析，但电脑上还是访问旧的 IP？

- 这就是**缓存**在作祟。修改权威服务器上的记录后，全球各地的本地 DNS 服务器并不会立刻知道，它们会继续使用自己缓存里的旧 IP，直到旧记录的 TTL 时间过期。
- **解决办法**：
  - 等待 TTL 过期（通常几十分钟到几小时不等）。
  - 在自己电脑上执行命令强制刷新本地缓存：Windows 打开 cmd 输入 `ipconfig /flushdns`；Mac 打开终端输入 `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`。
  - 浏览器那一层也没刷新的话，用无痕窗口或到 `chrome://net-internals/#dns` 手动清空。
- **上线前的正确姿势**：先把 TTL 调小，等旧缓存过期，再切换 IP。

### 8.7 DNS 解析失败该怎么排查？

按查询顺序逐层验证，命令都很短：

```bash
# 1. 本机配置的是哪个 DNS 服务器（以及 hosts 里有没有被写死）
cat /etc/resolv.conf && cat /etc/hosts

# 2. 换一个公共 DNS 直接问，绕开本机与运营商
dig @8.8.8.8 www.example.com +short

# 3. 只看解析结果（nslookup 在 Windows 上更顺手）
nslookup www.example.com

# 4. 逐级追踪：从根开始，看是哪一级没有给出答案
dig +trace www.example.com

# 5. 看 CNAME 链有没有断（接了 CDN 之后最常出问题的地方）
dig +noall +answer www.example.com CNAME
```

判断口诀：**`dig @8.8.8.8` 能通、本机不通 → 是本机或运营商的问题；`dig +trace` 在某级断掉 → 是那一级的配置问题；哪里都能解析出 IP 但访问不了 → 问题不在 DNS，回到连接层面排查。**

### 8.8 为什么根域名服务器只有 13 组，却不会成为瓶颈？

因为它从来不是“**13 台机器**”在扛流量：每一组都通过 **Anycast（任播）** 在全球部署了上百个镜像实例，用户请求会被路由到**拓扑上最近的实例**；而且根服务器只在缓存未命中、且本地 DNS 也不知道 TLD 地址时才会被问到，绝大多数请求在 TLD 或缓存层就被消化了。**Anycast 还有一个副作用是天然抗 DDoS**：攻击流量会被分散到全球各地，而不是集中打一台机器。
