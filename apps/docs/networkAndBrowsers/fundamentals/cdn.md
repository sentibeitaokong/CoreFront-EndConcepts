# CDN（内容分发网络）

CDN 的全称是 **Content Delivery Network（内容分发网络）**。如果说 DNS 是互联网的电话簿，那么 CDN 就是互联网的 **“全球快递系统”**。

CDN 的核心思想是：**“就近原则”**。它将你网站上的内容（如图片、视频、JS/CSS 文件）**复制并缓存到全球各地的“边缘节点”（缓存服务器）上**。当用户访问网站时，系统会自动分配离该用户物理距离最近、网络状态最好的节点来提供服务。

**一句话理解**：**CDN 用“把内容提前搬到离用户最近的地方 + 替你挡住绝大部分流量”这两件事，同时换来了更快的用户和更安全的源站。**

## 1. CDN 的核心组件与原理

从技术实现的角度来看，CDN 系统主要由三个核心部分协同工作：

- **分布式缓存节点 (Edge Nodes)**：这是 CDN 的物理基础，遍布全球的机房中。它们负责存储网站内容的副本，并直接响应最终用户的请求。
- **智能路由与调度系统 (Global Server Load Balancing, GSLB)**：这是 CDN 的大脑。它通过分析用户的 IP 地址（通常是用户的 Local DNS IP，配合 **ECS** 拿到更精确的子网信息）、网络拥堵情况、各节点的负载状态，**实时计算并为用户分配一个最优的边缘节点**。
- **回源机制 (Origin Pull)**：这是 CDN 与源站（你自己的服务器）之间的纽带。当用户请求的内容在边缘节点上不存在（未缓存）或已过期时，节点会主动向源站请求最新的内容，并将其缓存下来，以便后续用户访问。

**调度为什么能“找到最近的节点”**：这一步发生在 DNS 阶段而不是连接阶段——你的域名被 CNAME 到 CDN 的调度域名后，CDN 的 GSLB 直接**返回一个离你最近的节点 IP**，你的浏览器从头到尾只知道自己连了一个“**普通 IP**”。所以 CDN 不需要客户端配合，也不改变 HTTP 的任何语义，这也是它能无痛接入任何网站的原因。

## 2. CDN 加速的详细步骤（工作流程）

假设你的网站 `www.example.com` 接入了 CDN，用户在浏览器中输入这个网址，完整的请求流程如下：

1. **用户发起请求**：浏览器尝试解析 `www.example.com` 的 IP 地址。
2. **CNAME 引导**：因为你接入了 CDN，你在域名的 DNS 设置中，将 `www.example.com` 的 A 记录改成了 **CNAME 记录**，指向了 CDN 服务商提供的一个域名（如 `example.cdnprovider.com`）。
3. **智能 DNS 调度**：用户的 Local DNS 向 CDN 提供商的智能 DNS（GSLB）发起解析请求。GSLB 根据用户的地理位置、网络运营商（ISP）等信息，**挑选一个离该用户最近、负载最轻的 CDN 节点 IP**，并将其返回给用户的浏览器。
4. **就近访问**：浏览器拿到 CDN 节点的 IP 后，直接向该节点发起 HTTP 请求。
5. **节点处理请求（分两种情况）**：
   - **缓存命中 (Cache Hit)**：如果该节点上已经缓存了用户请求的文件（例如一张热门图片），节点会**直接将文件返回给用户**。此时，请求根本没有到达你的源站服务器，速度极快。
   - **缓存未命中 (Cache Miss) / 回源 (Origin Pull)**：如果该节点上没有这个文件，或者文件已过期，节点就会向你的**源站服务器 (Origin Server)** 发起请求，获取最新的文件。节点拿到文件后，一边将其返回给用户，一边**存入自己的缓存中**，以备下一次请求。

![CDN 边缘节点缓存命中与回源的请求流程示意图](/img/cdn.png)

**回源率与命中率**：命中数 ÷ 总请求数就是**命中率**，剩下的部分就是**回源率**。命中率是衡量 CDN 配置好坏的第一指标，也是成本指标——每一次回源都要消耗源站带宽。

## 3. 静态加速、动态加速与边缘计算

现代 CDN 不仅仅能缓存静态文件，还发展出了全站加速技术：

- **静态内容加速**：针对图片、CSS、JS 文件、视频等**不经常变动**的内容。原理就是上面提到的**缓存**。这是 CDN 最基础、最强大的功能。
- **动态内容加速**：针对 HTML 页面、API 接口（如登录请求、获取购物车信息）等**因人而异、实时变化**的内容。这些内容**不能被缓存**（因为每个人的数据不同）。CDN 加速动态内容的原理是**智能路由优化**和**协议优化**。CDN 节点虽然不缓存内容，但它会利用 CDN 提供商内部的优质私有专线，避开公网的拥堵路段，以最快、最稳定的路径将请求转发给源站，并将响应送回给用户。
- **协议优化**：对动态内容，CDN 还会替你做长连接复用、TLS 握手优化（会话复用、0-RTT）、开启 HTTP/2 或 HTTP/3（QUIC）。**用户到 CDN 节点这一段走最优协议，节点到源站那一段走专线**——这就是“**全站加速**”的完整含义。
- **边缘计算**：把一小段你的代码（边缘函数 / Serverless）直接跑到边缘节点上，例如改写响应头、做 A/B 分流、鉴权、图片实时裁剪。它让一部分“**原本必须回源**”的动态逻辑也不必回源了——这是 CDN 从“**缓存**”走向“**计算**”的一步。

## 4. 缓存层级与缓存策略

一次请求可能穿过好几层缓存，任何一层命中都算“**没回源**”：

[width(22,20,58)]

| 层级              | 位置           | 特点                                                       |
| :---------------- | :------------- | :--------------------------------------------------------- |
| 浏览器缓存        | 用户设备       | 最快，**完全不受 CDN 控制**，只认响应头里的缓存指令        |
| 边缘节点          | 用户所在城市   | 命中即返回，是 CDN 加速的主力                              |
| 中间层 / 父层节点 | 区域中心       | 边缘没命中时先问它，避免所有节点都直奔源站（回源率的关键） |
| 源站              | 你自己的服务器 | 每一层都没命中时才轮到它，成本最高                         |

**缓存能活多久、能不能被缓存，全部由响应头决定**（这是前端可以直接控制的）：

[width(31,69)]

| 响应头 / 指令                     | 作用                                                                 |
| :-------------------------------- | :------------------------------------------------------------------- |
| `Cache-Control: max-age=31536000` | 浏览器与 CDN 都缓存这么久（带 hash 的静态资源适合一年）              |
| `s-maxage`                        | **只针对 CDN 这类共享缓存**的存活时间，可覆盖 `max-age`              |
| `no-store`                        | 完全不缓存，每次必回源（登录接口、支付页面）                         |
| `no-cache`                        | 可以存，但每次用之前必须回源校验新鲜度（注意名字有误导性）           |
| `private`                         | 只允许浏览器缓存，**CDN 不许缓存**（用户个人信息必须加这个）         |
| `stale-while-revalidate`          | 先用旧内容顶上、后台顺便去更新，兼顾速度与新鲜度                     |
| `ETag` / `Last-Modified`          | 配合 `If-None-Match` 使用，源站返回 `304` 表示“**没变，用你本地的**” |

- **刷新 (Purge / Refresh)**：告诉 CDN 强行丢掉某些 URL 的缓存副本，用于“**发版后发现内容不对**”的应急。刷新是异步的，全网生效需要一点时间，且有些厂商对免费额度有限制。
- **预热 (Preload)**：提前把资源推送到各边缘节点，让第一批用户也能命中。常用于大促或热点内容发布。

## 5. CDN 的核心优势

- **极速的用户体验**：大幅降低网络延迟，网页秒开，视频不卡顿。
- **降低源站压力与带宽成本**：CDN 替源站挡住了 80%~90% 以上的静态资源请求，源站服务器的 CPU 和带宽压力骤减，通常能节省大量服务器成本。
- **高可用性与负载均衡**：即使某个 CDN 节点宕机，智能路由也会自动将流量切换到其他健康节点；很多 CDN 还支持多源站与故障自动切换。
- **安全防护 (缓解 DDoS 攻击)**：CDN 拥有海量的带宽储备和分布式的架构。当面临 DDoS 攻击（如海量的恶意垃圾流量）时，这些流量会被分散到全球的 CDN 节点上消化掉，从而保护了脆弱的源站服务器免受崩溃。许多 CDN（如 Cloudflare、阿里云）还内置了 WAF（Web 应用防火墙）功能。
- **隐藏源站 IP**：用户的请求只打到节点，源站真实 IP 不对外暴露，攻击者连“**打哪里**”都要先想办法找出来。

## 6. 前端接入 CDN 的实践要点

### 6.1 用文件名哈希，而不是刷新缓存

打包时给静态资源名加上内容哈希（如 `app.v1a2b.js`），内容一变文件名就变，浏览器和 CDN 都会去拿新文件，**旧的缓存自然“过期”**。这是唯一不需要人工介入、也不会出错的发版方式。

### 6.2 别让 URL 带随机参数

`?t=12345` 这类“**随手加个时间戳防止缓存**”的写法，会让 CDN 认为每个请求都是新文件，命中率直接归零（对应 2 节说的缓存键）。真需要绕过缓存时，应该走刷新流程，或在 CDN 控制台开启“**忽略参数缓存**”。

### 6.3 主站与静态资源分域名

把静态资源放在 `static.example.com` 而不是 `www.example.com`，有两个好处：**一是 Cookie 隔离**（主站的 Cookie 不会跟着每个图片请求发出去，省流量），**二是突破浏览器同域并发连接数限制**。跨域引用字体、`fetch` 资源时记得在 CDN 侧配置 `Access-Control-Allow-Origin`，否则会踩到 CORS。

### 6.4 HTTPS 证书配在 CDN 侧

用户到节点这一段由 CDN 终止 TLS（**TLS 卸载**），证书要上传到 CDN 控制台而不是只在源站配；节点到源站那一段可以选择回源协议（HTTP / HTTPS）。**只改了源站证书却忘了 CDN，表现就是浏览器依旧报证书错误。**

### 6.5 区分「浏览器缓存」与「CDN 缓存」

调试时最常犯的错是把两者混为一谈：本地 `Ctrl+Shift+R` 强刷**只清浏览器那一层**，CDN 节点上的旧副本一个字节都没动。排查“**我明明发布了新代码**”时，要先确认你看到的是节点返回的旧文件，还是浏览器自己留的旧文件（看响应头的 `Age`、`X-Cache: HIT/MISS` 之类字段最快）。

## 7. 常见问题 (FAQ) 与面试题

### 7.1 什么是 CDN 的“命中率”？为什么命中率低？

- **命中率**：指用户请求的内容直接由 CDN 节点响应（未回源）的次数占总请求次数的比例。命中率越高，说明 CDN 效果越好。
- **命中率低的原因**：
  - 缓存配置错误（如设置了不缓存、或者缓存过期时间 `max-age` 设置得太短）。
  - 大量用户访问了冷门资源（节点上没有）。
  - URL 中带有随机参数（如 `?t=12345`），导致 CDN 认为每次都是新请求而频繁回源（可以在 CDN 控制台开启“**忽略参数**”功能）。
  - 刚刷新了 CDN 缓存。
  - 响应头写了 `private` / `no-store`，或没写任何缓存指令而源站又被配置成不缓存。

### 7.2 前端发版了新代码，用户看到的还是旧页面，怎么办？（CDN 缓存刷新）

因为新代码被缓存在了 CDN 节点上且未过期。解决方法有：

- **最佳实践（工程化）**：前端打包时，给静态文件名加上哈希值（如 `app.v1a2b.js`）。发版后文件名变了，浏览器和 CDN 就会去请求新文件，旧文件自然失效。
- **手动刷新/预热**：登录 CDN 提供商的控制台，手动提交需要 **清除缓存（Purge/Refresh）** 的 URL 或目录。CDN 会强制全网节点删除旧副本。
- **别忘了 HTML**：`index.html` 通常不带 hash，最容易被缓存在节点上，所以它应该是**短缓存或不缓存**的，这样它才能及时引用到新的带 hash 资源。这也是“**前端发版后用户还是旧页面**”的头号原因。

### 7.3 CNAME 记录在 CDN 中起什么作用？

CNAME（别名记录）是接入 CDN 的关键一步。它将你自己的域名（如 `www.test.com`）指向了 CDN 厂商分配给你的调度域名（如 `test.cdn.aliyun.com`）。这样，当用户解析你的域名时，DNS 请求就会被“**转交**”给 CDN 的智能调度系统，由它来分配最优的节点 IP。

### 7.4 什么是“第一公里”问题？

在互联网术语中，“第一公里”是指服务器连接到互联网骨干网的这一段链路。由于带宽限制或跨网互联（如电信访问联通服务器），这通常是网络传输中最容易出现瓶颈的地方。CDN 通过在全球部署节点，把内容推送到离用户最近的“**最后一公里**”，从而完美绕过了“**第一公里**”的拥堵。

### 7.5 CDN 和负载均衡（Load Balancer, LB）有什么区别？

两者都用于分发流量，但场景和层级不同：

- **CDN**：是**广域网（全球/全国）级别**的分发。通过地理位置分布缓存内容，解决物理距离带来的延迟问题。
- **负载均衡 (LB)**：通常是**局域网/数据中心级别**的分发。在源站机房内部，将请求均匀地分配给后端的 10 台或 100 台服务器，解决单台服务器算力不足的问题。两者经常结合使用（CDN 负责边缘，LB 负责源站核心）。

### 7.6 CDN 缓存了错误响应怎么办？

源站短时间故障时返回的 `404`、`5xx` 也可能被节点缓存下来，形成“**源站已经恢复、用户却还在看错误页**”的雪上加霜。**做法**：在 CDN 控制台把错误状态码的缓存时间设为 0 或很短（大多数 CDN 默认就不会长期缓存 5xx，但要确认），并给静态资源配好回源重试与备用源站。

### 7.7 为什么 CDN 上也要开 HTTP/2 或 HTTP/3？

因为用户到节点的这一段是**延迟最敏感**的一段：HTTP/2 的多路复用能让几十个静态资源共用一个连接，省掉大量握手；HTTP/3 基于 QUIC，在弱网、切换网络时表现更好，且建立连接更快。CDN 厂商通常一键开启，属于零成本的提速手段。

### 7.8 域名解析到 CDN 后，为什么 `curl` 拿到的是 IP，但 `ping` 却不通？

`ping` 用的是 **ICMP**，而 CDN 节点普遍**不响应 ICMP**（避免被用来做探测和放大攻击），这并不代表节点不可用——用 `curl -I` 或 `curl -v` 看 HTTP 响应才准确。另外 CDN 会按地区返回不同 IP，你本机 ping 到的地址和其他人的未必是同一个，用它来“**验证 CDN 有没有生效**”本身就是个错误的方法。
