# JavaScript 脚本的异步加载

浏览器解析 HTML 时，默认的 `<script>` 标签是「**同步、阻塞**」的：遇到脚本会暂停解析、下载并执行脚本，然后再继续解析。异步加载则让**脚本的下载过程不阻塞 HTML 的解析**，从而缩短首屏时间、提升页面性能。

## 1. 默认的同步脚本（阻塞解析）

不写任何属性时，`<script src="...">` 的行为如下：

1. 浏览器解析 HTML，遇到 `<script>` 标签后**暂停解析**。
2. 开始下载脚本，下载期间**继续阻塞**（什么都不做）。
3. 下载完成后**立即执行**脚本。
4. 执行完毕后，才**继续解析**后面的 HTML。

```html
<script src="jquery.js"></script>
<script src="app.js"></script>
```

> 这就是为什么传统做法会把 `<script>` 放到 `<body>` 底部——等 DOM 解析完再下载执行，避免阻塞首屏渲染。但这样脚本的下载时机被推迟了，仍有性能损耗。

## 2. 异步加载的三种方式

异步加载让脚本的下载「并行」进行，不阻塞 HTML 解析。主要有三种方式：

![defer 与 async 异步加载的时序图](/img/asyncSecond.png)

### 2.1 `defer` 属性

![defer 加载时序图](/img/asyncThird.png)

`defer` 属性告诉浏览器**立即下载**脚本，但**延迟执行**：

```html
<script src="script1.js" defer></script>
<script src="script2.js" defer></script>
```

**工作方式**

- **并行下载**：浏览器看到 `defer` 脚本，会立即在后台开始下载它，同时继续解析和渲染页面的其他部分。
- **延迟执行**：脚本的执行会等到整个 HTML 文档被完全解析完毕（`DOMContentLoaded` 事件触发之前）才开始。
- **顺序执行**：多个 `defer` 脚本会**按照在 HTML 中出现的顺序**依次执行，`script1.js` 一定在 `script2.js` 之前执行。

**适用场景**

- 脚本执行依赖整个 DOM 结构（例如需要操作页面上的所有元素）。
- 多个脚本之间有依赖关系，需要保证执行顺序。

### 2.2 `async` 属性

![async 加载时序图](/img/asyncFourth.png)

`async` 属性告诉浏览器也**立即下载**脚本，但下载完成后**立即执行**：

```html
<script src="scriptA.js" async></script>
<script src="scriptB.js" async></script>
```

**工作方式**

- **并行下载**：和 `defer` 一样，浏览器会立即在后台下载脚本，不阻塞页面渲染。
- **立即执行**：一旦脚本下载完成，浏览器会**立即暂停 HTML 解析**执行该脚本，执行完再继续解析。
- **乱序执行**：多个 `async` 脚本的执行顺序是**不可预测的**，哪个先下载完哪个先执行，`scriptB.js` 完全可能在 `scriptA.js` 之前执行。

**适用场景**

- 脚本完全独立，不依赖 DOM，也不依赖其他脚本。
- 例如：网站分析工具、广告脚本、独立的第三方库。

### 2.3 动态创建 `<script>` 标签

还可以用 JavaScript 动态创建 `<script>` 元素并添加到文档中，这也是一种异步加载方式：

```js
// 创建一个新的 <script> 标签
const script = document.createElement('script')
script.src = 'my-dynamic-script.js'

// 将其添加到 <head> 或 <body>
document.head.appendChild(script)
```

**工作方式**

- 这种方式创建的脚本，其行为在现代浏览器中**类似于 `async`**：下载和执行都是异步的，下载完成后立即执行，不保证执行顺序。
- 默认不会阻塞页面的解析和渲染。
- 如果希望动态脚本**按顺序执行**，可手动设置 `script.async = false`：

  ```js
  script.async = false
  ```

**适用场景**

- 需要根据条件或在特定时机才决定是否加载脚本，例如用户点击按钮后才加载某个功能模块（按需加载 / code splitting）。

## 3. 三种方式对比

| 特性               | 默认（无属性）   | `defer`                                 | `async`                  | 动态创建                 |
| :----------------- | :--------------- | :-------------------------------------- | :----------------------- | :----------------------- |
| **下载时是否阻塞** | 是（下载也阻塞） | 否                                      | 否                       | 否                       |
| **执行时是否阻塞** | 是               | 否（等 DOM 解析完）                     | 是（下载完立即执行）     | 是（下载完立即执行）     |
| **执行时机**       | 下载后立即执行   | DOM 解析完毕后、`DOMContentLoaded` 之前 | 下载完毕后立即执行       | 下载完毕后立即执行       |
| **执行顺序**       | 按出现顺序       | 按 HTML 中出现的顺序                    | 乱序（谁先下完谁先执行） | 乱序（谁先下完谁先执行） |

## 4. ES Module 脚本

ES Module（`<script type="module">`）默认就是**延迟执行**的，行为与 `defer` 类似：

- 模块脚本默认**异步下载**，不阻塞 HTML 解析。
- 在 HTML 解析完成后（`DOMContentLoaded` 之前）按顺序执行。
- 因此 `type="module"` 通常**不需要**再额外加 `defer`。

```html
<script type="module" src="main.js"></script>
```

## 5. 经验法则

- **`defer` 是首选**：兼顾性能和可预测的执行顺序，是大多数场景的最佳选择。
- **`async` 用于独立脚本**：与主应用逻辑无关、无依赖的脚本（统计、广告等）用 `async`。
- **动态创建用于按需加载**：需要更灵活地控制加载时机（如路由级懒加载）时使用。
- **`type="module"` 自带延迟**：使用 ES Module 时无需再加 `defer`。
