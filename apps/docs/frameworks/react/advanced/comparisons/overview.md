# React 与 Vue 3 核心架构与设计取舍

React 和 Vue 3 的终极目标高度一致：将声明式的 UI 描述高效地映射到宿主平台（如 DOM）。然而，两者在实现这一目标时，采取了截然不同的架构哲学：**React 走向了“重度运行时调度”的拉（Pull）模型，而 Vue 3 走向了“编译期优化 + 细粒度响应式”的推（Push）模型。**

```markdown
React：JSX → React Element (不可变快照) → Fiber 协调 (多优先级、可中断) → Commit (统一同步提交) → 宿主节点
Vue 3：Template/JSX → 附带编译标记的 VNode → 细粒度响应式更新与靶向 patch (同步或微任务批处理) → 宿主节点
```

## 1. React 架构

### 1.1 从 JSX 到 React Element：不可变 UI 快照

React 组件通过 JSX 描述 UI，JSX 在编译后调用 `jsx()` 或 `createElement()` 生成 **React Element** —— 一个轻量、不可变的普通对象，它只包含 `type`、`props`、`key`、`ref` 等描述信息，不携带任何运行时状态。

Element 的不可变性是 React 整个架构的基石：它使得 React 可以在内存中安全地反复构建新的 UI 描述，而无需担心副作用污染。每次状态变化都会生成一棵全新的 Element 树，随后进入协调（Reconciliation）流程。

### 1.2 Fiber 架构：用户态协程与可中断渲染

为了突破早期递归 diff 无法中断的性能瓶颈，React 16 重构了协调引擎，引入了 **Fiber 架构**。Fiber 是对递归调用的模拟，它将原本隐式的调用栈显式化为可遍历的链表结构，使得渲染过程可以**分段执行、暂停、恢复甚至废弃**，
每个 Fiber 节点是一个 JavaScript 对象，承载了多重职责：

- **拓扑指针**：通过 `child`、`sibling`、`return` 形成可遍历的树，支持深度优先遍历。
- **状态容器**：存储组件实例、Hooks 链表（`memoizedState`）、更新队列（`updateQueue`）等运行时状态。
- **副作用标记**：`flags` 与 `subtreeFlags` 记录节点及其子树需要执行的 DOM 操作（增、删、改）。
- **优先级信息**：`lanes` 与 `childLanes` 用于表达任务优先级，参与调度决策。
- **双缓冲关联**：`alternate` 指针连接当前树（current）与工作树（workInProgress），实现无锁切换。

Fiber 架构使 React 能够将渲染拆分为多个工作单元（每个 Fiber 节点就是一个单元），并通过 **工作循环（Work Loop）** 驱动执行。在并发模式下，每处理完一个单元，都会检查 `shouldYield()`，如果时间切片用尽或存在更高优先级任务，则主动让出主线程，待下一帧继续。

### 1.3 调度器与 Lane 模型：优先级驱动的任务管理

React 的调度器（Scheduler）独立于渲染器，负责管理所有更新任务的优先级和执行时机。它基于 **Lane 模型**（位掩码）来表示优先级，每个更新都会被赋予一个 Lane，Lane 之间支持合并、相交和包含关系。

调度器通过以下步骤决定任务的执行：

- **入队与冒泡**：`setState` 或 `dispatch` 产生的更新被挂在对应 Fiber 的更新队列中，同时沿 `return` 路径向上冒泡，将 Lane 合并到父级节点的 `childLanes`，最终汇总到根节点。
- **确定优先级**：`ensureRootIsScheduled` 从根节点的 `pendingLanes` 中选出最高优先级的 Lane，作为本次渲染的目标优先级。
- **选择调度方式**：如果目标优先级是同步（SyncLane），则直接执行 `performSyncWorkOnRoot`（不可中断）；否则通过 Scheduler 以时间切片方式调度 `performConcurrentWorkOnRoot`。
- **中断与恢复**：高优先级任务可以抢占低优先级任务，后者会被中止并在未来重试（基于保存的 `baseState` 和 `baseQueue` 重放更新）。

### 1.4 双缓冲与提交阶段

React 在内存中维护两棵 Fiber 树：**current**（当前屏幕显示）与 **workInProgress**（正在构建的新树）。两者通过 `alternate` 指针关联，形成“**双缓冲**”模式。

- **Render 阶段**：在 workInProgress 树上执行 `beginWork` / `completeWork`，构建新的 Fiber 树并收集副作用，这一阶段可中断。
- **Commit 阶段**：一旦 workInProgress 树完成，进入不可中断的提交阶段，依次执行 DOM 突变（mutation）、布局副作用（useLayoutEffect）等，最后将 `root.current` 指向 workInProgress，完成切换。

## 2. Vue 3 架构

### 2.1 模板编译与 VNode 优化

Vue 3 同样使用 VNode 作为 UI 描述单元，但它在编译模板时，利用模板的结构确定性注入了大量优化信息，使得运行时的 patch 过程能够“**按图索骥**”,
编译阶段的关键优化包括：

- **静态提升**：完全静态的 VNode 被提升到渲染函数外部，后续渲染直接复用，避免重复创建和 diff。
- **PatchFlags**：为每个动态 VNode 标记动态属性类型（如 `TEXT`、`CLASS`、`STYLE`、`PROPS`），运行时 patch 时只需检查这些标志，跳过静态属性比较。
- **Block Tree**：编译器将模板中的动态节点收集到 `dynamicChildren` 数组中，更新时渲染器只遍历该数组，实现靶向更新，跳过整个静态子树。

VNode 本身是轻量对象，除了 `type`、`props`、`children` 外，还携带 `shapeFlag`（快速类型断言）、`patchFlag`、`dynamicProps` 等编译期元数据。

### 2.2 响应式系统：Proxy 与 ReactiveEffect

Vue 3 的响应式系统是整个框架的“心脏”。它基于 ES6 `Proxy` 拦截对象的读写操作，配合 `ReactiveEffect` 类实现依赖收集与触发。

- **依赖收集（track）**：当组件渲染函数或 `watch` 回调执行时，会创建一个 `ReactiveEffect` 实例并标记为当前激活的 `activeEffect`。在渲染函数中访问响应式数据的 getter 时，`track` 函数将当前 `activeEffect` 添加到该数据的依赖集合（Dep）中。
- **依赖触发（trigger）**：当响应式数据变化时，其 setter 调用 `trigger`，遍历 Dep 中的所有 Effect，并执行其 `scheduler` 或 `run` 方法。
- **组件渲染 Effect**：每个组件的渲染函数被包装成一个 `ReactiveEffect`，在挂载时执行一次并收集依赖。当依赖数据变化时，该 Effect 的 `scheduler` 被触发，将组件更新任务推入调度器队列。

响应式系统的“**推**”（Push）模型确保了更新是**点对点**的 —— 只有真正依赖了变化数据的组件才会被重新渲染，无需像 React 那样自顶向下遍历整棵树。

### 2.3 组件实例与更新机制

Vue 3 的组件运行时由 `ComponentInternalInstance` 承载，它独立于 VNode 存在，保存了组件的状态（`setupState`）、props、attrs、slots、生命周期钩子以及一个指向其渲染 Effect 的 `update` 字段。

当组件需要更新时，`update` 函数被调度执行，内部会重新调用渲染函数生成新的子树 VNode，然后执行 `patch` 过程，将新 VNode 与旧 VNode 进行比较并应用最小 DOM 变更。

### 2.4 调度器：微任务批处理

Vue 3 的调度器（Scheduler）负责管理所有异步更新任务，其核心是基于 `Promise.resolve().then()` 的微任务队列。

- 当响应式数据变化触发组件 Effect 的 `scheduler` 时，该 Effect 会被加入到调度器的 `pending` 队列。
- 在同一个微任务中，多次数据变化产生的多次入队会被合并，最终只触发一次批量更新。
- 调度器还提供了 `nextTick` API，允许开发者在 DOM 更新后执行回调。

与 React 的时间切片不同，Vue 3 的组件更新是**同步且不可中断**的（在单个微任务内完成），因此不存在可抢占的并发渲染，但也因此避免了复杂的状态回退和重放逻辑，使得运行时更轻量、易理解。

## 3. 核心机制对比总结

| 机制维度         | React (Fiber 架构)                                    | Vue 3 (响应式 + 编译优化)                                  |
| ---------------- | ----------------------------------------------------- | ---------------------------------------------------------- |
| **UI 描述**      | React Element（不可变）                               | VNode（携带编译优化标记）                                  |
| **状态存储**     | Fiber 节点的 Hooks 链表 / Class 实例                  | ComponentInternalInstance 的 `setupState`、`props` 等      |
| **更新触发**     | `setState` / `dispatch` 显式触发，自顶向下协调        | 响应式数据变化自动触发，自下而上点对点更新                 |
| **任务调度模型** | 基于 Lane 的优先级调度，可中断、可抢占                | 基于微任务的批处理，单次更新不可中断                       |
| **并发渲染**     | 原生支持（时间切片 + 可中断恢复）                     | 不支持（组件更新同步完成）                                 |
| **更新传播路径** | 从触发点向上冒泡到根，再从根向下遍历整棵 Fiber 树     | 直接从数据变化触发依赖组件 Effect，仅更新该组件及其子树    |
| **双缓冲**       | 有（current ↔ workInProgress，通过 `alternate` 连接） | 无（更新时直接修改现有 DOM，比较前后 VNode 打补丁）        |
| **DOM 更新策略** | 收集副作用（flags），在 Commit 阶段一次性批量执行     | `patch` 过程中直接调用 DOM API，边比较边更新               |
| **性能优化手段** | 跳过策略（memo、shouldComponentUpdate）、优先级调度   | 编译优化（静态提升、PatchFlags、Block Tree）、依赖粒度控制 |
| **学习曲线**     | 较陡（需要理解 Fiber、并发、优先级）                  | 较平缓（响应式直观，但深入需理解 Proxy 和 Effect）         |

## 4. 设计哲学与取舍

React 和 Vue 3 在核心理念上高度一致——都追求声明式 UI、组件化、跨平台——因此它们在"**做什么**"上趋同。真正的分歧在于"**怎么做**"以及"**把复杂性放在哪里**"：React 将复杂性集中在**运行时（Fiber / 协调 / 调度）**，Vue 3 则将复杂性前移到**编译期与响应式系统**。下表从设计哲学与取舍的维度，对两者做对照：

| 取舍维度             | React                                                                     | Vue 3                                                             |
| -------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **核心设计哲学**     | "**UI 是状态的纯函数**"，每次渲染都是一次从头计算，靠运行时协调保证正确性 | "**数据驱动视图**"，以响应式系统精确追踪依赖，靠靶向更新保证效率  |
| **复杂性放置位置**   | 运行时：Fiber、协调、调度器、Lane 模型                                    | 编译期 + 响应式：模板编译标记、Proxy 依赖收集、靶向 patch         |
| **换来的核心收益**   | 跨平台能力、原生并发（时间切片/可中断）、完整的 JS 表达能力               | 运行时轻量、点对点更新、更自然的响应式、更小的包体积              |
| **付出的主要代价**   | 运行时开销大、需手动优化（`useMemo`/`useCallback`）、心智负担重           | 模板结构化约束、缺乏并发能力、响应式系统边界（异步/循环依赖）复杂 |
| **优化依赖**         | 开发者手动优化 + 优先级调度（`React Compiler` 正逐步自动记忆化）          | 编译器自动注入优化标记，对开发者几乎透明                          |
| **更新语义**         | 自顶向下协调，即便简单更新也可能遍历整棵树（有跳过机制）                  | 自下而上点对点，只更新依赖了变化数据的组件及其子树                |
| **对开发者的暴露面** | 暴露优先级、调度、Hooks 规则等底层概念                                    | 封装响应式与调度细节，默认行为已足够高效                          |

### 4.1 设计哲学对照

| 设计理念       | React                                             | Vue 3                                                           |
| -------------- | ------------------------------------------------- | --------------------------------------------------------------- |
| **世界观**     | UI 是状态的映射，渲染函数每次从头执行             | 视图是数据的投影，依赖变化精准触发局部刷新                      |
| **表达形式**   | JSX + 完整 JavaScript（函数即组件）               | 模板 DSL 优先（亦支持 JSX/渲染函数）                            |
| **心智模型**   | 需理解 Fiber、并发、优先级、跳过策略              | 响应式直观，深入则需理解 Proxy 与 Effect                        |
| **编译器角色** | 可选（React Compiler 自动记忆化，不改变组件模型） | 必备（静态提升、PatchFlags、Block Tree 编码进渲染函数与 VNode） |
| **调度器角色** | 基于 Lane 的优先级调度，可中断、可抢占、可重放    | 微任务批量执行，去重、保证父子顺序与 pre/post 时序              |

### 4.2 取舍对照

| 取舍项               | React 的选择                                               | Vue 3 的选择                                     |
| -------------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| **通用性 vs 效率**   | 优先通用性：与宿主解耦，支持跨平台与并发                   | 优先效率：依赖模板静态结构做编译期优化           |
| **运行时 vs 编译时** | 偏运行时：把难题留给运行时解决，换来灵活性                 | 偏编译时：把难题左移到编译期，换来更轻的运行时   |
| **显式 vs 隐式**     | 偏显式：手动 `memo`、`useCallback` 等控制优化              | 偏隐式：框架自动追踪依赖、自动批量更新           |
| **灵活 vs 约束**     | 偏灵活：完整 JS 能力，但需自行承担性能与心智成本           | 偏约束：模板结构化换取可预测的优化，灵活性略受限 |
| **并发 vs 轻量**     | 偏并发：为 Suspense、Transition 等复杂交互模式提供基础设施 | 偏轻量：单次更新同步完成，避免状态回退与重放逻辑 |
